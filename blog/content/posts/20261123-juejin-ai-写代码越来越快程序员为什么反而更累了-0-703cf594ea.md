## 核心结论

来源事实：AI 可以更快完成页面、接口和测试等代码，但程序员的工作重点会从编写代码转向理解改动、判断结果、定位异常、处理任务依赖以及协调验收。代码生成速度提高，并不等于交付周期和整体工作量同步下降。

工程建议：评估效率时，应记录需求开始到验收完成的完整时间，同时关注评审等待、返工次数、审查是否延续到下班后，以及待验收改动是否积压。代码量、并行运行的 Agent 数量不能单独证明交付效率或工作负担已经改善。

## 能力机制

来源事实：多个 Agent 任务可以并行生成代码，但每项改动仍需单独验收。例如文档导出功能即使按钮可用、终端无报错，仍要检查内容完整性、表格与图片分页、无权限内容是否被导出、大文件失败后的页面恢复能力，以及编辑和保存逻辑是否受到影响。

任务切换也会产生额外成本。重新进入任务时，需要找回目标、已排除方案和上次进度；聊天记录越长，恢复上下文越困难。前端、接口和测试分别交给不同 Agent 时，如果没有提前统一失败响应格式等约定，各任务可能分别完成，组合后却无法正常工作。

工程建议：适合并行的任务应当彼此独立、影响范围清晰且结果容易自动检查。共同修改数据结构或存在依赖的任务，应先明确契约，必要时分阶段推进。

## 快速开始

来源未提供可确认执行的命令，因此不列出命令或密钥配置。

工程建议可按以下顺序调整工作方式：

1. 派发任务前写明范围和验收条件，例如搜索涉及哪些字段、是否保留排序、空结果如何展示、哪些既有行为不能改变。
2. 避免只描述“实现搜索”等宽泛目标，以免 Agent 自行扩展模糊匹配、缓存、排序调整或状态管理。
3. 为每次交接保留简短记录，包含改动内容、影响范围、实际验证项目、未解决问题，并关联文件、检查记录或样例。
4. 交付时附上可核验材料，如导出样例文件、必要截图、执行过的检查及已知限制。
5. 根据实际验收能力决定并行数量；结果开始积压时，先收尾或明确搁置项，再启动下一项。

## 适用边界

来源事实：自动化检查适合覆盖格式、类型和明确的权限用例，但无法替代对业务行为是否符合需求、关键场景是否遗漏的判断。测试通过、页面排版正常和 AI 的完成说明，也不能直接替代人工验收。

Agent 的完成状态只表示其输出已经产生，不能证明所有结果都已经验收。例如六项改动中只验收两项，其余四项仍应计入未完成工作。实现阶段缩短后，如果评审、联调、返工和验收没有获得相应时间，新增工作最终仍会落到具体人员身上。


## 核验清单

- 每项需求是否记录了从开始到验收完成的完整耗时？
- 是否分别统计了评审等待、返工和联调成本？
- 待验收改动是否持续积压，并集中到下班后处理？
- 并行任务是否相互独立，是否已统一接口、数据结构和失败响应等约定？
- 每项改动是否说明实际改了什么、影响哪里、验证了什么以及还有什么未解决？
- 是否提供了可打开或可复查的样例、检查记录和已知限制？
- 自动化检查是否覆盖格式、类型及明确权限规则？
- 人工验收是否检查了业务行为、权限边界、异常恢复和既有功能回归？
- 每次任务交接是否留下了足够的上下文，避免重新翻找聊天记录和推断进度？
- 收尾时是否记录已完成部分、未解决问题和下次继续的位置，并真正留出休息间隔？
