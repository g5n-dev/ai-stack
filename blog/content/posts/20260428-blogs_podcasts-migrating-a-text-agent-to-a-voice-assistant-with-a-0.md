## 摘要

#### 背景与动机
传统文本代理多以请求‑响应结构为主，交互简洁、输入可重复编辑。将其迁移为语音助理，需要在对话流、响应时延、错误容忍和用户体验上重新设计。

#### 文本与语音的核心差异
1. **输入形态**：语音是连续音频流，需实时转写并处理口音、噪声。
2. **输出形态**：语音返回需自然流畅、语调合适，且必须控制在毫秒级时延。
3. **错误恢复**：语音错误只能通过重新提问或确认纠正，缺乏回退编辑。
4. **上下文管理**：对话上下文需在每次语音回合中完整携带，避免信息丢失。

#### 迁移步骤概览
1. **评估业务场景**——是否需要实时交互、是否涉及复杂决策。
2. **选型与模型准备**——采用 Amazon Nova 2 Sonic，专有的声学‑语言联合模型。
3. **数据准备**——收集语音指令、纠错样本及口语化意图。
4. **对话设计**——把原有意图槽位转化为语音对话节点，加入确认、回退策略。
5. **系统 Prompt 适配**——精简、去除冗余结构，加入语气、口吻指令。
6. **工具与子代理复用**——保持原有业务工具（API、数据库）不变，通过统一的调用层暴露给语音代理。
7. **性能调优**——使用增量解码、流式 TTS，降低首响应时间。
8. **测试与监控**——语音质量、意图识别准确率、错误率、延迟等关键指标。

#### 代理架构拆解
- **前端层**：音频捕获 → 实时语音识别（ASR） → 语义理解（NLU）
- **核心层**：对话管理（DM） → 业务逻辑（子代理） → 动态 Prompt 生成
- **后端层**：业务工具调用 → 结果聚合 → 语音合成（TTS） → 音频返回

#### 工具与子代理的复用
原有文本代理中的工具（查询天气、下订单等）可直接封装为函数调用，保持接口不变。对话管理层通过统一的调用规范将工具结果注入到语音回复模板，实现一次实现、跨模态使用。

#### 系统 Prompt 的适配要点
- **简洁**：每轮仅携带必要上下文。
- **指令化语气**：明确“请稍等”“正在查询”等口语化指令。
- **错误预防**：加入“如果不确定，请先确认”类提示。

#### 常见陷阱与避免策略
- **过度依赖长文本**：语音输出不宜过长，需分段落或使用简短摘要。
- **忽视噪声环境**：应在训练数据中加入多种背景噪声，提高鲁棒性。
- **时延过高**：采用流式解码和预热模型，确保 P99 延迟 < 500 ms。
- **对话状态丢失**：使用持久化对话状态存储，避免多轮后信息遗漏。

#### 小结
把文本代理迁移到 Amazon Nova 2 Sonic 语音助理，核心在于保持业务逻辑不变的前提下，重新设计交互流、缩短响应时间、加强错误恢复，并通过统一的工具层实现代码复用。遵循上述步骤与最佳实践，可有效降低迁移风险，提升语音交互质量。
