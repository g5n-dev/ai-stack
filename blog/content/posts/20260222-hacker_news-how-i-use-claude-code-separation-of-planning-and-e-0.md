## 导语

在软件开发中，将构思规划与具体执行分离，是提升代码质量和维护效率的关键策略。本文以 Claude Code 为例，详细探讨了如何通过明确的职责划分来优化编程工作流。通过阅读本文，你将掌握一套结构化的方法，从而在利用 AI 辅助编码时，既能保持全局视野，又能确保代码实现的精准与可控。

## 评论

**文章中心观点**
在 AI 辅助编程中，应当严格区分“规划”（人类主导的高层架构与逻辑设计）与“执行”（AI 主导的代码生成与实现），以建立人类对代码库的终极控制权，防止因 AI 幻觉或缺乏全局观导致的系统腐烂。

**支撑理由与深度评价**

**1. 内容深度：认知架构的解耦与控制论**
*   **[你的推断]** 文章触及了人机协作中最核心的“认知层级”问题。作者主张的分离，本质上是将“系统 II”（慢思考、逻辑推理、架构决策）保留给人类，而将“系统 I”（快思考、模式匹配、语法生成）下放给 AI。
*   **[事实陈述]** 目前的大语言模型（LLM）是基于概率预测下一个 token，它们缺乏真正的长期规划能力和因果推理能力。如果让 AI 同时负责架构设计和具体实现，往往会陷入“局部最优解”，即代码写得漂亮，但模块间耦合度极高，甚至出现逻辑自洽但功能错误的幻觉。
*   **[作者观点]** 作者认为，通过先写设计文档或伪代码作为“契约”，再让 AI 填空，可以强制 AI 在人类设定的边界内工作。

**2. 实用价值：解决“AI 熵增”问题**
*   **[你的推断]** 这篇文章的方法论对于维护大型遗留代码库或高安全性系统（如金融、医疗）具有极高的指导意义。随着 AI 生成代码的比例提高，代码库的“熵”（混乱度）急剧上升，表现为命名风格不一、逻辑重复、隐式依赖增加。
*   **[事实陈述]** 许多开发者反馈，在使用 Copilot 等工具全权委托编码后，Debug 的时间并未减少，反而因为不理解 AI 生成的复杂逻辑链而增加。
*   **[作者观点]** “规划与执行分离”迫使开发者在 AI 动手前先理清思路，这实际上是一种“强制代码审查”的前置手段。

**3. 创新性：对抗“自动驾驶”依赖**
*   **[你的推断]** 在业界普遍追求“全自动 Agent（如 Devin）”的背景下，该文章提出了反直觉的观点：不要追求完全自动化，而是追求“可审计的半自动化”。
*   **[作者观点]** 这种方法将 Claude Code 从一个“代驾司机”降级为一个“听命的高级技工”。虽然听起来降低了 AI 的权限，但实际上提高了系统的可靠性。

**反例与边界条件**

尽管该观点极具价值，但在以下场景中可能失效或效率低下：

1.  **探索性编程：**
    *   **[你的推断]** 在编写一次性脚本、数据清洗或验证概念时，严格的规划往往是浪费时间。此时“AI 生成 -> 人类验证 -> 修改”的迭代循环比“先写设计文档”要快得多。
2.  **领域专家级重构：**
    *   **[事实陈述]** 如果开发者对特定库（如 React Hooks 或 Pandas）非常熟悉，他们可能直接让 AI 生成惯用代码，而不是先描述抽象逻辑。
3.  **上下文窗口极小的场景：**
    *   **[你的推断]** 如果 AI 无法记住整个项目的规划（上下文窗口限制），人类强行剥离规划层，会导致在执行层反复向 AI 解释背景，反而造成沟通摩擦。

**可验证的检查方式**

为了验证“规划与执行分离”是否真的优于“直接生成”，建议进行以下实验：

1.  **代码可维护性测试：**
    *   **指标**：引入“循环复杂度”和“代码重复率”作为指标。
    *   **实验**：让两组开发者完成同一功能。A 组使用“先写设计文档，再让 AI 实现”；B 组“直接与 AI 对话生成代码”。
    *   **观察窗口**：两周后，让第三组开发者对两组代码进行修改。记录修改所需时间和引入 Bug 的数量。如果 A 组修改时间显著少于 B 组，则文章观点成立。

2.  **幻觉捕获率：**
    *   **指标**：逻辑错误与 API 误用次数。
    *   **实验**：统计在一个包含 10 个功能点的开发任务中，AI 生成的代码在第一次运行时通过单元测试的比例。
    *   **观察窗口**：如果“分离模式”下的一通过率更高，说明规划层起到了有效的约束作用。

3.  **开发流体验：**
    *   **指标**：开发者认知负荷。
    *   **实验**：使用 NASA-TLX 量表测量开发者在两种模式下的脑力负担。
    *   **观察窗口**：如果在“分离模式”下，开发者在“规划阶段”负荷高，但在“Review 阶段”负荷极低，而在“直接生成模式”下全程焦虑，则证明了分离策略的心理优势。

**总结**

这篇文章的价值不在于教授具体的 Prompt 技巧，而在于提出了一种**“人机契约”**的工程伦理。它提醒我们，在 AI 时代，程序员的核心竞争力不再是敲击键盘的速度，而是**定义问题**和**判断真伪**的能力。虽然该模式在小型、快速迭代的原型开发中可能显得繁琐，但对于构建健壮、可维护的软件系统，这是一条必须遵守的原则。

```python
# 示例1：任务规划器 - 分离计划与执行
class TaskPlanner:
    """任务规划器，负责生成执行计划"""
    def generate_plan(self, task_description):
        # 根据任务描述生成具体步骤
        if "爬取网页" in task_description:
            return [
                "1. 确定目标URL",
                "2. 发送HTTP请求",
                "3. 解析HTML内容",
                "4. 提取所需数据",
                "5. 保存结果"
            ]
        elif "数据分析" in task_description:
            return [
                "1. 加载数据集",
                "2. 数据清洗",
                "3. 探索性分析",
                "4. 可视化结果"
            ]
        else:
            return ["1. 理解需求", "2. 设计方案", "3. 实施解决"]

class TaskExecutor:
    """任务执行器，负责执行具体步骤"""
    def execute_step(self, step):
        # 模拟执行步骤
        print(f"正在执行: {step}")
        return f"已完成: {step}"

def main():
    planner = TaskPlanner()
    executor = TaskExecutor()
    
    # 规划阶段
    task = "爬取网页数据"
    plan = planner.generate_plan(task)
    print(f"执行计划: {plan}")
    
    # 执行阶段
    for step in plan:
        result = executor.execute_step(step)
        print(result)

if __name__ == "__main__":
    main()
```

```python
class RequestBuilder:
    """请求构建器，负责构建API请求"""

    """请求发送器，负责发送请求和处理响应"""

def main():
    builder = RequestBuilder()
    sender = RequestSender()

if __name__ == "__main__":
```

```python
# 示例3：数据处理管道 - 分离处理步骤定义与执行
class DataPipeline:
    """数据处理管道，定义处理步骤"""
    def __init__(self):
        self.steps = []
    
    def add_step(self, step_name, step_func):
        """添加处理步骤"""
        self.steps.append((step_name, step_func))
    
    def process(self, data):
        """执行所有处理步骤"""
        result = data
        for step_name, step_func in self.steps:
            print(f"执行步骤: {step_name}")
            result = step_func(result)
        return result

def main():
    # 定义处理函数
    def clean_data(data):
        return [x.strip() for x in data if x.strip()]
    
    def transform_data(data):
        return [x.upper() for x in data]
    
    def validate_data(data):
        return [x for x in data if len(x) > 2]
    
    # 创建并配置管道
    pipeline = DataPipeline()
    pipeline.add_step("数据清洗", clean_data)
    pipeline.add_step("数据转换", transform_data)
    pipeline.add_step("数据验证", validate_data)
    
    # 处理数据
    raw_data = [" apple ", "banana", "", "  pear  ", "kiwi"]
    processed_data = pipeline.process(raw_data)
    print(f"处理结果: {processed_data}")

if __name__ == "__main__":
    main()
```

## 最佳实践指南

### 实践 1：明确区分规划阶段与执行阶段

**说明**: 在使用 Claude Code 时，应将工作流程明确划分为两个独立的阶段。规划阶段专注于理解需求、分析问题和制定解决方案；执行阶段专注于具体的代码编写、调试和实现。这种分离可以避免在思路尚未清晰时就急于动手，减少返工。

**实施步骤**:
1. 在开始任何编码任务前，先与 Claude 进行纯文本对话，明确目标
2. 不要在规划阶段请求 Claude 生成代码或执行文件操作
3. 确认方案完整无误后，再进入执行阶段
4. 在执行阶段严格按照既定方案实施

**注意事项**: 避免在规划阶段让 Claude 展示代码片段，这会分散对整体架构的注意力

---

### 实践 2：建立完整的上下文文档

**说明**: 在规划阶段，应让 Claude 生成一份详尽的上下文文档，包含项目背景、技术栈、架构设计、关键决策和实施计划。这份文档将成为后续执行阶段的单一事实来源。

**实施步骤**:
1. 让 Claude 阅读并理解现有代码库
2. 请求 Claude 生成一份全面的技术规划文档
3. 审查并确认文档中的所有细节
4. 将该文档作为后续对话的核心参考

**注意事项**: 文档应包含足够的细节，使 Claude 在执行阶段无需频繁询问背景信息

---

### 实践 3：使用"伪代码"作为过渡桥梁

**说明**: 在规划完成后、正式编码前，让 Claude 生成详细的伪代码或注释骨架。这有助于验证逻辑正确性，同时保持对实现细节的关注分离。

**实施步骤**:
1. 在规划阶段末期请求生成伪代码
2. 审查伪代码的逻辑流程而非语法细节
3. 确认伪代码覆盖所有边界情况
4. 将伪代码作为执行阶段的蓝图

**注意事项**: 伪代码应足够详细，但不应包含具体语言语法

---

### 实践 4：分模块验证而非整体实现

**说明**: 在执行阶段，应将大任务分解为小的、可验证的模块。每个模块完成后立即测试验证，而不是完成所有代码后再进行测试。

**实施步骤**:
1. 将整体方案拆分为独立的功能模块
2. 按优先级逐个实现模块
3. 每个模块实现后立即进行单元测试
4. 确保模块通过测试后再进行下一个

**注意事项**: 模块间的接口应在规划阶段明确定义

---

### 实践 5：维护严格的会话边界

**说明**: 为规划和执行阶段创建独立的对话会话。规划会话专注于思考和分析，执行会话专注于实施和调试。这样可以避免上下文混乱和指令冲突。

**实施步骤**:
1. 为新项目创建专门的"规划会话"
2. 完成规划后，保存关键输出并结束会话
3. 创建新的"执行会话"，输入规划文档作为上下文
4. 在执行过程中遇到架构问题时，返回规划会话

**注意事项**: 不要在执行会话中频繁修改规划阶段确定的核心决策

---

### 实践 6：建立明确的验收标准

**说明**: 在规划阶段必须明确定义"完成"的标准。这些标准应包括功能要求、性能指标、测试覆盖率和代码质量等方面。

**实施步骤**:
1. 在规划文档中列出明确的验收清单
2. 为每个功能点编写可测试的验收标准
3. 定义性能基准和质量门禁
4. 在执行阶段对照清单逐项验证

**注意事项**: 验收标准应具体、可测量、可实现

---

### 实践 7：记录决策历史与变更理由

**说明**: 在整个开发过程中，应维护一份决策日志，记录重要技术决策、方案选择及其理由。当需要回溯或调整时，这份日志至关重要。

**实施步骤**:
1. 在规划阶段记录每个关键决策的思考过程
2. 在执行阶段记录任何对原计划的偏离及原因
3. 定期审查决策日志，确保一致性
4. 在项目交接或复盘时使用该日志

1: 为什么需要将“规划”与“执行”分离开来？

1.  **降低认知负荷**：编写代码需要高度的专注力，而思考架构和宏观设计则需要不同的思维模式。混合进行容易导致疲劳和疏漏。

3.  **便于迭代**：先制定完整的计划，可以让人类审查者在大规模代码生成前就发现逻辑错误或设计缺陷，从而节省修改时间。
4.  **提高可靠性**：分步进行可以让 AI 专注于单一任务，要么专注于思考，要么专注于编写，从而提高每一阶段输出的质量。
