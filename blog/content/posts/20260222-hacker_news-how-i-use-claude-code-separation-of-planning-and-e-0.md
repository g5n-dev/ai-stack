## 导语

随着 AI 编程工具的普及，如何将其从“自动补全”升级为可靠的“研发搭档”，成为开发者关注的焦点。本文基于作者的实际使用经验，探讨了在 Claude Code 中将“规划”与“执行”分离的具体策略。通过这种工作流，你可以有效减少大模型在复杂任务中的幻觉与不可控性，在保持人类主导权的同时，最大化地利用 AI 提升编码效率与工程质量。

## 评论

**文章中心观点**
在 AI 辅助编程中，应当将“规划”与“执行”严格分离，由人类主导架构设计，由 AI 负责具体实现，以建立可验证的反馈闭环。

**支撑理由与边界条件分析**

1.  **认知带宽与上下文窗口的错配（事实陈述 / 你的推断）**
    *   **理由**：文章指出 LLM（即使是 Claude 3.5 Sonnet）在处理超长文件或复杂跨文件修改时，容易产生“幻觉”或丢失细节。通过人类编写详细的“规划文档”，实际上是利用人类的高阶逻辑能力压缩信息，为 AI 提供高密度的上下文，降低了 Token 消耗中的噪音比例。
    *   **反例/边界条件**：对于单一功能函数的编写（如写一个正则表达式或排序算法），这种分离反而增加了认知负担。直接对话交互的效率高于“写文档-运行-读文档”的循环。

2.  **线性因果链的可追溯性（作者观点 / 技术事实）**
    *   **理由**：当 AI 代码出错时，如果是一次性生成的大段代码，Debug 的过程如同大海捞针。文章提倡的“规划先行”使得每一步代码修改都有据可查。如果执行结果偏离计划，人类可以迅速定位是“计划错了”还是“执行错了”，从而实现精准纠错。
    *   **反例/边界条件**：在探索性编程或原型开发阶段，开发者本身就没有明确的规划，此时强行分离规划与执行会扼杀灵活性，AI 的“发散性思维”优势无法发挥。

3.  **信任机制的建立（行业观点 / 你的推断）**
    *   **理由**：从行业角度看，目前阻碍企业大规模采纳 AI 编码的核心痛点不是“速度”，而是“安全性”和“可控性”。该文章提出的方法论本质上是一种“人机协作的治理模式”。人类作为“架构师”审核计划，AI 作为“承包商”执行代码，这种分工让开发者敢于将关键任务交给 AI，因为控制权始终在人类手中。
    *   **反例/边界条件**：对于初级开发者，由于缺乏架构设计能力，他们写出的“规划文档”可能质量低下，导致 AI 执行出更糟糕的代码，反而不如直接让 AI 辅助生成代码再由人 Review 来得有效。

**多维度深入评价**

1.  **内容深度：从“Prompt Engineering”到“Workflow Engineering”的升维**
    文章的深度在于它没有停留在如何写好 Prompt 的技术层面，而是上升到了工作流设计的哲学高度。它揭示了当前 LLM 的本质局限：**LLM 是优秀的执行者而非优秀的战略家**。文章通过“Plan”和“Execute”的解耦，实际上是在构建一个“外部记忆系统”和“逻辑锚点”，这是对当前 AI 上下文遗忘缺陷的一种高明补偿。

2.  **实用价值：解决“AI 编程黑盒”焦虑**
    对于资深工程师而言，最大的痛苦不是 AI 写不出代码，而是不知道 AI 改动了什么。文章建议的通过 Markdown 文档作为“单一信源”，让 Claude Code 基于此文件进行编辑，具有极高的实战价值。这种方法将隐性的思维过程显性化，极大地降低了 Code Review 的心智负担。

3.  **创新性：重提“结构化编程”的人机版**
    虽然“分而治之”是老生常谈，但文章将其具体化为针对 AI Agent 的交互协议。它提出了一种新的交互范式：**文档即指令**。这不同于传统的 Chat 对话模式，更接近于传统的“规格说明书驱动开发”，但在 AI 的加持下，消除了传统瀑布模型中“写文档”与“写代码”之间的割裂感。

4.  **争议点：效率与灵活性的博弈**
    文章的观点可能受到“敏捷开发”拥护者的质疑。在快速迭代中，维护一份同步的规划文档成本极高。如果需求每小时都在变，更新规划文档的时间可能超过了直接写代码的时间。此外，这种方法假设人类总是能制定出完美计划，忽略了人类自身也会犯错的事实。

**实际应用建议**

*   **适用场景**：重构遗留系统、编写多文件关联的核心业务逻辑、需要高度一致性的 API 设计。
*   **不适用场景**：单文件脚本、探索性 API 测试、UI 细节的微调（这些场景直接对话更高效）。

**可验证的检查方式**

1.  **Bug 修复耗时对比**：
    *   *实验*：选取一个中等复杂度的 Bug（涉及 3-5 个文件），一组使用“直接对话修复”，另一组使用“规划-执行分离”。
    *   *指标*：统计从开始到通过测试用例的时间，以及修复过程中引入的新 Bug 数量。

2.  **代码可读性评分**：
    *   *观察*：让高级工程师对 AI 生成的代码进行盲审。
    *   *指标*：评估代码逻辑的连贯性。采用“分离法”的代码通常具有更强的逻辑线性，更容易被人类理解。

3.  **上下文窗口利用率**：
    *   *观察*：观察 Token 消耗记录。
    *   *指标*：检查在多次迭代中，是否因为规划文档的存在，减少了重复向 AI 解释背景信息的 Token 消耗。

4.  **“幻觉”发生率**：
    *   *实验*：让 AI 修改一个不存在的函数或调用错误的库。
    *   *指标*：在“规划先行”模式下

# 示例1：任务规划与执行分离系统
class TaskPlanner:
    """负责规划任务步骤"""
    def __init__(self):
        self.steps = []
    
    def add_step(self, description, action):
        """添加任务步骤"""
        self.steps.append({
            'description': description,
            'action': action
        })
    
    def get_plan(self):
        """返回完整的执行计划"""
        return [step['description'] for step in self.steps]

class TaskExecutor:
    """负责执行任务"""
    def __init__(self, planner):
        self.planner = planner
    
    def execute(self):
        """按计划执行任务"""
        for step in self.planner.steps:
            print(f"执行: {step['description']}")
            result = step['action']()
            print(f"结果: {result}\n")

# 使用示例
planner = TaskPlanner()
planner.add_step("加载数据", lambda: "数据已加载")
planner.add_step("处理数据", lambda: "数据处理完成")
planner.add_step("保存结果", lambda: "结果已保存")

executor = TaskExecutor(planner)
executor.execute()
```

# 示例2：AI助手规划-执行框架
class AIAssistant:
    def __init__(self):
        self.plan = []
    
    def plan_task(self, user_request):
        """根据用户请求规划任务"""
        # 这里模拟AI规划过程
        if "文件" in user_request:
            self.plan = [
                "1. 识别文件类型",
                "2. 读取文件内容",
                "3. 分析文件结构",
                "4. 生成处理方案"
            ]
        elif "数据" in user_request:
            self.plan = [
                "1. 连接数据源",
                "2. 查询数据",
                "3. 数据清洗",
                "4. 生成报告"
            ]
        return self.plan
    
    def execute_plan(self):
        """执行规划的任务"""
        results = []
        for step in self.plan:
            print(f"执行步骤: {step}")
            # 模拟执行结果
            result = f"{step} - 完成"
            results.append(result)
        return results

# 使用示例
assistant = AIAssistant()
user_request = "帮我处理这个CSV文件"
plan = assistant.plan_task(user_request)
print("执行计划:", plan)

print("执行结果:", results)

# 示例3：工作流编排器
class WorkflowPlanner:
    """工作流规划器"""
    @staticmethod
    def create_workflow(task_type):
        """根据任务类型创建工作流"""
        workflows = {
            "etl": ["extract", "transform", "load"],
            "ml": ["train", "validate", "deploy"],
            "report": ["collect", "analyze", "visualize"]
        }
        return workflows.get(task_type, [])

class WorkflowExecutor:
    """工作流执行器"""
    def __init__(self):
        self.handlers = {
            "extract": lambda: "数据提取完成",
            "transform": lambda: "数据转换完成",
            "load": lambda: "数据加载完成",
            "train": lambda: "模型训练完成",
            "validate": lambda: "模型验证完成",
            "deploy": lambda: "模型部署完成"
        }
    
    def execute_workflow(self, workflow):
        """执行工作流"""
        results = []
        for step in workflow:
            if step in self.handlers:
                result = self.handlers[step]()
                results.append(result)
                print(f"步骤 {step}: {result}")
        return results

# 使用示例
planner = WorkflowPlanner()
executor = WorkflowExecutor()

# 创建ETL工作流
etl_workflow = planner.create_workflow("etl")
print("ETL工作流:", etl_workflow)
etl_results = executor.execute_workflow(etl_workflow)

# 创建机器学习工作流
ml_workflow = planner.create_workflow("ml")
print("\n机器学习工作流:", ml_workflow)
ml_results = executor.execute_workflow(ml_workflow)
```

## 最佳实践指南

### 实践 1：明确区分规划阶段与执行阶段

**说明**: 将与 AI 的交互过程划分为两个截然不同的阶段。规划阶段专注于理解需求、分析架构和制定方案，执行阶段专注于具体的代码实现和问题解决。这种分离可以避免在未完全理解问题前就急于编写代码。

**实施步骤**:
1. 在开始任何编码任务前，先进行需求分析和方案讨论
2. 确认理解无误后，再进入具体的代码实现阶段
3. 在执行过程中遇到架构问题时，暂停并回到规划阶段

**注意事项**: 不要在同一个对话中同时进行架构讨论和代码实现，这样容易导致混乱

---

### 实践 2：使用独立会话管理不同阶段

**说明**: 为规划阶段和执行阶段分别创建独立的对话会话。规划阶段的会话专注于高层设计和决策，执行阶段的会话专注于具体的编码任务。

**实施步骤**:
1. 创建一个专门的规划会话，用于讨论项目结构、技术选型和实现方案
2. 规划确定后，创建新的执行会话，引用规划阶段的结论
3. 在执行会话中专注于具体的代码实现，避免重新讨论架构问题

**注意事项**: 保留规划会话的记录，以便在执行阶段需要时可以快速回溯

---

### 实践 3：在规划阶段输出结构化文档

**说明**: 在规划阶段要求 AI 输出结构化的设计文档，包括项目结构、文件列表、关键算法描述等，而不是直接生成代码。

**实施步骤**:
1. 要求 AI 先生成项目概览和技术架构说明
2. 获取详细的文件结构和模块划分
3. 确认关键功能的实现思路和伪代码描述

**注意事项**: 确保文档清晰完整，能够作为后续编码的独立参考

---

### 实践 4：分批次实现功能模块

**说明**: 将整体功能拆分为小的、可独立验证的模块，每次只要求 AI 实现一个或少数几个相关模块。

**实施步骤**:
1. 根据规划文档，将功能按优先级和依赖关系排序
2. 每次对话专注于实现一个完整的子功能
3. 完成并验证后再进入下一个模块

**注意事项**: 避免一次性要求生成大量代码，这样会增加调试和验证的难度

---

### 实践 5：建立明确的上下文传递机制

**说明**: 在从规划阶段转换到执行阶段时，建立清晰的上下文传递方式，确保执行阶段能够准确理解规划阶段的决策。

**实施步骤**:
1. 在执行会话开始时，明确引用规划阶段的关键决策
2. 提供规划阶段输出的结构化文档作为上下文
3. 在执行过程中遇到歧义时，明确指出参考规划文档的哪一部分

**注意事项**: 上下文传递要简洁明确，避免冗余信息干扰

---

### 实践 6：在执行前进行人工审查

**说明**: 在让 AI 执行代码生成或修改之前，人工审查其理解和计划是否正确，避免基于错误理解生成大量错误代码。

**实施步骤**:
1. 要求 AI 在生成代码前先说明其理解的任务和实现计划
2. 人工审查这个计划是否与预期一致
3. 确认无误后再要求 AI 开始编码

**注意事项**: 这个步骤虽然看似增加时间，但能大幅减少后续调试时间

### 实践 7：保持迭代反馈循环

- 保持对 AI 输出的批判性思维至关重要，开发者必须严格审核 AI 生成的代码与方案，以确保系统的安全性与稳定性。

### 1: 为什么需要将“规划”和“执行”分离开来？

1: 为什么需要将“规划”和“执行”分离开来？

2: 在实际操作中，这种分离的工作流是怎样的？

3: 这种方法是否适用于所有类型的编程任务？
