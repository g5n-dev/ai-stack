## 核心结论

DeepSeek Harness 的插件化设计提供了三条可迁移到 AI Coding 工作流的原则：插件之间无特权等级，注册是可逆的副作用，配置采用有序分层覆盖。基于这三条原则，AI Coding 工作流可以拆分为三层架构：静态资产与工作流运行时分离，资产通过契约组织为可装配插件，运行时解除对单一引擎的绑定。这套设计的收益是消除跨平台复制、隔离项目差异、避免流程长期绑定；代价是团队需要承担版本管理、依赖解析、冲突检测和迁移兼容的成本。插件化并非默认答案，它只在复制与绑定的成本已经高于组合与治理的成本时成立。

## 能力机制

DeepSeek Harness 将模型适配器、工具注册表、会话日志和 Agent Loop 都实现为插件，通过配置完成替换，插件卸载时注册的服务和事件一并撤销。它采用有序分层配置：预置 Bundle、Profile 补丁、用户级补丁和命令行补丁依次叠加，上层可按 ID 替换下层配置。

AI Coding 工作流的三层架构对应不同的职责边界。静态资产层负责声明流程拓扑、阶段契约、Agent 角色、Skill 和领域知识，不执行调度，不写运行状态。运行时层负责解析配置、推进阶段、调用检查器、维护状态、处理暂停与恢复。适配层通过投影把同一份中立资产转换成不同 Coding Agent 能读取的格式，产物为只读派生结果。

资产内部的装配单元采用声明式阶段配置。每个阶段可声明 ID、默认实现、技能替换点、能力列表、人工确认要求和离开前需通过的 Gate 检查。阶段内部可拆出节点，通过 enabled、depends_on、activation 字段控制启用、依赖和条件触发。契约约束产出格式而非实现细节，只要替代 Skill 满足同一份输出契约即可替换。互斥知识应物理隔离为独立资产，声明各自的适用范围、版本、风险等级和复核要求，运行时冻结架构选择而非临时推断。

多运行时场景下需要两类控制：执行权仲裁确保任一任务在任一时刻只被一个运行时持有写权限，契约兼容检查确保运行前验证资产版本、运行时能力和 Gate 接口，不能识别的字段必须明确报错。

## 快速开始

多运行时协作需要配置执行权仲裁和契约兼容检查，具体实现方式取决于所选运行时框架。

## 适用边界

这套三层架构适合满足以下条件的团队：项目之间确实存在差异，同时使用多种 Coding Agent，并且愿意维护统一资产源。如果项目技术栈和交付流程高度一致，一份共享规范加少量项目配置通常更省事。插件化不是默认答案，它只在复制与绑定的成本已经高于组合与治理的成本时成立。深度定制需要使用者理解插件职责、加载顺序、配置覆盖和兼容关系；框架维护者需要提供稳定契约、可追踪的配置树和足够可靠的默认组合。当前 DeepSeek Harness 仍处于 Developer Preview，官方明确提醒会出现破坏兼容性的变更，依赖其插件机制的系统也需关注版本演进。

## 核验清单

在评估或实施这套架构时，可逐项核验以下要点：

- 静态资产层是否仅包含声明性内容，调度代码是否完全位于运行时层
- 投影产物是否为只读派生结果，是否建立了回到源资产修改的流程
- 阶段声明是否包含明确的 Gate 定义，Gate 检查是否由独立检查器执行
- Skill 替换是否基于产出契约而非提示词相似性
- 互斥架构规范是否物理隔离，是否声明了适用范围、版本和风险等级
- 多运行时场景下是否配置了执行权仲裁机制
- 多运行时场景下是否配置了契约兼容检查，是否明确报错而非静默忽略
- 团队是否具备维护版本管理、依赖解析和冲突检测的能力
- 所依赖的运行时框架是否已脱离预览阶段，是否存在破坏兼容性的风险
