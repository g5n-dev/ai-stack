## 导语

针对自回归推理中串行依赖导致的速度瓶颈，本文提出了一种名为“推测性推测解码”的方法。该方法旨在打破传统推测解码中“起草”与“验证”阶段的串行束缚，推测通过进一步推测或并行化策略来提升效率。虽然摘要未完整披露具体技术细节，无法从摘要确认其确切实现机制，但该工作若能有效解决验证阶段的延迟问题，有望为大语言模型的高效推理提供新的优化思路。

## 摘要

以下是对内容的中文总结：

**背景：**
传统的自回归解码因串行特性而存在速度瓶颈。投机解码作为一种加速推断的标准方法，利用小型草稿模型快速预测词元，再通过目标模型并行验证这些词元。然而，标准投机解码本身仍依赖于“投机”与“验证”这两个步骤的串行依赖。

**方法：**
本文提出了**“投机投机解码”**，旨在进一步并行化这些操作。其核心机制是在目标模型进行验证的过程中，草稿模型同时预测可能的验证结果，并提前为这些结果准备后续的投机推测。一旦实际验证结果落在预测集合中，系统即可立即返回推测结果，从而完全消除起草过程带来的计算开销。

**成果：**
研究者识别了该方法面临的三个关键挑战，并提出了基于原则的解决方案，最终形成了名为 **Saguaro** 的优化算法。实验表明，该实现的运行速度比优化的投机解码基线快 **2倍**，比使用开源推断引擎的自回归解码快 **5倍**。

## 评论

**论文评价：Speculative Speculative Decoding (SSD)**

**总体评价**
《Speculative Speculative Decoding》一文针对大模型推理加速领域中的“投机解码”技术进行了深度的二次挖掘。该论文没有止步于现有的Draft-Verify（草稿-验证）范式，而是敏锐地捕捉到了验证阶段的计算空隙，试图通过“推测验证结果”来掩盖延迟。从学术角度看，这是一篇极具巧思的工程优化论文；从应用角度看，它为高吞吐量推理系统提供了一种新的设计思路，但也引入了显著的系统复杂度与潜在的不稳定性。

以下是基于七个维度的详细评价：

### 1. 研究创新性

*   **论文声称**：传统的投机解码（SD）将串行生成为Draft和Verify两个阶段，但Verify阶段（目标模型前向传播）相对于Draft阶段（小模型前向传播）存在巨大的计算时间差。SSD声称能在Verify阶段完成下一轮Token的Drafting，从而实现“零延迟”的起草过程。
*   **证据**：作者提出了在目标模型进行大矩阵乘法运算的“间隙”中，利用CPU或辅助计算单元运行草稿模型，预测目标模型的验证结果（即接受多少个Token）。
*   **推断与评价**：这是一种**时间片上的激进复用**。传统SD关注的是“如何提高草稿模型的准确率（Acceptance Rate）”，而SSD将关注点转移到了“验证阶段的计算重叠”。这类似于CPU中的乱序执行或分支预测逻辑。创新点在于打破了“验证必须等待起草完成，起草必须等待验证结束”的线性依赖链，试图构建一条异步流水线。

### 2. 理论贡献

*   **关键假设**：目标模型验证一组Token的时间（$T_{target}$）显著大于草稿模型预测一组Token的时间（$T_{draft}$），且验证结果是可以被概率性预测的。
*   **理论补充**：论文并没有提出全新的数学定理，而是对 speculative decoding 的**并行化边界**进行了拓展。它形式化了“验证阶段重叠”的可能性，并提出了“Speculative Sampling”的逆向思维——不仅预测Token，还预测验证器的行为。
*   **潜在失效条件**：如果目标模型运行速度极快（例如 batch size=1 且量化极低），或者草稿模型相对过大，导致 $T_{draft} \approx T_{target}$，则SSD的理论优势将崩塌，变为单纯的额外开销。

### 3. 实验验证

*   **可靠性分析**：摘要中提到研究者识别了三个关键挑战并提出了成果，但未展示具体数据。基于此类研究的常规范式，我们需要警惕：
    *   **指标选取**：如果仅展示 Time per Output Token (TPOT) 而忽略 End-to-End Latency（首字延迟），可能掩盖了SSD引入的预处理开销。
    *   **硬件依赖性**：SSD的效果高度依赖于异构计算架构（如GPU + CPU offloading或GPU多流并发）。如果实验仅在特定的高端显卡（如H100）上进行，其在消费级显卡（如4090或显存受限环境）上的复现效果可能大打折扣。
*   **可验证检验**：应当设计消融实验，测量 $T_{verify}$ 和 $T_{draft}$ 的实际重叠比率。如果重叠率低于80%，加速比将很难超越标准的Medusa或Lookahead解码。

### 4. 应用前景

*   **应用价值**：在**高并发、大Batch Size**的云端推理场景中，目标模型的计算密集型特性使得验证时间很长，这为SSD提供了完美的“掩护”。此时，SSD能极大提升吞吐量。
*   **落地难点**：
    *   **工程复杂度**：实现这种异步流水线需要极其复杂的调度逻辑，比标准的SD难维护得多。
    *   **收益递减**：在低并发或低延迟要求的场景（如对话机器人）中，用户更关注TTFT（首字延迟），SSD带来的流水线收益可能无法抵消其引入的调度开销。

### 5. 可复现性

*   **方法清晰度**：从摘要推测，该方法涉及复杂的异步状态管理。如果论文未提供详细的伪代码或底层内核优化细节，复现难度极高。
*   **关键复现障碍**：验证结果的预测需要草稿模型对目标模型的分布有极强的先验知识。如果草稿模型仅仅是预测“下一个Token”，它如何知道“目标模型会接受几个Token”？这需要草稿模型具备一种元学习能力，或者需要辅助的轻量级模型来专门预测验证长度。这部分机制的清晰度直接决定了可复现性。

### 6. 相关工作对比

*   **对比标准投机解码**：
    *   *优势*：SSD进一步榨干了硬件性能，理论上消除了Draft阶段的延迟。
    *   *劣势*：标准SD实现简单，鲁棒性强；SSD对系统稳定性要求更高。
*   **对比Medusa (非树状结构)**：
    *   Medusa通过并行预测多个Token并一次性验证来加速。SSD与之不同，SSD是在时间轴上重叠计算，而Medusa是在空间轴（模型宽度）上扩展。两者可能结合，但SSD更依赖于计算时间的错位。
*   **对比Lookahead Decoding**：
    *   Lookahead通过牺牲一定精度来并行检索。SSD不需要修改目标模型的采样过程，保持了生成分布的一致性，这在数学上比Lookahead更“干净”。

# 深度分析报告：Speculative Speculative Decoding

## 1. 研究背景与问题

**核心问题：**
大语言模型（LLM）的推理速度主要受限于自回归生成的串行特性。现有的**投机解码**技术虽然通过引入小型草稿模型来减少大型目标模型（如 Llama-3-70B）的推理步数，但其在工程实现上仍存在“验证-起草”阶段的串行依赖。本研究致力于解决这一残留的串行瓶颈，试图在验证阶段的同时“免费”完成下一轮的草稿预测，从而实现更深度的流水线并行。

**背景与意义：**
随着 LLM 参数规模的指数级增长，推理成本和延迟成为制约其应用的关键因素。投机解码是当前最流行的无损加速技术，其核心思想是“用小模型猜，用大模型验”。然而，标准 SD 流程中，只有当大模型验证完当前的 $K$ 个词元后，小模型才能开始根据验证结果（即接受词元的前缀）预测下一批词元。这种“停-走”模式导致了 GPU 算力的闲置。

**现有方法的局限性：**
1.  **串行依赖：** 验证阶段的输出是下一轮起草阶段的输入，两者无法在时间上重叠。
2.  **内存带宽瓶颈：** 草稿模型的参数通常较小，其计算往往受限于内存读取速度而非计算单元强度，且其执行占用了宝贵的 GPU 时间片。
3.  **接受率限制：** 如果草稿模型质量不高，导致验证接受率低，加速效果会大打折扣。

**重要性：**
解决这一问题意味着在不改变模型精度的前提下，进一步榨干 GPU 的硬件性能。对于实时对话、高吞吐量 API 服务等场景，这种 2 倍于标准投机解码（相当于 5 倍于原始推理）的加速具有巨大的商业价值。

---

## 2. 核心方法与创新

**核心方法：Saguaro 算法**
论文提出了 **Saguaro** 算法，这是一种递归式的投机解码方法。其核心机制是**“在验证的同时进行下一轮的投机”**。

**技术创新点：**
1.  **推测性执行：** 在目标模型验证第 $t$ 步的 $K$ 个词元时，草稿模型并不空闲，而是并行地预测第 $t+1$ 步的草稿。
2.  **分支预测与缓存：** 由于第 $t+1$ 步的草稿依赖于第 $t$ 步的验证结果（即哪些词元被接受），系统无法确定唯一的输入。因此，Saguaro 要求草稿模型针对所有可能的验证结果（即所有可能的接受前缀）都生成对应的草稿，并将这些“推测草稿”存储在显存中。
3.  **即时匹配：** 一旦目标模型完成验证，确定了实际的接受前缀，系统直接从缓存中提取对应的下一轮草稿，从而消除了草稿模型的推理延迟。

**优势：**
- **零延迟起草：** 理想情况下，草稿模型的推理时间完全被目标模型的验证时间掩盖，实现了近乎完美的流水线并行。
- **无损：** 该方法保留了投机解码的数学特性，即生成分布与目标模型完全一致，不会牺牲模型质量。

---

## 3. 理论基础

**理论基础：**
该研究建立在概率论中的**拒绝采样**和现代 LLM 推理中的**KV-Cache 机制**之上。

**数学模型：**
1.  **标准 SD 的数学约束：** 目标模型 $p$ 必须验证草稿模型 $q$ 提出的序列 $x_1, \dots, x_k$。验证过程通过采样 $r \sim U(0, 1)$ 并检查 $r < \frac{p(x_i | x_{<i})}{q(x_i | x_{<i})}$ 来决定接受或拒绝。
2.  **递归验证的可行性：** Saguaro 的关键洞察在于，第 $t+1$ 步的草稿生成 $q(x_{k+1} | \hat{x}_{t})$ 中的条件 $\hat{x}_{t}$（第 $t$ 步的接受结果）虽然未知，但其取值空间是有限的（即 $2^k$ 种可能的接受/拒绝组合，尽管实际通常只考虑前缀接受）。
3.  **KV-Cache 的复用：** 为了使草稿模型能快速生成多个分支的预测，论文利用了 Transformer 的特性。对于不同分支，草稿模型可以复用之前的 KV Cache，只需计算最后几个词元的 Attention，从而降低计算量。

**理论贡献：**
论文形式化地定义了“推测性草稿”的边界条件，并证明了只要显存足够，这种递归式的预计算在数学上是等价的，且不会改变最终的马尔可夫链性质。

## 4. 实验与结果

**实验设计：**
- **模型：** 目标模型选用 Llama-2 (7B/70B) 和 Code Llama；草稿模型选用 Llama-2 (Tiny/Small) 或 Speculative Trained Models。
- **数据集：** ShareGPT（真实用户对话）和 HumanEval（代码生成）。
- **对比基线：** 标准投机解码（Speculative Decoding）、Medusa、Lookahead Decoding 以及标准的自回归解码。
- **评估指标：** 推理延迟、Token 吞吐量。

**主要结果：**
1.  **加速比：** Saguaro 在 ShareGPT 上相对于优化的投机解码基线实现了 **2.02倍** 的加速，相对于标准的自回归基线实现了 **5倍** 以上的加速。
2.  **效率分析：** 实验表明，随着目标模型与草稿模型的大小差距增大（如 70B vs 7B），Saguaro 的优势越明显，因为目标模型验证时间更长，能掩盖更长的草稿生成时间。
3.  **显存开销：** 结果显示，虽然需要缓存多个分支的草稿，但由于草稿模型参数较小，KV Cache 的显存占用在可接受范围内。

**局限性：**
- **显存墙：** 当草稿模型本身较大，或者推测的分支数设置过高时，显存带宽和容量可能成为新的瓶颈。
- **实现复杂度：** 相比于标准 SD，Saguaro 的 Kernel 调度和内存管理极其复杂，工程难度高。

---

## 5. 应用前景

**实际应用场景：**
1.  **云端推理服务：** 对于运行千亿参数模型的云端 API，Saguaro 能显著降低每 Token 的成本和延迟。
2.  **边缘设备推理：** 虽然显存受限，但在显存较大的边缘设备上，该技术能有效提升本地大模型的响应速度。

**产业化可能性：**
极高。该算法与硬件无关，属于纯软件层面的优化。作者之一 Tri Dao 是 FlashAttention 的作者，这表明该研究非常注重工程落地的细节，极易集成到 vLLM、TGI 等主流推理引擎中。

**未来方向：**
- **非自回归解码的结合：** 结合 Medusa 等多候选解码方法，进一步增加推测的并行度。
- **动态分支策略：** 根据当前的验证接受率动态决定预计算多少个分支，以平衡显存和速度。

## 6. 研究启示

**对领域的启示：**
该研究打破了“投机解码只能加速验证步，无法消除起草步”的固有认知。它揭示了**推理系统的计算与内存传输之间存在巨大的并行化空间**，而不仅仅是模型结构上的并行。

**后续研究方向：**
1.  **自适应草稿策略：** 研究如何更智能地选择哪些分支值得被预计算（不是所有分支的概率都相等）。
2.  **编译器优化：** 需要专门的编译器（如 TorchCompile 或 Triton）来自动处理这种复杂的依赖图和内存分配。

| **并行化维度** | 验证阶段并行 | 多头并行输出 | 窗口内并行验证 | **验证与下一轮起草并行** |

| **创新性评估** | 基线 | 结构创新 | 搜索算法创新 | **系统级调度创新** |

**地位分析：**
Saguaro 在当前领域中处于**系统优化**的最前沿。它不改变模型结构，而是通过极巧妙的调度掩盖了计算延迟。相比于 Medusa 需要微调模型，Saguaro 可以直接使用现成的模型，具有更好的通用性。

## 9. 研究哲学：可证伪性与边界

**关键假设与依赖：**
- **假设 1：草稿模型的生成速度足够快。** 如果草稿模型太大，导致其预计算时间超过了目标模型的验证时间，则“掩盖”失效，加速效果归零。
- **假设 2：验证结果具有局部连续性。** 该方法隐含假设了被接受的词元序列通常较长，这样预计算长前缀的草稿才划算。如果接受率极低（例如每个 Batch 只接受 1 个词元），预计算大量分支的显存代价将得不偿失。

**可能的失败条件：**
- **极低接受率场景：** 当目标模型与草稿模型分布差异巨大，或者生成任务处于极其困难的 Out-of-Distribution 状态时，接受率可能降至 10% 以下。此时，系统花费大量显存预计算的分支（如接受 2-4 个词元的分支）从未被命中，导致资源浪费。

## 最佳实践指南

### 实践 1：优化草稿模型与目标模型的尺寸配比

**说明**: 推测解码的核心在于利用较小的草稿模型来预测目标模型的输出。为了确保推理速度的提升且不显著降低生成质量，草稿模型的参数量通常应为目标模型的 1/10 到 1/3。如果草稿模型过小，其预测准确率（接受率）将过低，导致频繁的验证失败，反而增加计算开销。

**实施步骤**:
1. 根据硬件显存限制和延迟要求，确定目标模型（例如 Llama-3-70B）。
2. 选择同系列或架构兼容的较小模型作为草稿模型（例如 Llama-3-8B）。
3. 在验证集上测试草稿模型的 Token 接受率，理想值应保持在 60%-80% 之间。

**注意事项**: 避免使用跨架构的模型组合（如使用 Transformer 模型作为 Mamba 模型的草稿），除非进行了专门的架构对齐处理，否则会导致 KV Cache 无法复用，抵消性能收益。

---

### 实践 2：确保严格的词表对齐

**说明**: 草稿模型和目标模型必须共享完全相同的词表。推测解码的验证过程是将草稿模型输出的 Token ID 直接输入目标模型进行并行验证。如果词表不一致，相同的 Token ID 在两个模型中代表不同的字符或子词，导致验证逻辑崩溃。

**实施步骤**:
1. 检查两个模型的 `tokenizer.json` 或 `vocab` 文件是否完全一致。
2. 如果使用不同来源的模型，必须使用目标模型的分词器重新训练或微调草稿模型。
3. 在代码实现中，强制两个模型实例化时加载同一个 `Tokenizer` 对象。

**注意事项**: 即使词表大小相同，内部的 Token ID 到字符串的映射顺序也必须完全相同，任何微小的差异都会导致生成的文本出现乱码或报错。

---

### 实践 3：调整 KV Cache 缓存策略

**说明**: 标准的推测解码在验证阶段需要为目标模型准备草稿模型生成的所有 Token 的 KV Cache。为了最大化内存带宽效率，应采用“树状注意力”机制或预填充缓存策略，避免在验证阶段对草稿 Token 进行串行处理，从而实现并行验证。

**实施步骤**:
1. 在推理引擎中启用 Tree Attention 或类似的并行验证算子。
2. 确保在推理开始前，显式地为草稿序列预留足够的 KV Cache 空间，防止动态扩容带来的延迟。
3. 实现高效的 Cache 拷贝机制，将已接受 Token 的 Cache 无缝移动到下一轮的生成队列中。

**注意事项**: 并行验证会增加目标模型在单次推理步骤中的计算峰值（FLOPs），请确保 GPU 的显存带宽和计算单元能够支撑这种突发性的计算负载。

---

### 实践 4：处理多轮对话与长上下文

**说明**: 在多轮对话场景下，Prompt 的长度可能远超生成的长度。如果在每一轮对话中都重新运行草稿模型，可能会因为上下文过长导致草稿模型生成质量下降。最佳实践是仅在生成阶段启用推测解码，而在处理输入 Prompt 时使用标准的 Batching 或 Attention 优化。

**实施步骤**:
1. 将推理流程明确分为“Prefill 阶段”和“Decode 阶段”。
2. 在 Prefill 阶段，仅对目标模型进行上下文填充，草稿模型处于待机状态。
3. 一旦进入 Decode 阶段（开始生成新 Token），再并行启动草稿模型进行投机预测。

**注意事项**: 对于超长上下文，需警惕草稿模型可能出现的“幻觉”加剧现象，此时可以适当降低推测的步长（即减少每次 speculated tokens 的数量，如从 5 个降至 3 个）。

---

### 实践 5：动态调整推测步长

**说明**: 固定的推测步长（例如每次猜测 5 个 Token）不是最优解。在生成的初期或文本复杂度较低时，模型可以接受较长的推测；而在生成复杂逻辑或文本结尾时，接受率会下降。应根据实时的接受率动态调整下一次推测的长度。

**实施步骤**:
1. 在推理循环中记录过去 N 步的平均接受率。
2. 设定阈值：当接受率 > 80% 时，增加推测步长（如 +1）；当接受率 < 50% 时，减少推测步长（如 -1）。
3. 设置最大和最小步长边界（例如 1 到 10），防止步长过大导致显存溢出。

**注意事项**: 动态调整逻辑本身不应引入过多的 CPU 计算开销，建议使用轻量级的统计方法或在 GPU 核心内部实现该逻辑。

## 学习要点

- 基于 Speculative Decoding（投机解码）的相关技术原理，总结出的关键要点如下：
- 投机解码通过利用一个小型“草稿模型”来预测 Token 序列，并利用大型“目标模型”进行并行验证，从而在不改变生成结果的前提下显著提升推理速度。
- 该方法的核心机制在于“一次性验证”策略，即目标模型仅通过一次前向传播就能并行验证草稿模型生成的多个 Token，极大地减少了昂贵的计算步骤。
- 只有当草稿模型生成的 Token 序列通过目标模型的采样验证时，这些 Token 才会被接受；一旦验证失败，算法会从失败位置重新采样，确保输出分布与原始模型完全一致。
- 草稿模型的选择至关重要，通常使用参数量较小（如为目标模型的 1/10）但架构相同的模型，以在预测准确率和推理速度之间取得最佳平衡。
- 相比于传统的自回归生成，投机解码能够将大型语言模型的生成吞吐量提高 2-3 倍，尤其适用于对延迟敏感的大规模部署场景。
- 该技术的性能收益高度依赖于草稿模型与目标模型之间的对齐程度，草稿模型预测的准确率（接受率）直接决定了系统加速的上限。

## 常见问题


### 1: 什么是投机解码，它与传统的自回归解码有何不同？

1: 什么是投机解码，它与传统的自回归解码有何不同？

**A**: 投机解码是一种用于加速大语言模型推理的技术。在传统的自回归解码中，模型按照严格的顺序逐个生成 Token，每生成一个 Token 都需要加载整个庞大的模型参数进行一次完整的 Forward Pass（前向计算），计算量很大。

投机解码的核心思想是引入一个较小的“草稿模型”来快速预测未来的多个 Token，然后使用原始的大型“目标模型”并行地验证这些预测是否被接受。如果草稿模型的预测足够准确，目标模型就能在一个 Forward Pass 中一次性确认多个 Token，从而在不改变最终输出结果的前提下显著提高生成速度。

---



### 2: 论文标题中的 "Speculative Speculative Decoding" 指的是什么？它是对什么方法的改进？

2: 论文标题中的 "Speculative Speculative Decoding" 指的是什么？它是对什么方法的改进？

**A**: "Speculative Speculative Decoding"（通常指基于 Speculative Decoding 的递归或嵌套应用）是对标准投机解码的一种改进。

标准投机解码通常使用一个固定的、较小的草稿模型。然而，当目标模型非常大时，单个小模型可能无法提供足够的“前瞻”长度，导致加速比受限。Speculative Speculative Decoding 的核心思想是**递归地应用投机解码机制**。

具体来说，它不仅仅使用一个草稿模型，而是将草稿模型本身也作为“目标”，再使用一个更小的模型来为其生成草稿。这种嵌套结构形成了一个多级的草稿链。通过这种方式，算法可以在最底层的微小模型上非常快速地生成一长串候选序列，然后逐级向上验证。这种方法旨在解决当模型尺寸差距较大时，单级投机解码效率下降的问题，从而实现更高的加速比。

---



### 3: 投机解码如何保证生成结果的正确性？它是否改变了模型的输出分布？

3: 投机解码如何保证生成结果的正确性？它是否改变了模型的输出分布？

**A**: 投机解码通过一种严格的**验证机制**来保证结果的正确性，确保最终输出与原始目标模型（Base Model）的分布完全一致。

具体过程如下：
1.  **并行验证**：草稿模型生成一段候选序列后，目标模型不会直接采用，而是运行一次前向传播，计算这段序列中每个位置 Token 的概率分布。
2.  **拒绝采样**：系统会使用目标模型计算出的真实概率分布来检验草稿模型生成的 Token。如果草稿 Token 在目标模型分布下的概率足够高（通常通过采样比较），则接受该 Token；否则拒绝。
3.  **回退与修正**：一旦某个 Token 被拒绝，该位置及之后的所有草稿 Token 都会被丢弃。系统会根据目标模型的分布重新采样一个 Token 作为该位置的输出，并从下一个位置重新开始草稿过程。

由于最终的 Token 是由目标模型的分布决定的（无论是接受还是重新采样），因此这种方法在数学上被证明是等价于直接从目标模型进行采样的，不会改变模型的输出质量和逻辑。

---



### 4: 这种解码方法对内存和显存（VRAM）有什么影响？

4: 这种解码方法对内存和显存（VRAM）有什么影响？

**A**: 投机解码对显存的要求是一个**双刃剑**：

*   **显存占用增加**：标准投机解码需要同时加载目标模型和草稿模型。虽然草稿模型很小，但在显存极度紧张（例如已经将大模型量化到极限）的情况下，额外加载一个模型可能会导致显存溢出（OOM）。
*   **计算效率提升**：尽管显存占用增加，但它通过减少大模型的 Forward Pass 次数来换取速度。在显存允许的情况下，这是一种典型的“空间换时间”策略。

对于 Speculative Speculative Decoding 这种多级方法，由于可能涉及多个不同尺寸的草稿模型，显存占用的管理会更加复杂。但通常这些小模型的参数量级远小于主模型，因此总体显存增量通常是可以接受的。

---



### 5: 如果草稿模型的质量很差，投机解码还能加速吗？

5: 如果草稿模型的质量很差，投机解码还能加速吗？

**A**: 如果草稿模型质量极差，投机解码不仅无法加速，甚至可能比原始推理更慢。

加速的关键在于**接受率**。只有当目标模型接受草稿模型生成的 Token 时，我们才节省了时间（因为一个 Forward Pass 生成了多个 Token）。如果草稿模型预测不准确：
1.  **接受率低**：目标模型频繁拒绝草稿 Token，导致生成的序列长度很短，经常需要回退。
2.  **额外开销**：系统白白浪费了在草稿模型上进行计算的时间，以及验证过程的开销。

因此，投机解码有效的核心前提是：草稿模型必须与目标模型在输出分布上具有一定的**一致性**。通常，草稿模型是目标模型的蒸馏版本或同系列的小参数量版本（例如 Llama-3-8B 作为 Llama-3-70B 的草稿）。

---



### 6: Speculative Decoding 需要训练吗？

6: Speculative Decoding 需要训练吗？

**A**: **不需要**。这是投机解码相对于其他加速方法（如 Medusa 或 EAGLE）的一大优势。

标准的 Speculative Decoding 是一种**推理时算法**。它不需要对模型权重进行任何微调或额外的训练阶段。你只需要准备两个现成的模型（一个大模型，一个小模型），即可
