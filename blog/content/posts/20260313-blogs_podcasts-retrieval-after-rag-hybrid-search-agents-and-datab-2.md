## 摘要

基于Turbopuffer联合创始人Simon Hørup Eskildsen的分享，以下是对RAG（检索增强生成）系统中“后检索”阶段的技术总结，主要涵盖混合搜索、智能体架构及数据库设计三个维度：

### 1. 混合搜索的必要性
RAG系统常面临一个核心权衡：**向量搜索**擅长捕捉语义相似性，但往往忽略具体的关键词（如产品编号、专有名词）；而**关键词搜索**（BM25）精确匹配能力强，却缺乏语义理解能力。

**结论是“混合搜索”：** 将向量搜索与关键词搜索结合。业界（如Weaviate）发现，单纯的向量检索效果往往不如混合检索。通过结合两者，可以同时弥补语义模糊和关键词遗漏的缺陷，显著提升召回率。

### 2. 智能体在检索中的角色
随着大语言模型（LLM）应用从简单的问答转向更复杂的**智能体**，检索策略也发生了变化。智能体需要使用工具进行推理和规划，这对检索提出了新要求：

*   **多轮检索：** 智能体不仅需要一次检索，而是需要根据上下文进行多次、迭代式的检索。
*   **结构化数据利用：** 智能体不仅依赖非结构化的文本，还需要查询结构化数据（如数据库元数据、Schema），以便更精准地定位信息。

### 3. 数据库设计的核心：HNSW与分离式架构
为了支撑高效的混合搜索和智能体需求，底层向量数据库的设计至关重要，特别是**HNSW（Hierarchical Navigable Small World）**算法：

*   **HNSW的优势：** 它是目前最快的向量索引算法之一。其核心优势在于**检索延迟与数据量无关**。无论数据库中有100条还是1亿条数据，检索速度都保持极快且稳定，这对于生产环境的用户体验至关重要。
*   **存储与计算的分离：** 传统的向量数据库常受限于单点故障或扩展性问题。Turbopuffer的设计理念是将存储层与计算层分离。通过利用云存储（如S3）作为共享存储层，可以在无状态的计算节点上运行HNSW，从而实现高可用性、快速故障恢复和弹性扩展，解决了传统架构的瓶颈。

### 总结
在RAG系统的后检索阶段，单纯依赖向量检索已不足够

## 最佳实践指南

### 实践 1：采用混合搜索架构以平衡语义与关键词匹配

**说明**: 单纯的向量搜索擅长捕捉语义意图，但在处理专有名词、缩略语或精确匹配请求时往往表现不佳。混合搜索结合了稠密向量和稀疏向量（如 BM25）的优势。Turbopuffer 的经验表明，在检索后重排序阶段结合这两种方法，能显著提高召回率和准确度，减少“幻觉”或遗漏关键信息的情况。

**实施步骤**:
1. 为数据集同时生成 Embedding 向量和用于关键词索引的元数据。
2. 在查询阶段，并行执行向量搜索和关键词搜索（BM25）。
3. 使用 Reciprocal Rank Fusion (RRF) 或加权评分算法合并两个结果列表。
4. 对合并后的前 N 个结果进行精细的重排序。

**注意事项**: 确保向量数据库和全文搜索引擎之间的数据同步一致性，或者在单一支持混合索引的数据库（如 Turbopuffer）中操作，以降低架构复杂度。

### 实践 2：优化数据库设计以支持高效的过滤操作

**说明**: 在 RAG 系统中，元数据过滤（Metadata Filtering）与向量搜索的结合至关重要。许多查询不仅需要语义相似，还需要满足特定条件（如时间范围、文档类型）。最佳实践要求在向量索引设计之初就将元数据作为一等公民，支持在向量空间搜索的同时进行快速的预过滤或后过滤，避免不相关的数据干扰检索结果。

**实施步骤**:
1. 识别检索流程中关键的过滤维度（如 `user_id`, `created_at`, `category`）。
2. 选择支持在索引层面进行元数据过滤的向量数据库，避免“先搜后滤”导致的性能瓶颈。
3. 对高频过滤字段建立专门的索引结构。
4. 在查询时，将过滤条件与向量查询一起发送，确保返回的上下文既相关又合规。

**注意事项**: 监控过滤条件对查询延迟的影响，避免在过滤基数极高的字段上进行全量扫描。

### 实践 3：利用智能代理进行多步推理与检索

**说明**: 传统的 RAG 往往是一次性检索，而引入 Agent 模式可以将检索过程转化为多步推理。Agent 可以根据初次检索的结果判断信息是否充足，如果不足则生成新的查询策略进行二次检索，或者调用不同的工具。这种“检索后 RAG”的循环机制能处理更复杂的问题，减少对单一检索质量的依赖。

**实施步骤**:
1. 设计一个具备“反思”能力的 Agent 循环逻辑。
2. 设定评估标准，让 Agent 判断当前检索到的上下文是否足以回答用户问题。
3. 如果信息不足，Agent 应自动重写查询或使用不同的关键词进行迭代检索。
4. 设置最大迭代次数以防止无限循环或成本过高。

**注意事项**: Agent 模式会显著增加 Token 消耗和延迟，需要通过缓存机制和并行查询来优化性能。

### 实践 4：实施检索后评估与重排序

**说明**: 检索出的结果并不一定按照与问题的相关性完美排序。引入重排序模型，如 Cross-Encoders，可以在检索阶段之后对候选文档进行更精细的评分。这一步骤虽然增加了一些计算开销，但能大幅提升最终送入 LLM 的上下文质量，从而提高生成答案的准确性。

**实施步骤**:
1. 在检索阶段获取比最终需要更多的文档（例如检索 Top 50，但只需要 Top 5）。
2. 将这 50 个文档与用户查询一起输入到专门的重排序模型中。
3. 根据重排序模型的得分重新排列文档。
4. 选取得分最高的前 K 个文档作为上下文。

**注意事项**: 重排序模型会增加推理延迟，建议仅对经过初步筛选的候选集进行重排序，而不是对所有数据操作。

**实施步骤**:
1. 收集领域内的文档对（Query-Document 正负样本对）。
2. 选择一个基础开源 Embedding 模型（如 BERT 或 RoBERTa 变体）。

**注意事项**: 微调需要一定的机器学习工程能力，且需定期更新模型以适应新术语和知识的变化。

## 学习要点

- 在 RAG 系统中，混合检索（结合关键词 BM25 与语义向量搜索）的效果优于单一的向量检索，能有效弥补语义匹配对专有名词和精确关键词识别能力的不足。
- 检索后处理是提升生成质量的关键环节，通过重排序（Reranking）模型对初次召回的结果进行精细筛选，能显著提高最终答案的相关性和准确性。
- 纯粹的向量检索并不等同于“搜索”，专业的搜索引擎需要结合稀疏向量（关键词）与密集向量（语义），以同时满足模糊匹配与精确查找的需求。
- 数据库设计对检索性能有决定性影响，应优先考虑为不同类型的数据（如文本块与元数据）建立适当的索引结构，而非盲目追求单一的大模型能力。
- 引入代理机制可以解决静态检索的局限性，通过自主规划查询策略和迭代检索，能够处理复杂问题并减少单一检索步骤带来的信息丢失。
- 在处理大规模数据集时，向量数据库的扩展性（如 HNSW 索引的优化）和查询延迟是核心挑战，需要平衡索引构建成本与检索速度。
- 元数据过滤是混合检索中不可或缺的一环，将结构化元数据与非结构化文本检索相结合，能够大幅提高搜索结果的精准度和可控性。
