## 核心结论

文档更新后 RAG 索引不会自动同步，需要显式维护。全量重建适合小规模知识库，逻辑简单且天然保持一致性；增量更新适合大规模高频变更场景，但需自行处理幂等性、块映射和批量写入等问题。更换 Embedding 模型时只能全量重建，无法增量。

## 能力机制

RAG 索引维护涉及两种核心机制。

全量重建每次从当前文档状态出发，重新完成读取、切块、嵌入、索引的全部流程。优点在于无需维护历史状态，天然消除残留数据；缺点是资源消耗与文档规模线性相关，重建期间需要保留旧索引服务线上请求。

增量更新仅处理变动的部分，实现方式是将文档转换为块并追加或覆盖现有索引。关键能力包括：基于文件路径和内容哈希生成稳定块 ID 保证幂等性；维护文档与块 ID 的映射表以支持删除旧块；通过队列或时间窗口批量处理以摊薄嵌入计算成本。

## 快速开始

实现增量更新需要准备三样东西：稳定的块 ID 生成策略、文档与块 ID 的映射表、批量写入机制。

块 ID 生成可采用文件路径加内容哈希的组合方式，确保同一文档无论处理多少次都产生相同 ID。映射表用于记录每篇文档对应的所有块 ID，删除文档时先查表获取所有相关块 ID，再执行删除操作。写入时建议攒批处理，避免单条处理带来的固定成本开销。

定时全量重建的实现方式相对简单：编写定时任务遍历所有文档，重新生成索引后切换服务。

## 适用边界

全量重建的典型场景是团队内部文档库，文档量级在几百篇且更新频率较低，定时凌晨重建即可覆盖。法规合规库等每季度集中更新的场景也适合整体重建。

增量更新适合商品信息、政策文档等每日大量变动的场景。内部维基类应用在总量达到百万块级别时，建议采用日常增量加每周全量重建对账的混合策略。

更换 Embedding 模型是特殊边界：旧向量与新向量不在同一向量空间，索引必须全量重建。

## 核验清单

增量更新需确认以下要素已实现：块 ID 生成策略可复现且稳定；文档与块 ID 映射表维护完整，支持删除时清理所有旧块；批量写入机制已实现，避免单条高频写入；旧块删除逻辑已覆盖，防止新旧内容同时被检索导致冲突。

全量重建需确认：定时任务已配置；重建期间旧索引可继续服务或已设计切换方案；磁盘空间充足支持双份索引暂存。

模型更换前需确认：已完成新模型评估；重建任务已排期；旧索引已保留或已确认不再需要。
