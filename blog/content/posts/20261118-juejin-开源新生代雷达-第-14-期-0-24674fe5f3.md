## 核心结论

本期的核心结论是：开源热度不能直接等同于工程质量、留存意愿或长期活跃度。

基于 2026 年 11 月 18 日的仓库元数据快照，24 小时增量榜中，`BaaRai/ARTEX` 以新增 1,745 Star 位居第一，总 Star 达 6,484，Fork 数为 2,822，Fork/Star 为 43.52%。项目采用 AGPL-3.0，仍有提交和 issue，但作者明确不推荐该自动化渗透测试项目，也不提供操作信息。

另一项修正是许可证判断：`lemomo-ai/lemo-opuscar` 的 GitHub `license` 字段虽然显示 `NOASSERTION`，实际 LICENSE 文件却采用分路径授权和 REUSE 规范。因此，核验许可证不能只看平台自动识别结果。

来源还观察到，工具型本地软件在本期头部项目中占比上升，但这些样本不足以证明所有工具都比 AI 项目存活更久。

## 能力机制

雷达的收录口径是创建不足 60 天的新仓库，并按 Star 增速及本地快照差分排序。24 小时增量来自 2026-11-17 与 2026-11-18 两次相隔 24.0 小时的快照对比，而不是累计 Star 的直接相减。

主要观察维度包括：

- **热度**：24 小时 Star 增量与累计 Star。
- **分发**：Fork 数及 Fork/Star，用来观察代码是否被复制。
- **留存信号**：Watch/Star 比，但该值只能表示关注倾向，不能替代真实用户留存。
- **交付强度**：提交时间、release、open issues 和 issue 响应情况。
- **存活状态**：仓库是否可访问、是否 archived，以及最近推送时间。

对于许可证，来源专门使用仓库 LICENSE 正文、逐文件许可声明及第三方素材登记进行核验。这套机制可以识别平台无法映射的混合授权结构。

## 快速开始

复现本期核验时，可按来源已确认的流程执行，无需安装被跟踪项目：

1. 选取创建不足 60 天的仓库，读取 Star、Fork、Watch、open issues、archived、`pushed_at` 和 release 信息。
2. 将当前快照与 24 小时前的本地快照差分，计算真实增量。
3. 读取 README 和 LICENSE 正文，确认项目用途、交付状态及授权边界。
4. 对 `NOASSERTION` 仓库继续检查分路径许可、第三方素材登记和明确排除项。
5. 将 Star 增量与 issue 增长、提交和 release 状态并列观察，避免仅按热度排序。

来源中的数据抓取时间为 2026-11-18 06:10–06:40（Asia/Shanghai），但没有提供可确认的安装或运行命令。

## 适用边界

本报告基于公开仓库元数据、README、许可证正文和公开讨论，未执行安装验证、代码审计或安全审计。Star 表示注意力，Watch/Star 表示关注倾向，提交和 release 表示交付活动，仓库可访问性表示存活状态；这些指标都不是质量证明。

许可证描述也不构成法律意见。商用、复制素材或使用第三方生成内容时，应以仓库授权原文及适用条款为准。自动化渗透测试、授权红队测试和未授权渗透在技术形态上难以仅凭仓库信息区分，因此来源不提供 ARTEX 的操作方法。

文中关于风险、热度与项目生命周期的判断仅对应本期样本，不能直接外推为普遍规律。
