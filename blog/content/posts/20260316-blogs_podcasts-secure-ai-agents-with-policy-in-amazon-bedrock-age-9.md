# Secure AI agents with Policy in Amazon Bedrock AgentCore

## 摘要/简介

本文将带你了解 Amazon Bedrock AgentCore 中的 Policy 如何构建一个确定性的执行层，该层独立于 Agent 自身的推理运行。你将学习如何将业务规则的自然语言描述转换为 Cedar 策略，然后利用这些策略实施细粒度、具有身份感知的管控，使 Agent 仅能访问其用户被授权使用的工具和数据。你还将看到如何通过 AgentCore Gateway 应用 Policy，在运行时拦截并评估每一次 Agent 对工具的请求。

## 导语

随着生成式 AI 的深入应用，如何在复杂业务中确保 Agent 合规执行成为关键挑战。本文介绍 Amazon Bedrock AgentCore 的 Policy 机制，探讨如何构建独立于推理的确定性执行层，将自然语言规则转化为 Cedar 策略。读者将学习实施细粒度、具有身份感知的管控，利用 AgentCore Gateway 在运行时精准拦截并评估工具调用，确保 Agent 仅访问授权范围内的数据与功能。

## 摘要

本文介绍了如何利用 Amazon Bedrock AgentCore 中的“Policy（策略）”功能，确保 AI 智能体在安全受控的环境中运行。

核心内容总结如下：

1.  **独立确定性执行层**：
    Policy 在 AgentCore 中创建了一个独立的强制执行层。这意味着安全检查不依赖于智能体自身的推理过程，从而提供了一个确定性且可靠的安全保障，防止智能体因“幻觉”或逻辑错误而越权。

2.  **自然语言转策略**：
    该功能允许用户将业务规则的**自然语言描述**直接转换为 **Cedar 策略**（一种开源的语言）。这使得定义复杂的业务逻辑变得更加简单直观。

3.  **细粒度与身份感知控制**：
    通过这些策略，系统可以实施精细化的访问控制。它能确保 AI 智能体仅代表用户访问其**被授权**的工具和数据，有效防止未经授权的数据泄露或操作。

4.  **运行时拦截与评估**：
    通过 AgentCore Gateway，Policy 会在**运行时**拦截并评估每一个智能体向工具发出的请求。只有符合策略的请求才会被放行，从而实现了实时的安全合规。

**一句话总结：**
Amazon Bedrock AgentCore 的 Policy 功能通过将业务规则转化为 Cedar 策略，并在 Gateway 层进行实时拦截与身份感知校验，为 AI 智能体提供了一个独立于其推理逻辑之外的、确定性的安全防护层。

## 评论

**中心观点：**
文章主张在亚马逊 Bedrock AgentCore 中引入基于 Cedar 语言的策略层，作为独立于大模型推理之外的确定性“护栏”，以解决生成式 AI 不可控的固有风险，实现企业级的安全合规。

**支撑理由与深度评价：**

**1. 确定性逻辑与概率性模型的解耦（事实陈述 + 作者观点）**
文章的核心论点在于将“业务规则”从“模型推理”中剥离。
*   **分析：** 这是一个非常务实且具备深度的架构视角。大模型本质上是概率性的，无法保证 100% 遵守指令。通过引入 Cedar 策略层，Bedrock AgentCore 实际上是在 AI 智能体外部构建了一个硬编码的“红队”系统。这种“双系统”设计（系统 1 为直觉/LLM，系统 2 为逻辑/Policy）符合当前 AI 工程化落地的最佳实践。
*   **反例/边界条件：** 这种解耦并非万能。对于需要深度上下文理解的模糊规则（例如“不得对客户表现出傲慢”），Cedar 这种基于属性的逻辑很难直接编码，策略层只能处理结构化的权限和数据访问问题，无法解决语气或隐含意图的违规。

**2. 自然语言到策略代码的转换效率（作者观点 + 你的推断）**
文章强调了将自然语言描述转化为 Cedar 策略的流程。
*   **分析：** 这里的创新点在于降低了策略编写的门槛。然而，从技术角度看，这中间存在一个“语义鸿沟”。自然语言是模糊的，而代码是精确的。如果文章暗示存在一个全自动的转换器，那么其准确率和覆盖率将是巨大的挑战。如果是指人工辅助翻译，则运维成本依然存在。
*   **反例/边界条件：** 业务规则往往包含复杂的“时间”或“上下文”依赖（例如“用户连续三次失败后锁定”）。将这类状态机逻辑转化为 Cedar 的声明式策略，可能会导致策略文件极其复杂，甚至难以调试，反而增加了系统维护的负担。

**3. 独立执行层的安全性（事实陈述）**
文章指出 Policy 的执行独立于 Agent 的推理。
*   **分析：** 这是安全架构中的关键原则——零信任。即便 Agent 被提示词注入攻击，只要底层的策略解析器（如 Cedar）只验证 Token 和 Action，攻击者也无法绕过权限读取数据库。这种分层防御极大地提高了系统的抗攻击能力。
*   **反例/边界条件：** 独立执行层并不代表完全安全。如果输入给策略层的参数本身就是由 LLM 幻觉生成的错误参数（例如 LLM 将 User ID 识别错误），策略层虽然阻止了非法访问，但也直接导致了业务流程的失败。这种“假阴性”在用户体验上可能难以接受。

**争议点或不同观点：**

*   **性能瓶颈 vs. 安全性：** 引入独立的策略检查层必然增加推理的延迟。在高并发、低延迟要求的场景下，每一次工具调用都要经过策略验证，这可能成为系统的性能瓶颈。
*   **Cedar 语言的适配性：** Cedar 是 AWS 开源的语言，虽然强大，但其学习曲线对于传统的业务分析师来说依然存在。企业是否需要为了使用 AgentCore 而专门培养一支 Cedar 策略编写团队？这可能是落地的阻力。
*   **过度依赖外部防御：** 批评者可能认为，过度依赖外部策略层会掩盖模型本身的对齐问题。理想状态应该是模型本身就懂得遵守规则，而非依靠外部“保姆”。

**实际应用建议：**

1.  **策略先行设计：** 在开发 Agent 之前，先定义好结构化的数据权限模型，不要试图用 LLM 的 Prompt 来解决权限问题。
2.  **混合验证模式：** 对于高风险操作（如删除数据、转账），强制使用 Cedar 策略硬阻断；对于低风险操作（如聊天语气），可以依赖模型自身的 Soft Guardrail，以平衡性能与安全。
3.  **策略测试覆盖：** 建立 Cedar 策略的单元测试库，模拟各种 Prompt Injection 攻击，确保策略层在极端情况下也能稳定运行。

**可验证的检查方式（指标/实验/观察窗口）：**

1.  **阻断率与误报率监控：** 在生产环境中观察 Policy 层的拦截日志。
    *   *指标：* 每 1000 次 Agent 调用中，Policy 拒绝的次数。
    *   *验证：* 如果拒绝率过高，说明策略过严或 LLM 频繁生成错误参数；如果为 0，说明策略可能形同虚设。
2.  **延迟增加测试：**
    *   *实验：* 对比开启 Policy 和关闭 Policy 两种情况下的 Agent 端到端响应时间。
    *   *验证：* 观察 Policy 引入的额外延迟是否在用户可接受的范围内（通常建议 < 200ms）。
3.  **对抗性样本测试：**
    *   *观察窗口：* 在红队测试阶段，输入典型的越狱指令。
    *   *验证：* 检查 Agent 是否试图执行被禁止的操作，以及 Policy 层是否成功抛出 `UnauthorizedError`，而不是由 LLM 产生拒绝文本（前者是策略生效，后者是模型配合，两者有本质区别）。

## 技术分析

# 技术分析：Amazon Bedrock AgentCore 的策略安全机制

## 1. 核心观点与架构逻辑

**核心理念**
文章提出了**控制层与推理层的分离**原则。传统的 AI 安全主要依赖提示词工程或模型微调，这种方式具有不确定性。Amazon Bedrock AgentCore 引入的 Policy 机制，旨在构建一个独立于大模型推理之外的确定性安全层，确保 Agent 的行为严格遵循业务规则。

**架构逻辑**
该架构的核心思想是将业务规则（Policy）从 Agent 的决策逻辑中剥离。AI Agent（LLM）负责规划与推理，而策略引擎负责权限与合规的最终裁决。这种分离解决了大模型固有的不可预测性问题，通过引入 Cedar 策略语言，将自然语言描述的业务规则转化为机器可执行的强制性约束。

## 2. 关键技术要点

**技术组件**
1.  **Amazon Bedrock AgentCore**：负责编排 Agent 行为的核心引擎，在执行动作前进行策略拦截。
2.  **Cedar 策略语言**：一种用于表达权限和访问控制的通用语言，支持逻辑验证。
3.  **确定性评估引擎**：区别于 LLM 的概率生成，该引擎基于二元逻辑（允许/拒绝）进行判断。

**实现机制**
系统通过以下流程实现安全控制：
1.  **策略定义**：将业务规则（如“仅经理可批准大于 $1000 的退款”）转化为 Cedar 策略代码。
2.  **上下文提取**：在 Agent 运行时，提取用户角色、资源属性和环境状态等上下文信息。
3.  **策略评估**：在 Agent 调用工具或 API 之前，AgentCore 拦截请求并将上下文传入 Cedar 引擎。
4.  **强制执行**：系统依据评估结果执行操作或阻断请求，确保行为合规。

**技术难点与应对**
*   **语义转译准确性**：将模糊的自然语言规则转化为精确的代码逻辑存在挑战。通常采用 LLM 辅助生成代码，并引入人工审核环节以确保逻辑严密。
*   **上下文实时性**：策略判断依赖准确的实时数据。解决方案是将 Agent 的数据源与策略引擎的属性源打通，确保决策依据的有效性。

## 3. 实际应用价值

**架构指导意义**
该技术为 AI 应用的安全设计提供了标准参考范式。它明确了 Prompt Engineering 主要用于优化交互体验，而代码级别的策略检查才是保障系统安全的防线。

**典型应用场景**
1.  **企业权限管理**：在 Agent 执行文件读取、修改或删除操作时，强制执行基于角色的访问控制（RBAC）。
2.  **金融交易合规**：限制 Agent 的操作范围，例如禁止特定角色的 Agent 执行转账，或限制单笔交易金额。
3.  **数据隐私保护**：确保 Agent 在处理敏感数据时，严格遵循数据隔离策略，防止跨层级的数据泄露。

## 最佳实践

## 最佳实践指南

### 实践 1：实施基于角色的精细访问控制

**说明**: 利用 Amazon Bedrock AgentCore 的策略功能，严格限制 AI 代理对特定 API 或操作的访问权限。通过定义明确的角色边界，确保代理仅拥有完成其特定任务所需的最小权限集，从而防止权限滥用或横向移动。

**实施步骤**:
1. 在 IAM 中为代理定义专属角色，仅授予必要的 Bedrock 和 Lambda 权限。
2. 在 AgentCore 的策略配置中，明确列出允许调用的 API 端点。
3. 使用条件键（如 `aws:PrincipalOrgID`）进一步限制访问来源。

**注意事项**: 避免使用 `*` 通配符授予权限，应遵循“默认拒绝”原则，显式声明允许的行为。

---

### 实践 2：配置敏感数据过滤与脱敏策略

**说明**: 防止 AI 代理在处理提示词或执行工具调用时泄露敏感信息（如 PII、凭证或专有代码）。通过策略层面对输入输出进行实时扫描和拦截，确保数据合规性。

**实施步骤**:
1. 利用 Amazon Bedrock Guardrails 或自定义 Lambda 函数作为策略的执行层。
2. 在策略中定义敏感实体模式（如正则表达式、关键词列表）。
3. 配置代理在检测到敏感数据时的响应行为（如拒绝回答或自动脱敏）。

**注意事项**: 定期更新敏感词库和模式匹配规则，以适应新的数据隐私法规要求。

---

### 实践 3：建立严格的输出边界与格式验证

**说明**: 确保 AI 代理生成的响应内容符合预期的格式和业务逻辑，防止生成恶意代码、非预期指令或越狱内容。策略应验证最终输出的结构化数据（如 JSON/XML）的有效性。

**实施步骤**:
1. 在 AgentCore 中定义输出架构约束。
2. 实施后处理策略，使用 JSON Schema 验证代理返回的每一个参数。
3. 设置针对特定恶意字符串或越狱尝试的静态拦截规则。

**注意事项**: 结合动态验证和静态规则，防止代理因模型幻觉而产生不安全的输出格式。

---

### 实践 4：限制工具调用的频率与资源消耗

**说明**: 为了防止 AI 代理因逻辑循环、恶意诱导或异常错误导致的后端资源耗尽（如 Lambda 调用风暴），必须在策略层面实施严格的速率限制和预算控制。

**实施步骤**:
1. 在代理配置中设置单个会话内的最大工具调用次数。
2. 利用 Amazon Bedrock 的并发限制功能控制总体请求速率。
3. 实施超时策略，强制终止长时间运行的工具调用链。

**注意事项**: 监控代理的调用模式，如果频繁触及上限，需优化代理的推理逻辑或调整限制阈值。

---

### 实践 5：强制执行可观测性与审计日志记录

**说明**: 安全不仅仅是防御，还包括追溯。必须确保所有代理的决策过程、策略应用情况以及工具调用都被完整记录，以便进行安全审计和事后分析。

**实施步骤**:
1. 启用 Amazon CloudWatch Logs 以记录 AgentCore 的策略评估日志。
2. 确保日志中包含请求 ID、用户身份、触发的策略规则以及拦截原因。
3. 将审计日志导出至 Amazon S3 或 SIEM 系统进行长期存储和分析。

**注意事项**: 在记录日志时，务必对日志中的敏感数据进行脱敏处理，防止日志本身成为泄露源。

---

### 实践 6：实施上下文感知的动态策略

**说明**: 安全策略不应是静态的，而应根据用户上下文（如地理位置、登录状态、历史行为）动态调整。AgentCore 应能够根据请求的上下文属性应用不同的安全规则。

**实施步骤**:
1. 在策略中引入上下文变量（如 `user.group`、`time.of.day`）。
2. 配置条件逻辑，例如：对于“外部用户”禁止调用“内部数据删除”工具。
3. 结合 Amazon Cognito 或外部身份提供商传递用户上下文信息。

**注意事项**: 确保上下文数据的传递是经过验证和加密的，防止请求头伪造导致的权限提升。

---

### 实践 7：定期进行对抗性测试与策略演练

**说明**: 随着攻击手段的演进，静态配置可能失效。必须建立定期的红队演练机制，模拟提示词注入和越狱攻击，以验证 AgentCore 策略的有效性。

**实施步骤**:
1. 建立包含已知越狱模式（如 DAN 模式、角色扮演攻击）的测试集。
2. 在预发布环境中自动运行这些测试用例，验证策略拦截率。
3. 根据测试结果反馈，迭代优化 AgentCore 的拒绝策略和提示词模板。

**注意事项**: 测试应在隔离的安全环境中进行，避免测试数据污染生产环境的模型训练或日志。

## 学习要点

- Amazon Bedrock AgentCore 引入了一种基于策略的机制，允许开发者通过定义明确的规则和边界来治理 AI 智能体，从而在不牺牲灵活性的前提下确保行为安全。
- 该框架支持精细化的访问控制，能够根据用户身份、上下文或特定资源动态限制智能体的操作权限，有效防止未经授权的数据访问或敏感操作。
- 通过将安全策略从核心业务逻辑中解耦，开发者可以更专注于应用功能的构建，同时利用策略层集中管理和更新合规要求，显著降低了运维复杂度。
- 系统具备实时监控和执行能力，能够在智能体执行任务期间即时拦截违反策略的指令或请求，确保 AI 行为始终处于预设的安全轨道内。
- 这种基于策略的方法为企业在生产环境中大规模部署 AI 智能体提供了必要的治理框架，有助于在利用自动化提升效率的同时满足严格的监管合规标准。
