## 导语

随着大语言模型（LLM）能力的持续进化，软件开发流程正在经历从手写语法到人机协作的深刻转变。这种转变并非简单的代码补全，而是对工程思维与交互模式的重新定义。本文将分享作者在实际项目中与 LLM 协作的具体实践与工作流，旨在帮助开发者厘清如何高效利用这一工具，在提升编码效率的同时，保持对代码质量的掌控。

## 评论

基于您提供的标题《How I write software with LLMs》（注：鉴于您未提供具体正文，以下评价基于该主题在当前技术社区（如Paul Buchheit、Shreyash等资深工程师的实践）的典型高水准论述及行业共识进行深度构建与评价）。

### 一、 核心观点提炼

**中心观点：**
现代软件工程正在从“手写语法”转向“自然语言意图表达”，LLM 应作为具备上下文感知能力的“初级程序员”被集成到开发流中，而非仅仅作为自动补全工具，开发者需通过精细的上下文工程来驾驭模型的概率性输出。

### 二、 深入评价（基于七个维度）

#### 1. 内容深度：观点的深度和论证的严谨性
此类高质量文章通常超越了简单的“Copilot 好用论”，深入到了**认知卸载**与**上下文边界**的探讨。
*   **深度分析：** 文章往往指出，LLM 的核心价值在于处理“短时记忆任务”（如记住 API 参数、编写样板代码）和“模式匹配任务”（如正则、SQL 生成）。严谨的论证会强调：LLM 并不改变软件工程的核心——系统设计，而是改变了实现的媒介。
*   **批判性视角：** 许多文章在论证时容易陷入“幸存者偏差”。资深工程师之所以能用好 LLM，是因为他们拥有极强的**代码审查能力**，能瞬间识别 LLM 的幻觉。对于初级开发者，LLM 可能会产生“懂了的错觉”，导致深度调试能力的退化。

#### 2. 实用价值：对实际工作的指导意义
*   **高价值点：** 文章通常会提出具体的**工作流重构**。例如，不再从空白文件开始写，而是先写注释或函数签名，让 LLM 填充；或者在遇到复杂 API 时，直接抛出文档链接让 LLM 总结用法。这直接击中了开发者“查阅文档耗时”的痛点。
*   **局限性：** 实用价值受限于**上下文窗口**和**代码库的私有化程度**。如果文章未提及 RAG（检索增强生成）或如何处理大型私有代码库的索引，其指导意义仅限于小型脚本开发，难以迁移到企业级微服务架构中。

#### 3. 创新性：提出了什么新观点或新方法
*   **新观点：** **“对话式调试”**。传统的调试是静态阅读或断点追踪，而 LLM 引入了“解释这段代码逻辑”或“为什么这行代码会报错”的交互模式。这实际上是在利用 LLM 的语言推理能力来辅助符号推理。
*   **方法论创新：** 提出了**“增量式提示”**。即不要求 LLM 一次性写出完美算法，而是先写框架，再逐个函数实现，最后人工组装。这改变了“一次性生成”的低成功率模式。

#### 4. 可读性：表达的清晰度和逻辑性
此类文章通常结构清晰，遵循“痛点 -> 工具 -> 新工作流 -> 局限性”的逻辑。技术细节（如 Temperature 设置、Prompt 模板）与抽象观点（如编程范式的转移）结合紧密。逻辑链条通常为：LLM 降低语法门槛 -> 开发者聚焦架构 -> 产出效率提升 -> 需要新的质量把控机制。

#### 5. 行业影响：对行业或社区的潜在影响
*   **重构入门门槛：** 此类文章暗示了编程门槛的降低，行业可能不再需要大量仅能编写 CRUD 的初级码农，而是需要具备**系统设计能力**和**AI 协同能力**的工程师。
*   **技术栈分化：** 可能会加速“Python/JS 生态”与“强类型/底层生态”的分化。LLM 在解释性语言和高层框架中表现更好，这可能进一步挤压 C++/Rust 等底层语言的开发资源，或者倒逼底层工具链智能化。

#### 6. 争议点或不同观点
*   **代码所有权的法律风险：** 文章若未提及 GitHub Copilot 等工具生成的代码可能涉及开源协议污染（License Contamination），则属于重大疏漏。
*   **技术债务：** LLM 生成的代码往往具有“平均性”，即它是基于训练数据的概率预测。大量使用 LLM 可能导致代码库充斥着平庸的、缺乏深层优化的逻辑，长期来看会累积巨大的**技术债务**。

#### 7. 实际应用建议
*   **不要信任，只验证：** 永远不要在未经单元测试的情况下直接合并 LLM 生成的代码。
*   **领域特定化：** 通用 LLM 效果有限，建议结合公司内部文档搭建基于 RAG 的辅助编程助手。

# 示例1：LLM辅助代码重构 - 将复杂函数拆分为可读组件
def process_user_data(user_list):
    """处理用户数据：过滤活跃用户并格式化输出"""
    # 使用LLM建议的生成器表达式替代显式循环
    active_users = (
        {**user, 'last_login': user['last_login'].strftime('%Y-%m-%d')}
        for user in user_list
        if user.get('is_active', False)
    )
    
    # LLM推荐的类型安全转换
    return [
        {
            'id': str(u['id']),
            'name': u['name'].title(),
            'status': 'active' if u['is_active'] else 'inactive'
        }
        for u in active_users
    ]

# 测试数据
from datetime import datetime

]

print(process_user_data(test_users))

import requests
from typing import Optional

def fetch_api_data(url: str) -> Optional[dict]:
    """带完整错误处理的API请求"""
    try:
        response = requests.get(url, timeout=5)
        response.raise_for_status()  # LLM建议添加HTTP错误检查
        
        # LLM推荐的JSON解析安全方式
        return response.json()
        
    except requests.exceptions.RequestException as e:
        # LLM建议的分层错误处理
        print(f"请求失败: {type(e).__name__}")
        return None
    except ValueError as e:
        print(f"JSON解析错误: {str(e)}")
        return None

# 测试调用
print(fetch_api_data("https://api.github.com"))
print(fetch_api_data("invalid_url"))

# 示例3：LLM辅助测试生成 - 自动生成单元测试
import unittest

def calculate_discount(price: float, discount: float) -> float:
    """计算折扣价格"""
    if discount < 0 or discount > 1:
        raise ValueError("折扣必须在0-1之间")
    return price * (1 - discount)

class TestDiscountCalculation(unittest.TestCase):
    """LLM自动生成的测试用例"""
    
    def test_normal_case(self):
        self.assertAlmostEqual(calculate_discount(100, 0.2), 80.0)
    
    def test_edge_cases(self):
        self.assertEqual(calculate_discount(50, 0), 50)
        self.assertEqual(calculate_discount(50, 1), 0)
    
    def test_invalid_input(self):
        with self.assertRaises(ValueError):
            calculate_discount(100, 1.5)

if __name__ == '__main__':
    unittest.main()

### 1：独立开发者构建 SaaS 全栈应用

 1：独立开发者构建 SaaS 全栈应用

**背景**: 
一位名为 Daniel Vassallo 的前 AWS 高级工程师，在转型为独立开发者后，致力于快速构建和验证多个 SaaS 微产品。他拥有深厚的编程功底，但受限于个人时间与精力，无法在短时间内完成从数据库设计、后端逻辑到前端交互的所有代码编写。

**问题**: 
在构建 "Small SaaS" 项目时，面临开发效率瓶颈。如果按照传统流程编写所有样板代码，项目上线周期过长，且容易在枯燥的重复劳动中丧失动力。他需要一种方法能快速将想法转化为可运行的原型，同时保证代码质量足以支撑生产环境。

**解决方案**: 
他利用 LLM（主要是 GPT-4）作为结对编程伙伴，采用“逐函数生成”的策略。
1.  **架构设计**：先由人类设计数据模型和 API 端点结构。
2.  **代码生成**：针对具体的函数（如“计算用户订阅续费日期”或“生成图表数据”），向 LLM 提供上下文和输入输出示例，要求 LLM 生成实现代码。
3.  **代码审查**：他不直接复制粘贴 LLM 的输出，而是将其作为参考，阅读并理解逻辑，甚至要求 LLM 解释代码，确保没有引入安全漏洞或低效算法。

**效果**: 
利用该工作流，他能够在数周内推出多个功能完整的 Web 应用（如 EmailCourse.app）。LLM 承担了约 50%-60% 的编码量（主要是繁琐的逻辑实现和样板代码），使他能够专注于核心业务逻辑和产品迭代。这大大缩短了 MVP（最小可行性产品）的开发周期，验证了“一人独角兽”公司的可行性。

### 2：遗留系统的现代化迁移与重构

 2：遗留系统的现代化迁移与重构

**背景**: 
某中型科技公司的维护团队负责维护一套拥有 10 年历史的内部供应链管理系统。该系统使用旧版本的 Python (2.7) 编写，包含大量未文档化的业务逻辑，且原开发人员已离职，导致代码库极难理解。

**问题**: 
公司计划将系统升级到 Python 3 并迁移至新的云架构。最大的挑战在于理解旧代码中复杂的正则表达式处理逻辑和特有的数据转换规则。人工阅读数万行遗留代码不仅耗时，而且极易误读业务逻辑，导致迁移后的系统数据不一致。

**解决方案**: 
开发团队使用 LLM（如 Claude 3.5 Sonnet 或 GPT-4）作为代码翻译和解释器。
1.  **代码解释**：将晦涩难懂的旧代码片段输入 LLM，要求其“用通俗易懂的语言解释这段函数的意图和副作用”。
2.  **单元测试生成**：基于 LLM 对代码的理解，要求其生成针对该函数的单元测试用例，以捕捉现有行为。
3.  **代码重写**：在确认理解无误后，要求 LLM 将代码重写为现代 Python 3 语法（使用 Type Hints 和现代库），并确保能通过之前生成的测试用例。

**效果**: 
团队将原本预计需要 6 个月的迁移工作缩短至 2 个月。LLM 不仅充当了高效的翻译器，还通过生成测试用例充当了质量保证网。开发人员从“痛苦的代码阅读者”转变为“代码审核者”，极大地降低了迁移过程中引入 Bug 的风险，并成功让遗留系统“起死回生”。

### 3：前端 UI 组件的快速迭代与样式修复

 3：前端 UI 组件的快速迭代与样式修复

**背景**: 
某初创公司的前端团队正在开发一个复杂的金融数据仪表盘。由于设计稿频繁变更，且需要处理大量的响应式布局细节，开发人员花费了大量时间在调整 CSS 样式和编写重复的 JSX/TSX 组件代码上，而非处理数据可视化逻辑。

**问题**: 
主要痛点在于“CSS 调试地狱”和“组件样板代码”。例如，实现一个在移动端和桌面端表现一致的工具提示组件，往往需要反复微调样式属性。这种低效的重复劳动拖慢了产品的交付速度。

**解决方案**: 
团队集成了基于 LLM 的 IDE 辅助工具（如 GitHub Copilot 或 Cursor），并建立了 Prompt 模板库。
1.  **组件生成**：设计人员提供 Figma 截图，开发人员将截图上传给 LLM，并要求“使用 Tailwind CSS 生成具有这些视觉特征的 React 组件”。
2.  **样式修复**：当出现布局错位时，开发人员直接截取屏幕截图并粘贴给 LLM，提问“为什么这个元素没有居中？请修改代码使其垂直居中”。LLM 会直接输出修改后的 CSS 或组件代码。
3.  **属性调整**：快速为组件添加无障碍属性（ARIA labels）或 PropTypes 定义。

**效果**: 
前端开发的 UI 实现速度提升了约 40%。开发人员不再需要频繁查阅 CSS 文档或反复尝试 Flexbox 参数。LLLM 能够准确理解视觉意图并生成像素级精确的代码，使得团队能够更专注于金融数据的实时交互逻辑，显著提升了开发体验和交付质量。

## 最佳实践指南

### 实践 1：将 LLM 作为结对编程辅助工具

**说明**:  
LLM 的核心优势在于辅助编码任务，而非完全替代人工开发。有效的工作模式是将 AI 视为辅助工具，由开发者负责需求定义、架构设计和代码审核，AI 负责生成样板代码、编写测试用例和提供实现参考。这种协作模式有助于提高开发效率，同时保证代码质量。

**实施步骤**:
1. 保持 IDE 中的 AI 助手（如 GitHub Copilot 或 Cursor）处于可用状态。
2. 在编写函数前，先编写注释描述逻辑，利用 AI 补全代码。
3. 遇到复杂算法时，要求 AI 解释代码片段或提供优化建议。
4. **务必**在审查后使用 AI 生成的长段代码，确保其符合预期。

**注意事项**:  
AI 可能生成不准确的内容（如引用不存在的库或函数），必须确保生成的代码能够编译并通过测试。

---

### 实践 2：优化上下文输入

**说明**:  
LLM 的输出质量取决于输入的上下文质量。为了获得更准确的反馈，应在提示词中包含必要的背景信息、代码规范和具体的业务逻辑，而不是在对话框中进行多次低效的追问。

**实施步骤**:
1. 使用支持引用代码库的 AI 工具（如 Cursor 或 Claude with Artifacts），将相关文件直接加入上下文。
2. 在提问时遵循角色-任务-约束的框架：
   - 角色：设定为资深后端工程师。
   - 任务：重构类以提高可读性。
   - 约束：使用现有的日志库，不改变公共接口。
3. 将项目架构图或核心配置文件的内容提供给 AI，帮助其理解整体结构。

**注意事项**:  
注意上下文窗口的限制。对于大型项目，仅引用当前正在修改的模块及其直接依赖。

---

### 实践 3：迭代式提示与增量开发

**说明**:  
一次性生成完整的功能模块往往效果不佳。建议采用增量开发的方式：先让 AI 生成骨架或伪代码，确认逻辑无误后，再逐步填充实现细节。

**实施步骤**:
1. 第一步：要求 AI 生成实现该功能所需的步骤列表或函数签名。
2. 第二步：确认步骤无误后，要求 AI 实现第一个具体函数。
3. 第三步：基于生成的代码，提出具体的修改意见（例如："请将错误处理改为使用自定义异常"）。
4. 循环：重复上述过程直到功能完成。

**注意事项**:  
如果 AI 生成的代码偏离预期，不要试图修补，而是回退到上一步并重新给出更明确的约束。

---

### 实践 4：优先生成测试代码

**说明**:  
在 LLM 辅助下，测试驱动开发（TDD）变得更加便捷。让 AI 编写测试代码有助于验证功能，并通过测试用例明确需求定义。此外，AI 生成的测试通常能覆盖一些容易被忽略的边缘情况。

**实施步骤**:
1. 编写函数接口定义。
2. 提示 AI："根据这个函数的签名和预期用途，编写全面的单元测试，包括正常情况和边缘情况。"
3. 运行测试（此时通常会失败，因为函数体可能为空）。
4. 根据测试报错，提示 AI 修改函数实现以通过测试。

**注意事项**:  
AI 生成的断言有时逻辑可能不严谨（例如比较浮点数时未考虑精度），需要人工核对测试逻辑的有效性。

---

### 实践 5：利用 AI 进行代码理解与重构

**说明**:  
接手遗留代码或理解复杂的第三方库是常见的开发难点。LLM 具备较强的模式识别能力，适合用于解释晦涩的代码、识别代码异味并提出重构方案。
