## 最佳实践指南

### 实践 1：构建模块化的“工具箱”架构

**说明**:
不要试图让大语言模型（LLM）直接通过生成代码来解决所有复杂的后端操作。最佳实践是预先构建一套经过测试、安全且功能单一的函数或API接口（即“工具”），并将这些工具的描述提供给LLM。LLM仅充当推理引擎，根据用户需求决定调用哪个工具以及传递什么参数，而不是生成执行逻辑本身。

**实施步骤**:
1. 梳理业务场景中可能用到的所有数据操作（如：执行SQL、调用API、读写文件）。
2. 为每种操作编写独立的Python函数，并添加严格的类型提示和错误处理。
3. 使用清晰的JSON Schema或文档描述每个函数的用途、参数和返回值。
4. 将这些函数注册到Agent框架中，供LLM动态调用。

**注意事项**:
确保工具的粒度适中，既要足够原子化以保持简单，又要避免过于琐碎导致LLM调用链过长。

### 实践 2：实施严格的数据访问控制与权限隔离

**说明**:
数据智能体通常需要访问敏感的生产数据库。不能简单地将数据库的管理员权限赋予Agent。最佳实践是实施最小权限原则，为Agent配置专用的服务账号，并严格限制其只能读取必要的表或字段，甚至限制返回的行数，以防止数据泄露或恶意消耗资源。

**实施步骤**:
1. 在数据库中创建专门用于AI Agent访问的只读角色。
2. 限制该角色只能访问特定的Schema或视图，屏蔽敏感字段（如PII个人隐私信息）。
3. 在API层或工具层实施“速率限制”和“超时机制”，防止意外的大规模全表扫描。
4. 记录所有数据访问日志以便审计。

**注意事项**:
永远不要允许通过自然语言直接执行DROP、UPDATE或INSERT等修改数据的操作，除非经过了极其严格的多重确认流程。

### 实践 3：在执行前引入“自我修正”与“验证”循环

**说明**:
LLM生成的SQL查询或API参数在第一次尝试时往往存在错误（如字段名拼写错误、语法错误）。最佳实践是设计一个反馈循环，捕获执行错误并将其返回给LLM，让LLM分析错误原因并自动修正代码，而不是直接向用户报错。

**实施步骤**:
1. 捕获工具执行过程中的异常（如数据库报错、API 404）。
2. 将具体的错误信息构建成自然语言提示，再次发送给LLM。
3. 要求LLM根据错误上下文重新生成修正后的指令。
4. 设置最大重试次数（例如3次），超过次数后转人工处理。

**注意事项**:
在将错误信息返回给LLM时，注意清理敏感的堆栈跟踪信息，仅保留有助于修正错误的上下文。
