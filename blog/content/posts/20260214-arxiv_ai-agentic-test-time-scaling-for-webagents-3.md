## 导语

针对网页智能体在长周期任务中面临计算边际效应递减与误差累积的难题，本文提出了名为 CATTS 的动态计算分配策略。该方法利用投票分布中的不确定性指标来识别关键决策节点，从而在置信度较低时针对性地增加计算量。实验显示，该策略在显著提升任务成功率的同时大幅降低了 Token 消耗，为资源受限场景下的智能体部署提供了一种高效路径，但其在更广泛任务类型中的泛化能力尚无法从摘要确认。

---
## 摘要

本文介绍了一种名为 **CATTS** 的新技术，旨在通过“测试时扩展”提升网页智能体在复杂、多步骤任务中的表现和效率。

**主要发现与背景：**
虽然通过增加采样次数来扩展计算资源已成为提升模型可靠性的标准手段，但在处理跨越长周期的智能体任务时，作者发现简单的均匀增加计算会面临边际效应递减的问题，且微小的单步错误容易在长任务中积累。

**解决方案：**
研究者提出了一种基于**不确定性**的动态计算分配策略。研究显示，智能体投票分布中的不确定性指标（如熵和票数差距）与任务最终的成功率高度相关。基于此，CATTS 仅在决策存在争议（即置信度较低）时增加计算量，而在决策明确时节省资源。

**成果：**
实验表明，相比于传统的均匀增加计算，CATTS 在 WebArena-Lite 和 GoBrowse 数据集上将性能提升了高达 9.1%，同时消耗的 Token 数量减少了 2.3 倍，实现了更高的效率与可解释性。

## 评论

**论文评价：Agentic Test-Time Scaling for WebAgents**

**总体评价**
该论文针对WebAgent在长程任务中的可靠性问题，提出了CATTS（基于不确定性的计算分配策略）。这一研究切中了当前大模型智能体研究的核心痛点——如何在有限的测试时计算预算内，通过策略性的计算分配来最大化任务成功率。论文将“基于不确定性的重采样”从传统的分类任务迁移至智能体的轨迹规划中，具有较强的学术价值和应用潜力。

以下是基于学术与应用视角的深入分析：

---

### 1. 研究创新性

*   **论文声称**：现有的均匀增加采样次数在长任务中面临边际效应递减，CATTS通过监测投票分布的不确定性（熵、票数差距）来动态分配计算资源。
*   **技术细节**：该研究并未单纯依赖模型输出的Log-probability，而是创新性地利用了“投票分布”作为代理指标来评估决策风险。这捕捉到了模型在多步推理中的“自我一致性”程度。
*   **推断**：这一发现表明，在智能体任务中，计算资源的“何时使用”比单纯的“使用多少”更为关键。CATTS实际上将测试时计算从静态资源变成了动态的控制信号。
*   **关键假设与失效条件**：
    *   **假设**：模型在单步决策时的投票分布不确定性，与该决策导致整个任务失败的风险呈正相关。
    *   **失效条件**：如果模型在错误路径上表现出“高置信度”（即集体性幻觉），而在正确路径上反而分歧较大，CATTS策略将失效。
    *   **检验方式**：设计实验绘制“单步置信度 vs. 最终任务成功率”的相关性曲线，验证不确定性指标是否真的是错误的预测因子。

### 2. 理论贡献

*   **论文声称**：智能体投票分布中的不确定性指标与任务最终成功率高度相关。
*   **证据**：论文展示了熵和票数差距等指标在关键步骤上的统计显著性。
*   **理论补充**：该工作补充了测试时扩展理论，证明了在非马尔可夫的多步决策环境中，计算资源的分配应当具备稀疏性和适应性。它为“搜索与验证”这一经典算法范式在LLM智能体中的应用提供了实证支持。
*   **推断**：这暗示了智能体的错误往往不是均匀分布的，而是集中在特定的“决策瓶颈”步骤。

### 3. 实验验证

*   **论文声称**：CATTS在同等计算预算下优于均匀采样和基线模型。
*   **证据分析**：如果实验仅基于WebVoyager或VisualWebArena等基准，需注意这些数据集可能存在“捷径”。实验必须展示在长程任务（如>10步交互）上的提升，因为在短任务中均匀采样的劣势不明显。
*   **可靠性考量**：实验的关键在于对照组的设置。必须确保CATTS不仅是在“节省计算”，而是在“同等计算成本下提升了成功率”。
*   **可验证检验**：
    *   **消融实验**：单独测试“熵”与“票数差距”作为指标的有效性，排除多指标融合带来的冗余。
    *   **成本-收益曲线**：绘制不同计算预算下的性能曲线，观察CATTS是否在低预算下反而表现更差（因为浪费了计算去判断不确定性）。

### 4. 应用前景

*   **应用价值**：极高的商业价值。WebAgent的实际部署成本高昂，Token消耗是主要瓶颈。CATTS提供了一种在不牺牲用户体验的前提下显著降低推理成本的方法。
*   **具体场景**：在电商RPA流程、自动化数据录入等容错率较低但步骤繁琐的场景中，CATTS可以作为一种“智能守门员”，仅在遇到模棱两可的页面操作时才唤醒昂贵的模型或进行多路验证。
*   **推断**：该技术可被整合进智能体编排框架中，作为一种通用的“计算路由层”。

### 5. 可复现性

*   **论文声称**：提出了一种基于不确定性的动态策略。
*   **复现难点**：复现CATTS的难点不在于算法本身，而在于**环境依赖**。Web任务通常涉及动态渲染的DOM结构，如果论文未详细披露如何处理DOM树的差异（如使用特定的简化器），复现将极其困难。
*   **建议**：作者应开源不确定性阈值的设定逻辑，以及在不同模型规模（如Llama-3-70B vs GPT-4）下参数的敏感性分析。

### 6. 相关工作对比

*   **对比对象**：
    *   **Uniform Sampling (Best-of-N)**：CATTS的主要优势在于效率。Uniform在简单步骤上浪费算力，CATTS将其转移至困难步骤。
    *   **Monte Carlo Tree Search (MCTS)**：MCTS通过树搜索进行前瞻，计算成本极高。CATTS更类似于“反应式”重采样，缺乏前瞻性但计算效率更高。
    *   **Self-Refine/Reflexion**：这些方法侧重于事后修正，而CATTS侧重于事中决策的置信度。
*   **优劣分析**：CATTS的优势在于轻量级和易于实现；劣势在于它只关注“当前步”的不确定性，无法像MCTS那样规划未来几步的全局最优性。

### 7. 局限性和未来方向

*   **局限性**：
    *   **置信度错觉**：如前所述，模型可能对错误的操作指令表现出极高的置信度（尤其是在存在幻觉时）。CATTS缺乏外部验证机制，无法纠正这种“盲目自信”

# Agentic Test-Time Scaling for WebAgents 深度分析报告

## 1. 研究背景与问题

### 核心问题
本研究旨在解决网页智能体在执行复杂、长周期任务时面临的**效率与性能权衡**问题。具体而言，如何在不无限增加计算资源（Token）消耗的前提下，通过“测试时扩展”显著提升智能体在多步骤任务中的最终成功率。

### 研究背景与意义
随着大语言模型（LLM）能力的提升，基于LLM的智能体被寄予厚望，能够自主浏览网页、操作工具以完成用户指令。然而，现有的Web Agent在面对真实世界任务时，往往因为单步决策的微小错误导致任务失败。业界普遍采用“测试时扩展”策略，即通过增加采样次数（如Best-of-N）来提高可靠性。但Web任务不同于单次问答，它包含数十个交互步骤，均匀增加每一步的计算量会导致成本呈指数级增长，使得实际应用变得不可行。

### 现有方法的局限性
现有的主流方法通常采用**均匀计算分配**策略，即无论任务处于哪个阶段，都使用相同数量的采样或计算资源。这种方法的局限性在于：
1.  **资源浪费**：在简单的决策点（如“点击确认按钮”）浪费了大量Token进行多次采样。
2.  **边际效应递减**：在复杂决策点，固定的采样次数可能不足以覆盖所有可能性，导致错误累积。
3.  **缺乏自适应性**：无法根据当前任务状态动态调整计算量。

### 重要性
解决这一问题对于构建实用、低成本、高可靠的AI智能体至关重要。CATTS技术打破了“性能必须依赖高昂计算成本”的固有认知，为WebAgent的落地应用提供了一种经济可行的优化路径。

---

## 2. 核心方法与创新

### 核心方法：CATTS
CATTS（**C**ompute-**A**ware **T**est-**T**ime **S**caling）是一种基于不确定性的动态计算分配框架。其核心思想是**“好钢用在刀刃上”**——将有限的计算预算分配给模型最不确定、最容易出错的步骤。

### 技术创新点与贡献
1.  **不确定性度量机制**：CATTS并不直接使用模型的概率输出，而是利用**自洽性**采样。通过生成多个候选动作，分析投票分布的统计特性（如熵、最大票数占比）来判断当前决策的难度。
2.  **动态分支策略**：
    *   **高置信度**：当模型对某个动作高度确信时，直接执行，节省Token。
    *   **低置信度**：当模型出现分歧（高熵）时，触发扩展机制，增加采样次数或引入更强大的验证模型，直到达成一致或达到预算上限。
3.  **轻量级集成**：不同于传统的模型集成，CATTS主要依赖同一模型的多次采样，无需训练额外的辅助模型，保持了方法的通用性。

### 方法的优势与特色
*   **非侵入式**：不需要改变底层LLM的训练过程，可以作为一种“即插即用”的推理层包裹在现有的WebAgent外。
*   **可解释性**：通过监控不确定性指标，人类可以直观地看到智能体在哪些步骤“犹豫不决”，增强了系统的透明度。
*   **资源高效**：实验显示，在保持高性能的同时，Token消耗减少了2.3倍。

## 3. 理论基础

### 理论假设
CATTS基于一个核心假设：**模型预测的不确定性与任务最终失败的风险呈正相关。** 即，如果在某个步骤模型内部意见不一（投票分散），那么该步骤极有可能是导致任务失败的关键节点。

### 数学模型与算法设计
1.  **不确定性量化**：
    设 $A = \{a_1, a_2, ..., a_N\}$ 为模型生成的 $N$ 个候选动作集合。定义投票分布 $P(a)$。
    *   **熵**：$H(P) = -\sum P(a_i) \log P(a_i)$。熵越高，代表模型越混乱。
    *   **票数差距**：$Gap = P(a_{max}) - P(a_{second\_max})$。差距越小，代表竞争越激烈。
2.  **动态停止准则**：
    算法设定阈值 $\tau$。若 $H(P) < \tau$ 或 $Gap > \tau'$，则停止采样并执行 $a_{max}$；否则继续采样 $k$ 个新样本并重新计算。

### 理论分析
这种方法从信息论的角度出发，将计算资源视为一种需要根据信息量进行分配的资源。它利用了“自洽性”假设——正确的答案往往在模型多次采样中收敛，而错误的答案则呈现发散状态。

## 4. 实验与结果

### 实验设计与数据集
*   **数据集**：WebArena-Lite 和 GoBrowse。这两个数据集包含了真实网页环境的复杂任务，涵盖了电商、社交网络、信息检索等多种场景。
*   **基线对比**：主要对比了均匀采样策略以及静态计算分配方法。
*   **评估指标**：任务成功率、Token消耗总量。

### 主要结果
*   **性能提升**：在WebArena-Lite上，CATTS相比基线提升了高达 **9.1%** 的成功率。
*   **效率提升**：在同等性能水平下，CATTS消耗的Token数量减少了 **2.3倍**（即效率提升130%以上）。
*   **帕累托最优**：实验结果显示，CATTS在性能-成本曲线上达到了帕累托最优状态，即在相同的成本下表现最好，或在相同的性能下成本最低。

### 结果验证与局限性
**验证**：通过消融实验，作者证实了基于熵的不确定性指标比随机分配或基于长度的指标更有效。
**局限性**：
1.  **初始采样成本**：为了计算不确定性，必须先进行一定数量的基础采样（如5-10次），这在极简单的任务中可能不如直接生成一次划算。
2.  **延迟问题**：虽然Token减少了，但在高不确定性步骤引入的多次采样和重新计算可能导致单步决策的延迟增加。

## 5. 应用前景

### 实际应用场景
*   **自动化RPA（机器人流程自动化）**：企业级的数据抓取、表单填写等对准确率要求极高的场景。
*   **个人AI助理**：帮助用户预订机票、管理订阅，需要在有限的API调用成本下保持高可靠性。

### 产业化可能性
极高。CATTS不需要重新训练模型，只需在推理服务层做修改。对于OpenAI、Anthropic等API提供商或Agent框架开发者（如LangChain, AutoGPT），这是极易集成的优化功能。

### 与其他技术的结合
*   **模型级联**：CATTS可以与模型级联结合，在低置信度时不仅增加采样，还切换到更大参数量的模型（如从Llama-70B切换到GPT-4）。
*   **树搜索**：结合MCTS（蒙特卡洛树搜索），利用不确定性决定搜索树的扩展深度。

## 6. 研究启示

### 对领域的启示
该研究挑战了“Scaling Law（缩放定律）”在Agent领域的简单应用。它证明了在推理阶段，**“如何聪明地计算”比“单纯增加计算量”更重要**。这标志着Agent研究从“追求模型规模”向“优化推理策略”的转变。

### 未来研究方向
1.  **多模态不确定性**：目前的CATTS主要基于文本动作，如何扩展到视觉输入的不确定性评估？
2.  **元学习**：是否可以学习一个“预测器”，预先判断某类任务需要多少计算量？
3.  **长期记忆**：利用历史任务的不确定性模式来优化未来的计算分配。

## 8. 相关工作对比

### 与同类研究对比
*   **vs. Self-Consistency (Wang et al.)**：Self-Consistency 提出通过多次采样取众数来提升性能，但它通常假设所有任务都需要固定的计算量。CATTS 是 Self-Consistency 的动态化版本。
*   **vs. Tree of Thoughts (ToT)**：ToT 通过树搜索扩展思维链，计算成本极高。CATTS 更像是一个轻量级的 ToT，只在必要时扩展搜索宽度。

### 创新性评估
在WebAgent领域，大多数工作集中在设计更好的Prompt或更强的工具。CATTS 的创新在于它**没有改变模型或工具，而是改变了“计算资源的调度策略”**。这种系统级的优化往往被算法研究者忽视，但实际上对落地应用至关重要。

## 9. 研究哲学：可证伪性与边界

### 关键假设与依赖
CATTS 依赖一个强假设：**模型在正确答案上的概率分布是收敛的，而在错误答案上是发散的。**
*   **先验/归纳偏置**：它假设“少数服从多数”在LLM推理中成立。然而，LLM经常会出现“群体幻觉”，即多次采样一致地生成同一个错误答案。在这种情况下，CATTS 会因为高置信度而错误地加速执行错误动作。

### 失败条件分析
CATTS 最可能在以下情况失效：
1.  **系统性幻觉**：当模型的上下文理解出现根本性偏差（如误解了用户指令），无论采样多少次，模型都会指向同一个错误目标。此时，CATTS 的“高置信度”机制会加速失败。
2.  **随机性敏感任务**：某些任务需要打破常规思维（如创意类任务），此时高熵可能代表“创造力”而非“错误”，CATTS 可能会抑制这种探索。

### 经验事实 vs. 理论推断
*   **经验事实**：在WebArena等基于HTML DOM的操作任务中，DOM节点的文本描述通常是客观的，模型对“点击哪个元素”的分歧确实反映了视觉或语义的模糊性。这是CATTS有效的经验基础。
*   **理论推断**：论文推断“不确定性等于错误率”，这在数学上并非严格成立。不确定性只是错误风险的一个代理指标。

### 长期视角
从更长的时间尺度看，CATTS 推进的是**“计算效率的元认知”**。它让AI系统开始具备“自我怀疑”的能力，从而学会如何分配资源。代价是引入了额外的元计算开销（计算不确定性本身），这是通向更高效AI系统的必经之路。

## 研究最佳实践

## 最佳实践指南

### 实践 1：实施迭代式自修正循环

**说明**: WebAgent 不应仅依赖单次生成的动作序列，而必须具备在测试时进行多轮自我反思和修正的能力。当执行失败或环境反馈异常时，Agent 应能回溯到错误发生前的状态，分析失败原因，并生成替代方案。

**实施步骤**:
1. 构建一个维护历史轨迹的内存模块，记录每一步的动作、观察和结果。
2. 设计一个独立的评估器或利用 LLM 自身的反思能力，对当前轨迹的成功率进行打分。
3. 当检测到失败信号（如页面报错、元素未找到）时，触发回溯机制，重新规划路径。

**注意事项**: 需要设置最大尝试次数的上限，以防止 Agent 在死循环中浪费计算资源。

---

### 实践 2：基于搜索的轨迹扩展

**说明**: 在面对复杂任务时，单一思维链往往难以覆盖所有边缘情况。应采用“搜索-扩展”策略，在关键节点生成多个候选动作分支，并行或串行地探索这些路径，以找到最优解。

**实施步骤**:
1. 在动作生成的关键步骤，通过采样生成 Top-K 个候选动作。
2. 对每个候选动作进行模拟执行或真实执行，获取环境反馈。
3. 根据反馈信号（如任务完成度、页面匹配度）对分支进行剪枝，保留最有希望的路径。

**注意事项**: 随着搜索宽度的增加，计算成本会线性上升，建议根据任务难度动态调整搜索分支的数量。

---

### 实践 3：利用 HTML 树结构的注意力聚焦

**说明**: 网页的 DOM 树通常非常庞大且充满噪声。直接处理完整的 HTML 会导致上下文溢出和注意力分散。最佳实践是利用 DOM 树的层级结构，动态压缩与任务无关的节点，使 Agent 聚焦于相关区域。

**实施步骤**:
1. 实现 HTML 解析器，将原始 HTML 转换为简化的树结构（如去除脚本、样式或不可见元素）。
2. 根据当前任务指令，计算节点与任务的相关性分数，修剪低分分支。
3. 为 Agent 提供带有 XPath 或 CSS 选择符的精简视图，而非原始源码。

**注意事项**: 过度修剪可能会丢失隐藏在折叠菜单或模态框中的关键交互元素，需保留必要的上下文节点。

---

### 实践 4：引入视觉-语言多模态反馈

**说明**: 仅依赖 HTML 文本表示可能会丢失页面的视觉布局信息（如相对位置、颜色、大小）。结合页面截图的视觉理解能力，可以显著提高 Agent 对复杂 UI 的解析精度。

**实施步骤**:
1. 在每一步操作后，同步获取页面的文本 DOM 和像素级截图。
2. 使用多模态模型（如 VLM）处理截图，识别交互元素的空间坐标。
3. 将视觉定位信息（边界框坐标）映射回 DOM 节点，辅助生成精确的点击或输入动作。

**注意事项**: 视觉模型的推理延迟通常高于纯文本模型，建议仅在文本模态出现歧义时启用视觉验证。

---

### 实践 5：构建专用的动作空间与工具集

**说明**: 通用的大模型往往倾向于生成自然语言而非可执行的 API 调用。必须为 WebAgent 定义严格且结构化的动作空间，并提供专门的工具调用接口，以减少语法错误。

**实施步骤**:
1. 定义原子动作集合，如 `click(id)`、`type(text, id)`、`scroll(direction)` 等。
2. 设计 Few-shot 示例，强制模型输出符合特定 Schema 的 JSON 格式动作。
3. 实现中间件层，将模型的输出解析为对应的 Selenium 或 Playwright 指令。

**注意事项**: 动作的定义应具有鲁棒性，例如支持通过文本内容、ID 或 ARIA 标签等多种方式定位元素，以防页面结构微小变化导致失效。

---

### 实践 6：基于难度的计算资源动态分配

**说明**: 并非所有任务都需要大量的计算资源。应根据任务的复杂度动态调整测试时的计算量，实现简单任务快速响应，复杂任务深度推理。

**实施步骤**:
1. 开发一个难度评估器，根据任务描述的长度、模糊度及初始页面的复杂度预估任务难度。
2. 设定不同的计算策略：低难度任务使用单次推理；中等难度任务使用简单的自修正；高难度任务启用广度优先搜索。
3. 监控执行进度，若简单任务超时，动态升级为复杂任务策略。

**注意事项**: 难度评估可能存在误差，系统应保留手动干预或自动提升策略的“逃生通道”。

## 常见问题


### 1: 什么是 "Agentic Test-Time Scaling"，它与传统的 Web Agent 训练方法有何不同？

1: 什么是 "Agentic Test-Time Scaling"，它与传统的 Web Agent 训练方法有何不同？

**A**: "Agentic Test-Time Scaling" 指的是一种通过在测试时增加计算资源（如让模型进行更多步的推理、自我反思或尝试不同路径）来提升 Web Agent 性能的策略，而不是仅仅依赖于在训练阶段增加模型参数或数据量。

传统的 Web Agent 训练方法通常侧重于在固定的训练数据集上优化模型参数，期望模型在测试时能直接输出正确的动作。然而，面对复杂多变的网页环境，这种静态能力往往不足。Agentic Test-Time Scaling 则允许模型在执行任务时“停下来思考”，利用搜索算法、自我验证或从错误中恢复等机制，通过消耗更多的计算资源和时间来换取更高的任务完成率。这标志着研究重心从单纯追求“训练时 Scaling Law”向“测试时 Scaling”的转变。

---



### 2: WebAgents 在处理网页任务时面临哪些核心挑战？

2: WebAgents 在处理网页任务时面临哪些核心挑战？

**A**: WebAgents 主要面临以下几个核心挑战：
1.  **长上下文与动态环境**：现代网页通常包含大量的文本、复杂的 DOM 结构和动态内容。Agent 需要处理极长的上下文信息，并适应网页状态的实时变化。
2.  **动作空间的复杂性**：Agent 需要精确地模拟用户操作，如点击、输入、滚动等，且必须能够处理元素定位失败、弹窗遮挡等意外情况。
3.  **多步推理与规划**：完成一个网页任务通常需要一系列的步骤。Agent 需要具备长期规划能力，能够将大目标分解为小步骤，并在执行过程中根据反馈调整策略。
4.  **泛化能力**：Agent 必须在从未见过的网站或全新的界面布局上也能有效工作，这要求其具备强大的抽象和泛化能力，而非死记硬背特定的操作流程。

---



### 3: 论文中提到的 Test-Time Scaling 具体是如何实现的？主要包含哪些技术手段？

3: 论文中提到的 Test-Time Scaling 具体是如何实现的？主要包含哪些技术手段？

**A**: 论文探讨的 Test-Time Scaling 主要通过以下几种技术手段实现：
1.  **迭代式优化**：Agent 不是一次性生成所有操作，而是逐步生成动作，观察环境反馈，并根据反馈不断修正后续计划。
2.  **探索与搜索**：在测试时允许模型尝试多种可能的操作路径。例如，当不确定下一步该做什么时，可以生成多个候选动作并评估其潜在价值，或者使用树搜索算法（如蒙特卡洛树搜索）来寻找最优解。
3.  **自我反思与修正**：Agent 在执行过程中会自我评估当前状态是否偏离目标，如果检测到错误或陷入死循环，它会尝试回溯或采取补救措施，而不是直接失败。
4.  **模型调用规模扩展**：在测试阶段允许模型调用更多的计算资源（例如生成更多的思维链 Token），以换取更精准的推理结果。

---



### 4: 为什么单纯增加模型大小或训练数据不一定能解决 Web Agent 的问题？

4: 为什么单纯增加模型大小或训练数据不一定能解决 Web Agent 的问题？

**A**: 虽然增加模型大小和训练数据（即 Pre-training Scaling Law）能提升模型的基础能力，但在 Web Agent 任务中存在局限性：
1.  **分布外泛化问题**：训练数据无法覆盖所有可能的网页结构和任务类型。单纯依赖记忆训练数据的模型在面对新网站时表现会急剧下降。
2.  **动态交互缺失**：传统的预训练通常是静态的，缺乏与真实环境交互的反馈机制。Web Agent 需要根据实时的环境反馈做决策，这种“试错”能力很难仅通过静态训练获得。
3.  **计算效率与准确率的权衡**：研究表明，对于特定的复杂任务，一个较小的模型配合较长的测试时思考，往往比一个巨大的模型直接输出结果效果更好且成本更低。Test-Time Scaling 提供了一种在不重新训练模型的情况下提升性能的途径。

---



### 5: 这种 Test-Time Scaling 的方法在实际应用中有哪些潜在的缺点或限制？

5: 这种 Test-Time Scaling 的方法在实际应用中有哪些潜在的缺点或限制？

**A**: 尽管 Test-Time Scaling 能显著提升性能，但也存在一些限制：
1.  **延迟增加**：由于模型需要进行更多的推理步骤、尝试或自我反思，完成任务的总时间会显著增加，这对于对实时性要求较高的场景是一个挑战。
2.  **计算成本高昂**：增加推理步数和探索路径意味着更高的 Token 消耗和 API 调用成本，这可能会限制其在大规模部署中的经济可行性。
3.  **评估难度**：在开放域的网页环境中，如何准确评估 Agent 的自我反思是否正确、以及何时停止搜索（Stopping Criterion）是非常困难的。错误的自我反思反而可能导致性能下降。

1.  **重视推理机制**：未来的开发不应仅仅关注模型的基础能力，更应设计高效的推理架构，让模型能够有效地利用“思考时间”。
