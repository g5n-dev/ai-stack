## 摘要

这篇文章主要讲述了 OpenAI 如何构建一套实时访问控制系统，以应对 Sora 和 Codex 等高需求产品的扩容挑战。该系统通过结合速率限制、使用量跟踪和信用额度三大机制，解决了传统仅靠“速率限制”无法解决的资源分配与用户体验平衡问题。

以下是核心内容总结：

**1. 挑战背景**
随着 Sora（视频生成）和 Codex（代码生成）等计算密集型模型的应用普及，单纯限制每秒请求数（RPS）的传统速率限制已不足以管理后台负载。OpenAI 需要一种既能防止系统过载，又能确保用户获得无缝、持续访问体验的新方案。

**2. 核心解决方案：三大机制结合**
OpenAI 设计了一个基于“信用”和“实时跟踪”的访问层，主要由以下部分组成：

*   **灵活的访问控制：**
    系统不再仅仅拦截请求，而是根据用户的信用额度和历史使用情况，动态决定是允许、排队还是拒绝请求。这使得 OpenAI 能够精细地控制谁能在何时使用模型，从而优化资源分配。
*   **使用量跟踪：**
    为了准确计费和配额管理，系统必须实时追踪 Token（词元）消耗或视频生成时长等指标。这要求在极低的延迟下完成计量，确保在高并发场景下数据的准确性和一致性。
*   **信用额度系统：**
    这是扩容的关键。通过引入预付费信用或试用点数，系统可以“削峰填谷”。用户消耗信用来换取计算资源，这既保证了用户体验（在额度内无需频繁重试），也防止了滥用，让 OpenAI 能根据库存情况平滑地发放访问权限。

**3. 技术架构与实现**
*   **实时性：** 该系统被设计为请求路径上的关键组件，要求在毫秒级内完成鉴权和计量，以免增加模型生成的端到端延迟。
*   **数据一致性：** 在分布式环境中，确保使用量扣减和余额更新的准确性至关重要，系统采用了严谨的数据存储策略来避免超卖或计费错误。

**4. 成果**
通过这套结合了**速率限制（硬性防线）**、**使用量跟踪（精准计量）**和**信用额度（柔性资源管理）**的系统，OpenAI 成功实现了对 Sora 和 Codex 的规模化访问控制

## 评论

**文章中心观点**
OpenAI 通过构建一个融合了实时速率限制、动态配额追踪与预付信用体系的精密准入控制系统，成功解决了高算力模型（如 Codex 和 Sora）在商业化初期供需极度不平衡与资源抢占难题，实现了从“排队等待”到“持续可用”的范式转变。

**支撑理由与评价**

**1. 从“静态防御”转向“动态调度”的资源治理逻辑**
*   **事实陈述**：文章详细描述了 OpenAI 如何摒弃传统 API 简单的“每分钟请求数（RPM）”限制，转而采用基于 Token 吞吐量和 GPU 占用时的综合计量系统。
*   **你的推断**：这标志着 AI 基础设施运营的成熟。Codex（代码生成）和 Sora（视频生成）属于典型的“重算力、长延迟”任务。传统的 RPM 限制无法防止用户提交一个耗尽 GPU 数小时的超大任务。OpenAI 实际上是将云原生领域的“资源配额”与“负载均衡”技术下沉到了应用层，通过实时监控后台 GPU 队列长度，动态调整用户的准入阈值。
*   **实用价值**：对于正在构建 GenAI 应用的开发者，这意味着单纯的接口限流已失效。必须建立基于“算力成本”的内部计费模型，而非基于“调用次数”。

**2. “信用体系”作为需求侧的削峰填谷机制**
*   **事实陈述**：文章引入了“Credits（信用点数）”的概念，用户需要消耗信用来换取模型推理时间。
*   **作者观点**：这不仅是商业变现手段，更是一种技术缓冲层。通过引入有偿或基于贡献的信用机制，天然过滤了低价值的滥用请求，并在物理资源受限时利用经济杠杆抑制瞬时洪峰。
*   **创新性**：将免费试用层与付费层通过统一的“信用管道”进行管理，使得系统可以在不中断服务的情况下平滑迁移用户，避免了“免费墙”带来的体验断层。

**3. 实时反馈回路的用户体验设计**
*   **事实陈述**：系统强调向用户实时展示其资源使用状态和剩余配额。
*   **你的推断**：在生成式 AI 中，用户等待焦虑远高于传统软件。OpenAI 的这套系统通过透明化资源状态，将“系统错误”转化为“资源暂缺”，降低了用户对报错的挫败感，提升了系统的可预测性。

**反例与边界条件**
*   **边界条件 1（冷启动问题）**：这种高度依赖信用和配额的系统，对于新用户或无法立即证明商业价值的研究者存在极高的门槛。如果信用获取机制过于僵化，可能会扼杀创新性的边缘用例。
*   **边界条件 2（系统复杂度代价）**：维护一个实时、全局分布式的配额追踪系统本身具有极高的工程复杂度。一旦该计费/限流系统出现故障，将导致整个模型服务不可用，这引入了新的单点故障风险。

**争议点与不同观点**
*   **人为稀缺性 vs. 物理限制**：业界有观点认为，OpenAI 早期的严格限流（特别是针对 Sora）部分是营销策略，旨在制造“人为稀缺”以维持品牌溢价，而不仅仅是物理 GPU 不够用。文章试图从纯技术角度解释，但难以完全剥离商业动机。
*   **开源 vs. 闭墙**：这种复杂的准入控制是闭源 SaaS 模式的护城河。对于开源模型社区（如 Stable Diffusion），其策略是“让用户自己跑”，不存在中心化的限流难题。这引发了关于 AI 民主化与中心化管控路径的长期争论。

**可验证的检查方式**
1.  **API 延迟与配额耗尽的相关性实验**：监控在高并发请求下，API 返回 `429 (Too Many Requests)` 的具体时间戳与错误信息文案。如果错误信息包含具体的“重置时间”或“建议购买配额”的链接，即可验证其将限流作为转化漏斗的推断。
2.  **Token 吞吐量波动率观察**：在非高峰时段与高峰时段，使用相同 Prompt 测试 Sora 或 Codex，观察其生成的实际速度（Token/s）。如果高峰期速度显著下降而非直接拒绝，说明系统采用了“排队降级”而非“熔断拒绝”的策略。
3.  **信用消耗逻辑分析**：分析不同复杂度任务（如 10秒视频 vs 60秒视频）的信用消耗比。如果消耗比是非线性的（例如长视频边际成本更低），则可证实系统利用定价机制在引导用户行为。

**实际应用建议**
对于技术团队而言，不要试图从零构建类似的系统。建议：
1.  **采用分层限流**：在 API 网关层实现基于 RPM 的基础防护，在应用层实现基于“算力积分”的业务逻辑防护。
2.  **异步化处理**：对于 Sora 类耗时任务，必须采用异步队列模式，不要在 HTTP 连接中保持等待，否则会击穿负载均衡器。
3.  **成本可视化**：在产品前端直接展示“本次生成消耗的估算电费/算力成本”，能有效降低用户的滥用率。

# Beyond rate limits: scaling access to Codex and Sora 深度分析报告

## 1. 核心观点深度解读

### 主要观点
文章的核心观点在于：**传统的单一维度速率限制已无法满足现代生成式AI（如Codex和Sora）的高并发与高算力消耗需求，必须转向一种多维度的、基于经济模型的实时访问控制系统。**

### 核心思想
作者传达的核心思想是**“资源货币化与动态配额”**。OpenAI不仅仅是在做技术上的流量控制，而是在构建一个微观经济系统。在这个系统中，用户的访问权限不再仅仅是“每分钟多少次请求”，而是结合了“使用量追踪”和“积分/信用”的综合体。这意味着访问控制从单纯的防御性措施（防止系统崩溃）转变为一种资源分配机制（确保公平性和可持续性）。

### 创新性与深度
该观点的创新性在于打破了技术限制与商业逻辑的界限。传统的API限流通常是静态的（如固定的时间窗口），而OpenAI提出的系统是**实时且状态化**的。深度在于它承认了生成式AI的特殊性：**请求的异质性极大**。生成一段简单的代码与生成一部1分钟的高清视频（Sora），其算力成本相差几个数量级，单纯限制“请求数”已失效，必须限制“计算量”或“成本”。

### 重要性
这个观点至关重要，因为它是AI模型从实验室走向大规模商业应用的基石。如果没有这种精细化的访问控制，面对Sora这种极度消耗资源的模型，平台要么被少数用户耗尽资源导致服务中断，要么因为运营成本过高而无法维持。这是实现AI民主化与商业可持续性的关键工程。

## 2. 关键技术要点

### 涉及的关键技术或概念
1.  **动态速率限制**：超越固定令牌桶算法，基于实时系统负载和用户等级动态调整阈值。
2.  **使用量计量**：针对不同模型（Codex按Token，Sora按GPU时长/分辨率）建立统一的计量单位。
3.  **积分/信用系统**：一种预付费或配额机制，用于在技术限制之外增加经济限制层。
4.  **实时访问控制引擎**：能够在毫秒级时间内决策是否允许请求通过的中间件。

### 技术原理和实现方式
*   **多级漏桶与令牌桶结合**：系统可能维护两个主要桶。一个是“频率桶”（防止突发流量冲击数据库），一个是“配额桶”（防止长期资源耗尽）。
*   **原子计数器**：为了支持高并发，使用Redis等内存数据库配合Lua脚本进行原子性的扣费操作。每次请求不仅要检查`requests_per_minute`，还要检查`credits_balance`。
*   **异步解耦**：对于Sora这类生成任务，访问控制可能是两阶段的：提交任务时扣除“预留额度”，任务完成时扣除“实际额度”并退还差额。

### 技术难点和解决方案
*   **难点：计量的滞后性**。Sora生成视频可能需要几分钟，如何在生成前判断用户是否有足够额度？
    *   **解决方案**：采用“预估扣费”机制。系统根据历史数据预估成本，先冻结积分，任务结束后多退少补。
*   **难点：全局公平性**。如何防止“大户”挤占所有资源？
    *   **解决方案**：引入“突发预留”机制。即使在用户额度充足时，也保留一部分系统容量给低频用户或新用户，确保系统多样性。

### 技术创新点
最显著的创新在于**将“配额”作为一等公民接入API网关**。传统的限流是网络层的，而OpenAI的系统是应用层与业务层的深度结合。它允许系统在过载时，不是直接返回429 Too Many Requests，而是根据用户优先级和剩余积分进行智能排队或降级服务。

## 3. 实际应用价值

### 对实际工作的指导意义
对于架构师和后端工程师而言，这篇文章揭示了**资源受限型系统的设计范式**。在设计SaaS平台时，不能仅考虑技术QPS，必须将业务逻辑（如用户套餐、资源成本）融入到基础设施层的流量控制中。

### 应用场景
1.  **AI推理平台**：任何提供LLM或图像生成服务的平台。
2.  **云渲染农场**：类似于Sora的视频渲染服务。
3.  **API经济平台**：需要精细计量API调用成本（如按数据量、算力而非次数计费）的B2B服务。
4.  **企业级内部共享服务**：在大公司内部，不同部门共享昂贵的GPU集群，需要一套类似的系统来分配资源。

### 需要注意的问题
*   **用户体验摩擦**：过于复杂的限流和计费会让用户困惑。需要将技术细节转化为清晰的UI提示（如“您还剩5分钟生成时长”）。
*   **数据一致性**：在高并发下，确保积分扣除的准确性是极大的挑战，必须处理好分布式事务。

### 实施建议
不要试图从头构建所有组件。利用现有的API网关（如Kong, APISIX）配合Redis进行速率限制，同时通过自定义插件引入“积分校验”逻辑。对于长时间运行的任务，务必采用异步状态机模式来管理生命周期。

## 4. 行业影响分析

### 对行业的启示
OpenAI的实践表明，**AI Infra（基础设施）正在从单纯的“技术栈”向“运营栈”演进**。未来的AI公司不仅要有强大的模型训练能力，更要有强大的资源调度和计费工程能力。

### 可能带来的变革
这将推动**“算力即服务”的标准化**。类似于云计算从买服务器到按秒计费的变革，AI服务将普遍采用按Token、按步数或按生成质量的精细化计费模式。

### 发展趋势
*   **分层访问控制**：根据用户付费等级提供不同的模型版本（如Sora有480p和1080p版本，对应不同的限流策略）。
*   **市场化的资源调度**：当算力紧缺时，允许用户通过加价来获取优先处理权，类似AWS的Spot Instance。

## 5. 延伸思考

### 拓展方向
*   **动态定价**：如果系统能根据实时负载调整价格（Uber的溢价模式），是否也能应用于AI API？
*   **联邦学习下的访问控制**：在数据隐私保护的前提下，如何在不暴露原始数据的情况下计量用户对模型的贡献并给予访问额度？

### 需进一步研究的问题
如何设计一个既能防止滥用，又能鼓励探索性使用的限流算法？例如，对于开发者测试API，是否应该给予“无限但低速”的访问，而不是“高速但有限”的访问？

## 6. 实践建议

### 如何应用到自己的项目
1.  **审计现有API**：检查你的API网关是否只做了简单的QPS限制。
2.  **引入成本概念**：为每个API端点定义一个“成本分数”（CPU、内存、IO的加权值）。
3.  **构建配额中心**：建立一个独立的微服务，专门负责用户配额的查询、预扣和结算。

### 行动建议
*   **第一步**：在Redis中实现一个简单的`user_quota`计数器，并在中间件中校验。
*   **第二步**：对于耗时任务，实现`pending_charges`（待定费用）机制。
*   **补充知识**：深入学习Redis Lua脚本（保证原子性）和分布式锁。

### 注意事项
避免“硬编码”限流规则。规则应当是可配置的，以便在系统负载过高时，运维人员可以通过动态调整配置来限流，而不需要重新部署代码。

## 7. 案例分析

### 成功案例分析：OpenAI ChatGPT Plus
ChatGPT Plus在高峰期限制GPT-4的使用（每3小时40条），但GPT-3.5不限。这正是**分级访问控制**的体现。通过牺牲部分GPT-4的体验来保证系统的整体稳定性，同时通过Plus订阅（Credits）来筛选用户。

### 失败案例反思：早期Midjourney
Midjourney在早期爆发阶段曾因缺乏有效的速率限制，导致免费用户大量占用GPU资源，付费会员反而无法生成图片。这直接导致了他们取消了免费试用，转向纯付费/邀请制，这证明了单纯的“好人式”限流（如每用户限制）在资源极度稀缺时是无效的，必须引入“信用/付费”门槛。

### 经验教训总结
**限流不仅是技术问题，更是产品问题。** 必须将限流策略显性化地展示给用户，让他们明白为什么被限制（如“您的算力豆已用完”），而不是给一个冷冰冰的500错误。

### 实践 1：实施自适应批处理策略

**说明**: 
Codex 和 Sora 等 AI 模型在处理请求时，往往受限于最大并发请求数（RPM/TPM），而非单纯的 Token 处理能力。通过将多个独立的用户请求聚合成一个批次进行处理，可以显著减少建立连接和握手带来的网络开销，并提高单次调用的数据吞吐量。自适应意味着根据当前的负载情况动态调整批次的大小。

**实施步骤**:
1. 在应用层构建一个中间缓冲队列，用于暂存进入的 API 请求。
2. 设定时间窗口（例如 100ms）或数量阈值（例如 50 个请求）作为触发批处理的条件。
3. 编写聚合逻辑，将多个 Prompt 合并为结构化输入（如 JSON Array），利用模型的多轮对话或并行处理能力。
4. 根据错误率动态调整批次大小：一旦遇到 429 (Too Many Requests) 错误，自动缩减下一批次的请求数量。

**注意事项**: 
批处理会增加请求的延迟（等待队列填满的时间），因此不适用于对实时性要求极高的交互式场景。需在吞吐量和延迟之间找到平衡点。

### 实践 2：构建智能指数退避与重试机制

**说明**: 
在扩展访问规模时，瞬时的流量高峰不可避免。简单的重试会加剧服务器负载，导致限流情况恶化。实施“抖动”的指数退避策略，可以在系统压力大时自动降低请求频率，并在恢复后平滑地增加流量，从而实现“弹性”访问。

**实施步骤**:
1. 捕获所有与限流相关的 HTTP 状态码（如 429）或网络异常（如 timeout）。
2. 设计重试策略：第一次重试等待 1 秒，第二次等待 2 秒，第三次等待 4 秒，以此类推，设置最大重试次数（如 5 次）。
3. 引入随机抖动：在计算出的等待时间基础上增加一个随机的毫秒数（例如 `wait_time * random.uniform(0.8, 1.2)`），防止多个客户端同时重试造成“惊群效应”。
4. 对于无法恢复的错误（如 401 认证失败），立即停止重试以避免浪费配额。

**注意事项**: 
必须为重试逻辑设置上限，避免在服务长时间不可用时无限期挂起用户请求。建议结合“断路器”模式使用。

### 实践 3：优化 Prompt 缓存与去重

**说明**: 
在代码生成或视频生成场景中，用户的请求往往包含大量重复的上下文或指令。对于 Codex，重复的代码库上下文；对于 Sora，重复的风格描述，都会消耗大量的 Token。通过在客户端或网关层实现缓存和去重，可以避免重复发送相同的内容，从而绕过针对输入 Token 的速率限制。

**实施步骤**:
1. 对用户输入进行标准化处理（去除空格、统一大小写等），并生成哈希值作为唯一标识。
2. 在发送请求前，检查本地或 Redis 缓存中是否存在该哈希值的结果。
3. 对于部分重复的上下文（如 Codex 的系统提示词），建立引用机制，仅发送哈希 ID 或简短引用，如果 API 支持则直接使用，不支持则由本地服务拼装。
4. 设定合理的 TTL（生存时间），确保生成内容的时效性。

**注意事项**: 
缓存策略需要谨慎处理，过期的缓存可能导致用户获得旧版本的模型结果。对于生成类任务，需确保去重逻辑不会误判细微的差异。
