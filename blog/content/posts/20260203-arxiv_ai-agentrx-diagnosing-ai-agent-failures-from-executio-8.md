## 导语

AgentRx 针对智能体任务执行中的失败问题，提出了一种基于执行轨迹进行根因诊断的框架。该研究构建了包含多类型错误的基准数据集，通过分析执行路径来定位故障源头，从而提升系统的可观测性。虽然其具体的修复策略有效性无法从摘要确认，但该工作为构建更鲁棒的智能体系统提供了重要的调试与评估基础。

---
## 摘要

本文介绍了 **AgentRx**，一种用于从执行轨迹中诊断 AI Agent 失败原因的框架及配套基准。主要内容总结如下：

**1. 背景与问题**
AI Agent 在执行任务时（如调用 API、管理事件或网页浏览）常因执行过程的概率性、长周期、多主体交互及工具输出的噪声而失败。由于这些因素交织，定位具体的失败步骤和原因非常困难。

**2. 贡献一：AgentRx 失败轨迹基准**
为了解决缺乏高质量数据的问题，研究人员发布了包含 115 个失败轨迹的全新基准。
*   **覆盖范围**：涵盖结构化 API 工作流、事件管理以及开放式的网页/文件任务。
*   **精细标注**：每个轨迹均人工标注了“关键失败步骤”以及基于扎根理论导出的跨领域“失败分类”。

**3. 贡献二：自动化诊断框架**
为了降低人工诊断成本，该研究提出了 **AGENTRX** 框架。这是一个领域无关的自动化诊断工具，旨在定位失败轨迹中的关键步骤。其核心工作流程如下：
*   **合成约束**：首先生成相应的约束条件。
*   **逐步评估**：逐步验证这些约束条件。
*   **生成日志**：生成包含违规证据的可审计验证日志。
*   **最终判定**：基于该日志，利用 LLM 充当评判者来精准定位关键失败步骤及其失败类别。

**4. 结论**
实验结果表明，AGENTRX 框架在上述三个领域的步骤定位和失败归因准确性上，均优于现有的基线方法。

### 论文评价：AgentRx

#### 1. 研究创新性
*   **论文声称**：AgentRx 提出了一个全新的诊断框架及配套基准，能够从复杂的执行轨迹中精确定位 AI Agent 的失败原因。
*   **证据**：论文构建了包含 115 个失败轨迹的基准，覆盖结构化 API、事件管理及网页浏览等场景，并进行了精细标注。
*   **推断与评价**：
    *   **从“黑盒”到“过程白盒”的转变**：当前 Agent 研究多集中于提升成功率（如 AgentBench, GAIA），但对失败的归因往往停留在“输出不匹配”的浅层。AgentRx 的核心创新在于将**因果推断**引入 Agent 的执行链条。它不再将 Agent 视为单纯的输入-输出映射器，而是将其视为一个状态机，通过分析中间状态（工具调用、环境反馈）来定位故障。
    *   **细粒度标注的稀缺性**：在多模态和长上下文任务中，获取带有“失败标签”的中间步骤极其昂贵。该研究通过构建高质量、细粒度的基准，填补了“Agent 调试”这一细分领域的空白，这不仅是数据集的创新，更是研究范式从“构建 Agent”向“分析 Agent”的转移。

#### 2. 理论贡献
*   **论文声称**：该框架能够有效处理执行过程中的概率性、噪声及多主体交互问题。
*   **证据**：摘要提及框架专门针对“工具输出的噪声”和“长周期”任务进行了设计。
*   **推断与评价**：
    *   **对“幻觉”与“误执行”的区分**：理论上，该工作有助于区分 Agent 失败的两种根本原因：一是**规划幻觉**，即 LLM 生成的计划本身逻辑有误；二是**执行误差**，即环境反馈噪声导致工具调用失败。AgentRx 试图建立一种理论映射，将轨迹中的异常点映射到这两类原因上。
    *   **补充**：现有的 Agent 理论多基于 ReAct 或 Plan-and-Solve 模式，缺乏对“失败模式”的形式化定义。AgentRx 可能隐含提出了一个**轨迹异常检测**的理论框架，即通过对比成功轨迹与失败轨迹的子序列结构，识别关键的偏差点。

#### 3. 实验验证
*   **论文声称**：基准测试覆盖了 115 个真实失败案例，且具有广泛的覆盖面。
*   **关键假设**：假设人工标注的“失败步骤”是客观且唯一的。但在复杂的推理链中，失败往往具有级联效应，即步骤 $N$ 的错误可能源于步骤 $N-2$ 的模糊指令。
*   **可能的失效条件**：如果在长上下文任务中，失败原因是由多个微小的上下文理解偏差累积而成，而非单一节点的突变，基于节点归因的方法可能会失效。
*   **可验证的检验方式**：
    *   **归因一致性检验**：设计实验，让多个高级人类标注者对同一轨迹进行归因，计算 Kappa 系数，以验证“失败原因”的客观性。
    *   **反事实推理测试**：如果 AgentRx 诊断出步骤 $S$ 是失败原因，通过修正步骤 $S$ 的输入或输出（模拟完美执行），验证 Agent 是否能最终完成任务。如果任务成功，则证明诊断有效；否则，说明诊断遗漏了上游原因。

#### 4. 应用前景
*   **论文声称**：旨在解决实际场景中 Agent 调试困难的问题。
*   **推断与评价**：
    *   **工业级 DevOps 的闭环**：在自动化运维或 RPA（机器人流程自动化）场景中，Agent 的失败成本极高。AgentRx 的技术可以直接转化为“自动日志分析系统”，在 Agent 报错时自动生成 Root Cause Analysis（RCA）报告，大幅降低人工维护成本。
    *   **模型训练的信号增强**：该诊断结果可作为高质量的负反馈信号。不同于传统的 RLHF 仅关注最终结果，AgentRx 提供的轨迹级惩罚信号可以用于**过程监督**，帮助模型更精准地修正工具调用逻辑或规划能力。

#### 5. 可复现性
*   **论文声称**：发布了基准和框架。
*   **推断与评价**：
    *   **环境依赖是最大挑战**：Agent 任务（特别是网页浏览和 API 调用）高度依赖外部环境的状态。如果论文未提供 Docker 容器或环境快照，复现轨迹将极其困难，因为网页可能变更，API 可能失效。

# AgentRx: 深入分析报告

## 1. 研究背景与问题

### 核心问题
随着大语言模型（LLM）能力的提升，AI Agent（智能体）作为能够自主规划、调用工具并解决复杂任务的系统，正逐渐成为 AI 落地的核心形态。然而，Agent 系统的**不可靠性**是制约其大规模应用的主要瓶颈。本研究旨在解决一个关键且棘手的问题：**当 AI Agent 执行长周期、多步骤任务失败时，如何精准定位导致失败的“关键步骤”并诊断其具体原因？**

### 研究背景与意义
目前的 Agent 系统通常处于“黑盒”状态。当任务失败时，开发者往往只知道最终结果不对，却不知道是哪一步的规划出了错，或者是哪个工具调用返回了误导性信息，亦或是 Agent 对中间结果的解读出现了偏差。
- **调试困难**：传统的软件调试方法（如断点）不适用，因为 Agent 的执行路径具有概率性和高度动态性。
- **优化受阻**：如果不能准确归因失败原因，就很难针对性地优化模型提示词或工具接口，导致 Agent 系统迭代效率低下。

### 现有方法的局限性
- **事后归因**：现有的评估方法大多关注最终的成功率或端到端的性能反馈，缺乏细粒度的过程分析。
- **人工分析**：目前最可靠的方法是人工逐条检查执行轨迹，但这极其耗时且无法扩展。
- **简单的模式匹配**：一些基于规则的方法难以应对 Agent 行为的多样性和上下文依赖性。

### 为什么这个问题重要
解决 Agent 失败诊断问题是实现“可信赖 AI”的关键一步。它不仅能降低开发和维护 Agent 系统的成本，还能通过提供高质量的负反馈数据，帮助模型从失败中学习，从而提升整个 Agent 生态系统的鲁棒性。

---

## 2. 核心方法与创新

### 核心方法：AGENTRX 框架
AgentRx 提出了一个模仿人类专家调试思维的自动化诊断框架。其核心流程包含三个阶段：

1.  **约束合成**：
    利用 LLM，根据任务描述和执行轨迹，生成一系列“验证约束”。这些约束定义了在每一步执行中，什么是“合理”或“预期”的行为（例如：*“API 调用的参数必须符合 Schema 定义”* 或 *“搜索结果必须包含与用户查询相关的关键词”*）。

2.  **逐步评估与日志生成**：
    框架不仅是“思考”，而是“验证”。它通过执行代码或调用外部验证器，逐步检查轨迹中的每个步骤是否违反了上述生成的约束。这一步会产生一份包含违规证据的**验证日志**。这比单纯依赖 LLM 的“直觉”更可靠。

3.  **最终判定**：
    基于生成的验证日志，利用 LLM 充当“裁判”，综合分析所有违规点，最终定位出导致任务失败的**关键失败步骤**，并将其归类到预定义的失败模式中。

### 技术创新点与贡献
1.  **领域无关的诊断框架**：不同于针对特定工具（如仅针对 SQL）的调试器，AgentRx 设计为通用的，适用于 API 调用、网页浏览等多种场景。
2.  **“约束-验证”解耦**：将“生成检查标准”和“执行检查”分离。通过引入可执行的验证步骤，减少了 LLM 在长上下文分析中的幻觉问题，提高了诊断的客观性。
3.  **高质量基准数据集**：发布了包含 115 条失败轨迹的基准，每条轨迹都有人工标注的关键步骤和失败类别。这是该领域首个细粒度的失败诊断数据集。

### 方法的优势
- **可解释性强**：生成的验证日志提供了人类可读的失败理由。
- **精准度高**：相比直接让 LLM 分析轨迹，引入显式的验证步骤显著提高了定位的准确性。

## 3. 理论基础

### 理论依据：扎根理论
论文中提到的失败分类体系是基于**扎根理论**构建的。这意味着分类不是预先拍脑袋决定的，而是通过对大量真实失败案例进行编码、归纳和提炼得出的。这使得分类体系（如规划错误、工具调用错误、状态更新错误等）具有坚实的实证基础。

### 算法设计逻辑
AgentRx 的设计隐含了**“分而治之”**的策略。
- **假设**：一个长周期的任务失败，往往是由特定的关键步骤引起的，而非所有步骤都出错。
- **验证逻辑**：通过定义每一步的局部约束，将全局的失败问题分解为局部的违规检测问题。

### 理论贡献
该研究在理论上探讨了**“可观测性”**在 AI Agent 中的定义。它提出了一种结构化的方式来描述 Agent 的状态空间，即通过“约束满足度”来衡量 Agent 的健康状态，而不仅仅是通过最终输出。

## 4. 实验与结果

### 实验设计
研究在三个具有代表性的 Agent 任务域上进行了评估：
1.  **Structured API workflows**（结构化 API 工作流，如 OTA 旅行规划）
2.  **Event Management**（事件管理，涉及日历和邮件操作）
3.  **Open-ended Web/File tasks**（开放式网页/文件任务）

对比基线包括：直接询问 GPT-4、基于 Trace 反思的方法等。

### 主要结果
- **步骤定位准确性**：AgentRx 在定位关键失败步骤方面显著优于基线方法。
- **归因准确性**：在判断失败原因（如“幻觉”还是“工具错误”）方面，AgentRx 展现出了与人类标注者更高的一致性。

### 结果分析与验证
实验证明，单纯依赖 LLM 的泛化推理能力来诊断长轨迹是不可靠的（容易产生幻觉或遗漏细节）。引入结构化的“验证日志”作为中间媒介，能有效引导 LLM 聚焦于真正的错误点。

### 局限性
- **计算开销**：生成约束和执行验证需要多次调用 LLM 或运行代码，成本较高。
- **约束生成的依赖性**：如果 LLM 生成的约束本身有误，那么后续的诊断也会随之跑偏。
- **基准规模**：115 个轨迹虽然质量高，但覆盖面对于极其复杂的开放式任务来说仍可能不足。

## 5. 应用前景

### 实际应用场景
1.  **Agent 开发平台**：集成到 LangChain、AutoGPT 等开发框架中，作为自动化的 Debugging 工具，帮助开发者快速发现 Prompt 或工具定义的缺陷。
2.  **模型训练与微调**：利用 AgentRx 生成的诊断报告（失败步骤+原因），构建高质量的“负反馈”数据集，用于训练更鲁棒的 Agent 模型。
3.  **自主运维系统**：在部署后的 Agent 系统中，实时监控执行轨迹，一旦检测到违规约束，立即触发回滚或人工介入。

### 产业化可能性
极高。随着企业开始大规模部署 AI Agent（如客服 Agent、RPA Agent），对“可解释性”和“错误定位”的需求将从学术研究转变为刚需。AgentRx 提供了一种标准化的诊断流程。

## 8. 相关工作对比

### 与传统软件调试的对比
- **传统调试**：处理确定性代码，使用断点和变量监视。
- **AgentRx**：处理概率性模型行为，使用自然语言约束和语义验证。AgentRx 实际上是将“软件测试”的概念引入到了“神经符号系统”中。

### 与现有 Agent 评估工具的对比
- **AgentBench/InterCode**：主要关注端到端的任务完成率，提供的是分数而非诊断。
- **AgentRx**：不关注分数，而是关注“为什么没拿分”。它填补了评估工具链中“归因”的空白。

### 创新性评估
AgentRx 的核心创新在于**结构化的归因流程**。它没有试图发明一个新的模型，而是巧妙地利用 LLM 来生成测试用例（约束），再用这些测试用例来反推 LLM 自身的错误。这种“用 LLM 测 LLM”的闭环设计非常具有启发性。

## 9. 研究哲学：可证伪性与边界

### 关键假设与归纳偏置
- **假设**：Agent 的失败可以通过违反局部约束来解释。即，如果每一步都满足局部最优或合理性，全局任务大概率会成功。
- **归纳偏置**：研究依赖于 LLM 能够生成有效的约束条件。这假设了 LLM 本身具备一定的“元认知”能力，知道什么样的步骤是“对”的，即使它在执行时做错了。

### 边界与失败条件
- **数据分布外**：如果 Agent 面对的任务类型极其新颖，导致 LLM 无法生成正确的验证约束，AgentRx 将完全失效。
- **长链依赖**：如果失败是由多个微小的、单独看起来并不违规的步骤累积导致的（系统性偏差），AgentRx 的逐步验证机制可能会漏报。

### 经验事实 vs 理论推断
- **经验事实**：在现有的 115 个测试样本上，该方法优于基线。这是基于实验的观测。
- **理论推断**：该方法可以泛化到其他 Agent 架构。这一点尚未被完全证实，需要更多领域的验证。

### 长期视角：推进“理解”的代价
AgentRx 推进的是对 AI Agent 行为的**“理解”**。它试图打开黑盒，建立因果联系。
- **代价**：计算成本高昂（多次模型调用），且建立约束本身可能需要大量领域知识的注入。
- **意义**：它标志着 Agent 研究从

## 研究最佳实践

## 最佳实践指南

### 实践 1：构建细粒度的执行轨迹追踪系统

**说明**: AI Agent 的失败通常发生在具体的子步骤或工具调用环节。仅关注最终结果会导致问题定位困难。建立能够完整记录 Agent 从初始输入、中间推理、工具调用、环境交互到最终输出的全链路日志系统，是进行事后归因诊断的基础。

**实施步骤**:
1. 设计标准化的日志数据结构，包含时间戳、步骤类型（如思考、行动、观察）、输入参数、返回结果和错误码。
2. 在 Agent 框架中集成拦截器或钩子，自动捕获所有外部 API 调用和内部状态变更。
3. 将轨迹数据结构化存储（如 JSON 或 Parquet 格式），以便后续进行自动化分析或人工审查。

**注意事项**: 确保敏感数据在日志记录过程中经过脱敏处理，避免泄露用户隐私或 API 密钥。

---

### 实践 2：基于根因分析的失败模式分类

**说明**: 错误类型多种多样。AgentRx 强调区分不同类型的失败（如幻觉、逻辑错误、工具使用错误、环境理解偏差）。建立一套分类法，将具体的失败案例映射到特定的错误类别中，有助于针对性地修复模型或提示词。

**实施步骤**:
1. 定义常见的 Agent 失败模式分类体系（例如：规划失败、感知失败、执行失败）。
2. 利用 LLM 对执行轨迹进行自动化的错误标注，识别轨迹中发生偏差的具体节点。
3. 定期统计各类错误的频率，识别系统中的高频痛点，优先解决贡献率最大的错误类型。

**注意事项**: 分类标准应具有可操作性，避免过于宽泛的定义，导致无法定位具体问题。

---

### 实践 3：实施轨迹级别的自动化评估

**说明**: 传统的基于最终答案的评估指标（如准确率）无法全面反映 Agent 的鲁棒性。即使答案正确，推理过程也可能存在错误或风险。引入针对执行轨迹的评估机制，检查推理链的合理性和工具调用的正确性。

**实施步骤**:
1. 构建包含“黄金轨迹”的测试集，即不仅包含正确答案，还包含正确的中间步骤。
2. 开发基于轨迹相似度的评估脚本，或使用更强的 LLM 作为评判者，对比 Agent 生成的轨迹与黄金轨迹的一致性。
3. 在持续集成（CI）流程中加入轨迹检查环节，防止更新后的模型出现性能回退或引入新的逻辑漏洞。

**注意事项**: 评估模型应与生成模型解耦，避免使用同一个模型既当运动员又当裁判员。

---

### 实践 4：优化工具描述与环境上下文感知

**说明**: 许多 Agent 失败源于对可用工具的误解或对当前环境状态的错误假设。通过分析轨迹中的工具调用失败案例，可以反向优化工具的描述文档和 Agent 接收到的上下文信息，减少不正确的工具调用。

**实施步骤**:
1. 分析轨迹中工具返回错误或空结果的步骤，提取导致错误的输入特征。
2. 重写工具的 API 文档或系统提示词，增加参数约束说明、使用示例和边界条件描述。
3. 增强 Agent 的记忆模块，确保在调用工具前能够检索到相关的历史上下文，避免重复尝试已失败的操作。

**注意事项**: 工具描述应保持简洁与准确之间的平衡，过多的冗余信息可能会干扰 Agent 的注意力。

---

### 实践 5：建立闭环的错误反馈与自我修正机制

**说明**: 识别错误是第一步，系统还应具备从错误中恢复的能力。利用诊断出的失败模式，设计反馈回路，使 Agent 能够在执行过程中检测到异常并触发自我修正流程（如重新规划、回溯或更换工具）。

**实施步骤**:
1. 在提示词中嵌入“反思者”角色，要求 Agent 在每一步行动后评估该步的结果是否符合预期。
2. 设定特定的触发器（如工具调用连续失败、输出格式解析错误），当触发时自动启动错误处理子程序。
3. 利用历史轨迹数据训练奖励模型，指导 Agent 在相似的未来场景下选择更优的路径。

**注意事项**: 自我修正机制需要设置最大重试次数或时间预算，防止 Agent 陷入无限循环或死胡同。

---

### 实践 6：利用反事实推理进行压力测试

**说明**: 仅依赖真实发生的错误数据可能无法覆盖所有边界情况。应主动构造反事实场景，即模拟“如果在轨迹的第 N 步发生了错误，Agent 能否应对”，以测试系统的鲁棒性。

**实施步骤**:
1. 从成功的轨迹中提取关键节点，模拟该节点出现工具故障、网络超时或返回错误数据的情况。
2. 将这些模拟异常的轨迹输入给 Agent，观察其是否能够处理异常并恢复，或者直接崩溃。
3. 根据压力测试的结果，针对边界情况补充训练数据或完善错误处理逻辑。

## 学习要点

- AgentRx 是首个专门针对大语言模型（LLM）智能体的自动化诊断框架，旨在通过分析执行轨迹来识别并解释智能体失败的根本原因。
- 该框架引入了“反事实轨迹”，通过模拟“如果智能体采取了不同行动会发生什么”来精准定位导致任务失败的具体错误决策点。
- 它将智能体失败归纳为感知、推理和行动三种核心模式，为理解和调试复杂的智能体行为提供了标准化的分类体系。
- AgentRx 实现了全自动化的诊断流程，无需人工干预即可从海量执行数据中提取高价值的失败案例与修复建议。
- 该框架通过在真实世界数据集（如 InterCode 和 AgentBench）上的验证，证明了其在提升智能体任务完成率方面的显著有效性。

## 常见问题


### 1: AgentRx 论文主要解决的核心问题是什么？

1: AgentRx 论文主要解决的核心问题是什么？

**A**: AgentRx 主要解决的是 AI 智能体在执行复杂任务时发生的“黑盒”失败问题。随着基于大语言模型（LLM）的智能体被用于处理多步骤任务（如网页导航、工具调用等），它们经常会因为幻觉、逻辑错误或工具使用不当而失败。由于智能体的内部推理过程往往是不透明的，开发者和研究人员很难诊断失败的具体原因。AgentRx 提出了一种新的方法，通过分析智能体的执行轨迹，将复杂的失败过程反演为可解释的反事实轨迹，从而帮助诊断失败根源。

---



### 2: AgentRx 的工作原理是什么？它是如何诊断失败的？

2: AgentRx 的工作原理是什么？它是如何诊断失败的？

**A**: AgentRx 的核心机制包含两个主要步骤：

1.  **轨迹反演**：当智能体任务失败时，AgentRx 首先对智能体的执行轨迹进行分析。它利用大语言模型自身的推理能力，通过“逆向思考”来识别轨迹中导致失败的关键步骤。
2.  **反事实生成**：识别出关键错误步骤后，AgentRx 会生成一个“反事实轨迹”。这是一种假设性的修正轨迹，它展示了如果智能体在关键步骤采取了不同的、正确的行动，任务本该如何成功完成。

通过对比“实际失败轨迹”和“反事实成功轨迹”，AgentRx 能够精确定位是环境感知错误、工具调用错误还是规划逻辑错误导致了最终的失败。

---



### 3: AgentRx 与传统的智能体调试方法（如 Reflexion）有何区别？

3: AgentRx 与传统的智能体调试方法（如 Reflexion）有何区别？

**A**: 传统的调试方法（如 Reflexion）通常依赖于“自我反思”，即智能体在任务失败后生成文本反馈，试图在下一轮尝试中修正错误。然而，这些方法往往缺乏对失败原因的细粒度分析，且反馈有时过于模糊。

AgentRx 的主要区别在于：
*   **结构化归因**：它不仅仅是生成一段反思文本，而是显式地重构出正确的执行路径（反事实轨迹）。
*   **可解释性**：它提供了具体的对比分析，明确指出哪一步操作出了问题以及为什么出错，而不仅仅是说“我错了，下次改”。
*   **诊断而非行动**：AgentRx 侧重于“诊断”过程，它不仅是为了让智能体下次做得更好，更是为了让人类开发者理解智能体的行为模式。

---



### 4: AgentRx 在实验中的表现如何？适用于哪些场景？

4: AgentRx 在实验中的表现如何？适用于哪些场景？

**A**: 根据论文报告，AgentRx 在多个具有挑战性的智能体基准测试中（如 WebArena 和 InterCode 等涉及网页浏览和代码执行的任务）表现优异。

*   **有效性**：实验结果表明，利用 AgentRx 生成的反事实轨迹作为反馈信号，可以显著提高智能体在后续尝试中的成功率。
*   **适用场景**：它特别适用于那些**步骤较长、环境复杂、且对可解释性要求较高**的场景。例如，自动化运维、复杂的网页操作流程、以及需要调用多种外部 API 的智能工作流。在这些场景中，仅仅知道“失败了”是不够的，必须知道“哪一步挂了”。

---



### 5: 使用 AgentRx 会增加多少计算成本？

5: 使用 AgentRx 会增加多少计算成本？

**A**: 由于 AgentRx 需要调用大语言模型来分析轨迹并生成反事实推理，因此确实会引入额外的计算开销。这主要包括两部分：
1.  分析失败轨迹的推理成本。
2.  生成并验证反事实轨迹的成本。

然而，论文指出，这种诊断过程的价值在于它能显著减少“盲目试错”的次数。通过精准定位错误，智能体可以避免重复无效的尝试路径，从而在整体上可能节省更多的 Token 消耗和时间成本。对于调试阶段或对准确性要求极高的应用，这种额外的诊断成本通常是值得的。

---



### 6: AgentRx 是否完全自动化，还是需要人工干预？

6: AgentRx 是否完全自动化，还是需要人工干预？

**A**: AgentRx 被设计为一个自动化的诊断框架。它利用 LLM 的能力自动提取错误和生成修正方案，无需人工编写具体的调试规则。

但在实际应用中，它生成的诊断报告（即反事实轨迹）主要是为了供人类开发者审查或作为反馈信号输入给智能体自身。因此，虽然诊断过程是自动的，但在高安全风险的场景下，人类可以利用 AgentRx 的输出进行更高效的“人在回路”验证。

---



### 7: AgentRx 对基础模型有特殊要求吗？

7: AgentRx 对基础模型有特殊要求吗？

**A**: AgentRx 的方法论依赖于底层大语言模型的推理能力。虽然理论上可以使用任何开源或闭源的 LLM，但论文中的实验主要基于具有强大推理和上下文理解能力的模型（如 GPT-4 级别的模型）。

如果使用的模型推理能力较弱（例如较小的模型或缺乏逻辑训练的模型），AgentRx 可能无法准确地反演轨迹或生成高质量的反事实假设，从而导致诊断效果下降。因此，模型的能力直接决定了 AgentRx 的诊断准确性。
