## 导语

针对 AI Agent 因执行过程复杂而难以定位故障的问题，本文提出了自动化诊断框架 AgentRx 及包含 115 个失败轨迹的新基准。该方法通过合成约束并逐步评估执行日志，实现了对失败步骤的精准归因。尽管其具体自动化程度与人工标注效率尚无法从摘要确认，但该研究为降低长周期任务的分析成本提供了跨领域的通用思路。

---
## 摘要

以下是关于论文《AgentRx: Diagnosing AI Agent Failures from Execution Trajectories》的简洁总结：

**核心问题**
AI Agent 在执行任务时经常失败，但由于其执行过程具有概率性、长周期、多代理交互以及受噪声工具输出干扰等特点，导致这些失败难以定位和归因。

**研究贡献**
1.  **新基准数据集**：
    *   作者发布了一个包含 **115 个失败轨迹** 的新基准，涵盖结构化 API 工作流、事故管理以及开放式的 Web/文件任务。
    *   每条轨迹都经过人工标注，标记了导致失败的关键步骤及失败类别。
    *   建立了一个基于扎根理论的、跨领域的失败分类体系。

2.  **AGENTRX 框架**：
    *   这是一个**自动化、领域无关**的诊断框架，旨在降低人工分析成本。
    *   **工作原理**：
        1.  **约束合成**：首先合成约束条件。
        2.  **逐步评估**：逐步评估这些约束。
        3.  **生成日志**：生成包含违规证据的可审计验证日志。
        4.  **LLM 判决**：基于该日志，利用大语言模型（LLM）作为判决器，来定位关键失败步骤并分类失败类型。

**实验结果**
在三个领域的测试中，AGENTRX 框架在步骤定位和失败归因方面的表现均优于现有的基线方法。

## 评论

以下是对论文《AgentRx: Diagnosing AI Agent Failures from Execution Trajectories》的深入学术评价。

---

### **《AgentRx》论文深度评价报告**

#### **1. 研究创新性**

*   **论文声称**：AgentRx 引入了一种全新的“事后归因”范式，通过分析失败轨迹来诊断 Agent 的错误，并发布了包含 115 个精细标注失败案例的基准测试。
*   **证据**：论文展示了其数据集覆盖了结构化 API、事故管理及 Web/文件任务三类场景，且每个样本均包含导致失败的关键步骤标注和错误类型分类（如幻觉、工具选择错误等）。
*   **推断与评价**：
    该研究在方法论上实现了从“评估成功率”到“诊断失败根因”的视角转换。传统的 Agent 评估（如 AgentBench, SWE-bench）主要关注任务完成率，而 AgentRx 首次系统性地构建了**因果链路**的数据集。这种创新性在于它将 Agent 的调试过程从“黑盒试探”转变为“白盒解剖”。
*   **关键假设**：假设 Agent 的执行轨迹（包含思维链、工具调用、中间状态）包含了足够的信息以供人类或模型进行回溯诊断。
*   **失效条件**：对于非 CoT（Chain-of-Thought）架构的 Agent，或者轨迹记录不完整（如缺少中间环境状态反馈）的系统，该方法可能失效。
*   **验证方式**：设计消融实验，对比仅使用最终结果与使用完整轨迹进行诊断的准确率差异。

#### **2. 理论贡献**

*   **论文声称**：AgentRx 建立了一个通用的 Agent 失败分类学，将错误归纳为规划、执行、知识获取等维度。
*   **证据**：论文定义了详细的标签体系，并统计了不同类型任务中错误类型的分布情况（例如，Web 任务中检索错误占比更高）。
*   **推断与评价**：
    理论上，该工作补充了 AI Agent 可靠性理论中的**“错误归因”**板块。它隐含地提出了一种观点：Agent 的智能不仅表现为成功的能力，更表现为对失败的可解释性。这为后续研究“自愈 Agent”提供了理论基石——只有准确分类错误，才能设计针对性的修复策略。
*   **关键假设**：Agent 的失败是离散且可分类的，且存在一个主导性的失败根因，而非多个微小误差的累积耦合。
*   **失效条件**：在多 Agent 协作场景中，失败可能源于交互涌现出的混沌效应，单一维度的分类学可能无法解释复杂的系统级崩溃。
*   **验证方式**：尝试用该分类体系标注多 Agent 系统（如 AutoGen）的失败案例，计算标注者间信度（IFA），若一致性大幅下降，则说明理论框架在复杂系统中失效。

#### **3. 实验验证**

*   **论文声称**：基于 AgentRx 数据集训练的轻量级诊断模型（如 Llama-3-8B-Instruct）在失败定位任务上表现优异，甚至优于 GPT-4 等闭源模型。
*   **证据**：论文展示了不同模型在轨迹诊断任务上的 F1 分数和准确率，并提供了混淆矩阵分析。
*   **推断与评价**：
    实验设计的亮点在于**“模型作为诊断者”**的设定。这验证了小模型可以通过学习轨迹模式来掌握大模型的“病理特征”。然而，实验存在潜在的**数据泄露风险**：如果训练集中的失败模式与测试集高度相似（例如同一种 API 调用错误），则模型可能只是在记忆模式而非泛化诊断。
*   **关键假设**：测试集中的失败轨迹与训练集在底层逻辑上是独立同分布的，或者至少具有可迁移的结构特征。
*   **失效条件**：当 Agent 架构发生根本性变化（例如从 ReAct 模式变为 Plan-and-Solve 模式），诊断模型的泛化能力将面临严峻考验。
*   **验证方式**：进行跨架构测试。在一个从未见过的 Agent 架构（例如全新的规划工具）生成的轨迹上测试诊断模型的准确率。

#### **4. 应用前景**

*   **论文声称**：该研究有助于构建自动调试工具和提升 Agent 系统的鲁棒性。
*   **证据**：通过识别具体的失败步骤，开发者可以针对性地修复提示词或工具接口。
*   **推断与评价**：
    应用价值极高。在工业界，部署 Agent 最大的阻碍不是“不够聪明”，而是“不可控”。AgentRx 提供了一种**监控流水线**的雏形。它可以集成到 Agent DevOps 平台中，实时监控执行轨迹，一旦检测到高风险模式（如反复的无效工具调用），即可触发熔断或重试机制。此外，该数据集是训练“批评者模型”的黄金语料。
*   **关键假设**：生产环境中的日志格式与 AgentRx 定义的轨迹格式兼容，且诊断延迟在可接受范围内。
*   **失效条件**：在极高并发或对隐私敏感的场景下，上传完整轨迹进行诊断可能不可行。
*   **验证方式**：构建一个端到端的原型系统，集成诊断模块，测量其对整体任务成功率的提升幅度及诊断带来的时间开销。

*   **论文声称**：作者已发布数据集和代码，且标注过程经过严格的质量控制。

# AgentRx: 从执行轨迹诊断 AI Agent 失败——深度分析报告

## 1. 研究背景与问题

### 核心问题
随着大语言模型（LLM）能力的提升，基于 LLM 的 AI Agent（智能体）在处理复杂任务（如调用 API、网页浏览、文件操作）方面展现出巨大潜力。然而，这些 Agent 在执行过程中经常失败。该论文试图解决的核心问题是：**如何高效、准确地诊断 AI Agent 的失败原因？**

具体而言，Agent 的执行过程具有非确定性（概率性）、步骤长、涉及多轮交互以及依赖外部工具反馈等特点。当任务失败时，仅仅通过查看最终的输出结果很难定位是哪一个具体的中间步骤出了问题，或者是哪一种类型的错误导致了失败。

### 研究背景与意义
- **黑盒性质**：LLM 是概率模型，其推理过程对于人类来说仍具有黑盒属性。Agent 的行为更是模型逻辑与外部环境交互的叠加，极其复杂。
- **调试困难**：目前的 Agent 调试主要依赖人工阅读海量日志，成本极高且容易遗漏。
- **可靠性瓶颈**：如果无法有效诊断失败，就很难改进 Agent 的设计或提示词，这限制了 AI Agent 在关键业务场景中的落地。

### 现有方法的局限性
- **事后归因**：大多数现有工作只关注最终的成功率，缺乏对失败过程的细粒度分析。
- **人工标注**：完全依赖人工分析轨迹，不仅昂贵，而且无法规模化。
- **简单基线**：现有的自动化诊断方法（如简单的关键词匹配或直接让 GPT-4 分析整个轨迹）在面对长轨迹和噪声干扰时，往往因为上下文过长或注意力分散而表现不佳。

### 为什么这个问题重要
解决 Agent 的诊断问题是实现“可信赖 AI”的关键一步。只有理解了 Agent *为什么*失败（是因为规划错误、工具调用错误、还是理解错误？），开发者才能针对性地进行修复。这直接关系到 AI Agent 系统的工程化落地和迭代优化。

## 2. 核心方法与创新

### 提出的核心方法：AGENTRX
论文提出了一个名为 **AGENTRX** 的自动化、领域无关的诊断框架。其核心思想是将“诊断”问题转化为“约束验证”问题，而不是让 LLM 直接进行开放式分析。

该框架包含两个主要阶段：
1.  **离线阶段（约束合成）**：利用 LLM 分析任务描述和成功轨迹，生成一套用于验证每个步骤正确性的约束条件。这些约束定义了“在这一步，什么是对的，什么是错的”。
2.  **在线阶段（诊断执行）**：
    *   **逐步评估**：拿着合成好的约束，去检查失败轨迹中的每一个步骤。
    *   **生成日志**：记录每一步是否违反了约束以及具体的证据。
    *   **LLM 判决**：基于生成的违规日志，让 LLM 进行最终的判决，定位关键失败步骤并分类失败类型。

### 技术创新点与贡献
1.  **约束引导的诊断**：这是最大的创新。不同于直接让 LLM “找茬”，AgentRx 先让 LLM 生成“检查清单”。这种解耦策略极大地降低了推理难度，提高了诊断的准确率。
2.  **领域无关性**：该方法不依赖特定的 API 或工具定义，而是通过通用的接口处理轨迹，因此可以应用于 Web 任务、API 工作流等多种场景。
3.  **新基准数据集**：构建了一个包含 115 个失败轨迹的高质量人工标注数据集，并提出了基于扎根理论的失败分类体系，为后续研究提供了评估标准。

### 方法的优势
- **抗噪声能力强**：通过生成结构化的验证日志，过滤掉了无关的上下文信息，帮助判决器 LLM 聚焦于关键错误。
- **可解释性**：不仅给出诊断结果，还提供了具体的违规约束和证据，便于开发者理解。
- **模块化**：约束合成和诊断执行分离，可以使用不同的模型或策略来优化不同部分。

## 3. 理论基础

### 使用的理论基础
- **扎根理论**：在构建数据集和分类体系时，作者采用了扎根理论的方法。这意味着他们不是预先设定好错误类别，而是通过分析大量实际失败的 Agent 轨迹，从中归纳出常见的失败模式（如：幻觉、工具误用、上下文丢失等）。
- **假设检验与验证**：AgentRx 的逻辑内核类似于软件测试中的断言。它将诊断过程看作是对一系列假设（即：Agent 的行为是否符合预期约束）的验证过程。

### 算法设计
虽然没有复杂的数学公式推导，但其算法逻辑基于**信息抽取与验证**：
- **Input**：Task Description ($T$), Failure Trajectory ($\tau_{fail}$), Reference/Success Info ($T_{ref}$).
- **Process**:
  1.  **Synthesize Constraints** ($C$): $LLM_{generator} \rightarrow (T, T_{ref}) \mapsto \{c_1, c_2, ...\}$
  2.  **Verify Steps** ($V$): For each step $s_i \in \tau_{fail}$, check if $s_i$ satisfies relevant $c_j$. Generate log $L$.
  3.  **Judge** ($J$): $LLM_{judge} \rightarrow (L) \mapsto (\text{Failure Step}, \text{Failure Type})$.

### 理论贡献分析
论文的理论贡献在于提出了一种**将复杂的因果推理问题降维为结构化验证问题**的范式。它证明了在处理长上下文 Agent 轨迹时，先进行结构化的信息提取（约束验证），再进行逻辑推理，比端到端的推理效果更好。

## 4. 实验与结果

### 实验设计和数据集
- **数据集**：包含 115 个真实世界的失败轨迹，涵盖三个领域：
    1.  **Structured API Workflows**（结构化 API 工作流，如 Spotify 操作）。
    2.  **Incident Management**（事故管理，涉及诊断系统故障）。
    3.  **Open-ended Web/File tasks**（开放式 Web/文件任务，如研究公司并写报告）。
- **评估指标**：
    - **Step Localization F1**：定位到具体失败步骤的 F1 分数。
    - **Attribution Accuracy**：正确分类失败类型的准确率。
    - **Cost**：使用的 Token 成本。

### 主要实验结果
- **性能优越**：AgentRx 在步骤定位和失败归因上显著优于基线（如直接询问 GPT-4、TraceAnalysis 等）。
- **成本效益**：虽然引入了额外的约束合成步骤，但由于诊断过程更加精准，总体上在保持高性能的同时，成本处于可接受范围（相比直接使用超长上下文让 GPT-4 分析，可能更节省 Token，因为约束验证可以并行化或使用更小的模型）。

### 结果分析与验证
实验表明，**约束的质量**直接决定了诊断的上限。如果约束合成阶段生成的约束过于宽松或严格，都会影响最终结果。此外，实验验证了“两阶段法”（先生成约束，再验证）优于“单阶段法”（直接分析轨迹）。

### 实验的局限性
- **对参考信息的依赖**：约束合成通常需要成功的轨迹或详细的任务描述作为参考。如果完全没有参考信息，约束生成的质量可能会下降。
- **复杂逻辑推理**：对于跨越多个步骤的、长链路的逻辑错误（例如，步骤 A 的错误直到步骤 Z 才显现），基于单步约束的验证可能难以捕捉。

## 5. 应用前景

### 实际应用场景
- **Agent 开发调试工具**：集成到 LangChain、AutoGPT 等 Agent 开发框架中，作为自动化的 Debugger。
- **生产监控**：在 Agent 运行时，实时监控其轨迹，一旦发现违反关键约束，立即中断或回滚，防止产生严重后果。
- **数据集清洗**：用于自动筛选和标注训练数据，提高微调数据的质量。

### 产业化可能性
极高。随着企业开始大规模部署 AI Agent，对于“可观测性”和“安全性”的需求呈指数级增长。AgentRx 提供了一种标准化的诊断流程，非常适合转化为企业级的 SaaS 服务或内部平台工具。

### 与其他技术的结合
- **RLHF（基于人类反馈的强化学习）**：利用 AgentRx 自动生成的失败报告作为 Reward Model 的信号，用于训练更稳定的 Agent。
- **Self-Reflexion（自我反思）**：将 AgentRx 作为 Agent 的“外挂大脑”，让 Agent 在行动前先自我检查约束，或者在失败后自动阅读诊断报告进行修正。

## 6. 研究启示

### 对该领域的启示
- **从“做得更好”转向“错得更明白”**：过去的研究多集中在如何提高 Agent 的成功率，而本论文指出了“诊断”是提升成功率的前提。
- **结构化的重要性**：在处理 LLM 的复杂输出时，引入结构化的中间表示（如约束、验证日志）是提高可靠性的关键。

### 可能的研究方向
- **动态约束生成**：目前的约束是静态生成的，未来可以研究在执行过程中动态调整约束。
- **多模态诊断**：扩展到处理包含图像、音频的多模态 Agent 轨迹诊断。
- **自我修复闭环**：诊断出错误后，如何自动生成修复代码或 Prompt 并重新执行。

## 研究最佳实践

## 最佳实践指南

### 实践 1：构建细粒度的执行轨迹追踪系统

**说明**：
AgentRx 的核心在于利用执行轨迹来诊断失败。仅仅记录 Agent 的最终输出是不够的，必须完整记录每一步的中间状态、工具调用、参数传递以及环境反馈。这相当于为 AI Agent 建立一套“黑匣子”系统，以便在任务失败时进行回溯分析。

**实施步骤**:
1. 定义标准化的日志数据结构，包含时间戳、动作类型、输入参数、返回结果和错误代码。
2. 在 Agent 的每个决策点和工具调用接口处植入自动记录逻辑。
3. 确保日志能够关联具体的任务 ID 和会话上下文，以便独立分析每次执行。

**注意事项**:
- 避免记录敏感的个人身份信息（PII）或敏感密钥，需要对日志数据进行脱敏处理。
- 注意日志存储的成本，对于高频 Agent，应实施日志轮转或仅保留失败任务的完整轨迹。

---

### 实践 2：基于轨迹切片的根因分析

**说明**：
当 Agent 失败时，不应笼统地归因为“模型幻觉”或“工具错误”。应参考 AgentRx 的诊断方法，将长轨迹切分为原子步骤，逐一验证每个步骤的正确性。区分是规划阶段的错误、工具选型的错误，还是参数传递的错误。

**实施步骤**:
1. 建立自动化脚本，将执行轨迹解析为可视化流程图。
2. 对比成功案例与失败案例的轨迹分支，定位轨迹分叉的节点。
3. 针对失败节点进行单元测试，复现该特定步骤的输入输出条件。

**注意事项**:
- 轨迹切分粒度要适中，过细会导致分析噪音过大，过粗可能掩盖具体错误。
- 重点关注“循环未终止”或“重试次数耗尽”等异常模式。

---

### 实践 3：实施分层反馈与反思机制

**说明**：
基于 AgentRx 的诊断结果，建立分层反馈机制。不仅要在任务失败时进行反思，还要在执行过程中的关键节点设置“检查点”。如果监测到轨迹偏离预期（如连续出现工具调用错误），应触发反思机制强制 Agent 重新规划。

**实施步骤**:
1. 设计一个“评估器”组件，专门用于监控当前轨迹状态与目标的距离。
2. 定义触发反思的条件（例如：连续 N 步输出无效、工具返回异常、或置信度分数低于阈值）。
3. 将历史失败案例的修正方案注入到 Prompt 的上下文中，指导 Agent 进行自我修正。

**注意事项**:
- 反思机制会增加 Token 消耗和延迟，需要设置合理的超时和预算限制。
- 防止陷入“反思循环”，即 Agent 在错误的方向上不断反思却无法推进。

---

### 实践 4：建立工具调用的验证与预处理流程

**说明**：
许多 Agent 失败源于工具调用参数格式错误或上下文缺失。最佳实践要求在 Agent 调用外部工具（如 API、数据库）之前，增加一层验证逻辑，确保生成的参数符合工具的 Schema 定义。

**实施步骤**:
1. 维护严格的工具 Schema 定义，并利用 Pydantic 或类似库进行结构化验证。
2. 在 Agent 生成工具调用参数后，先通过验证器检查，若不通过则直接反馈错误信息给 Agent 而不执行实际调用。
3. 对于复杂的工具，提供“示例调用”作为少样本提示，减少格式错误。

**注意事项**:
- 验证错误信息必须清晰明确，指出具体哪个字段不符合要求，以便 LLM 能够理解并修正。
- 定期更新工具定义文档，确保 Agent 的知识库与实际 API 版本同步。

### 实践 5：利用合成数据进行针对性微调

**说明**：
通过 AgentRx 诊断出的常见失败模式（如特定的推理错误或工具使用误区），可以生成合成数据。利用这些“困难样本”对 Agent 模型进行微调，从概率上提高模型处理特定复杂场景的能力。

**实施步骤**:
1. 从历史日志中提取典型的失败轨迹。
2. 人工或自动修正这些轨迹，生成“正确的执行路径”作为训练样本。
3. 使用监督微调（SFT）技术，训练模型识别并避免类似的错误模式。

**注意事项**:
- 确保合成数据的多样性和质量，防止模型过拟合于特定的修正模式。
- 微调后必须进行回归测试，确保模型在修正旧错误的同时没有引入新错误或降低通用能力。

除了传统的任务成功率（SR），还需要引入基于轨迹的细粒度指标。这有助于量化 Agent 在执行过程中的稳定性，并符合 AgentRx 强调的从轨迹中诊断问题的理念。

1. 定义“轨迹效率”指标，例如：完成任务的平均步数、Token 消耗量。

## 学习要点

- AgentRx 提出了一种基于因果干预的自动诊断框架，能够从执行轨迹中识别并定位导致 AI 智能体失败的特定错误组件（如规划、记忆或工具使用）。
- 该方法通过“反事实推理”技术，在不实际重新运行智能体的情况下，模拟修正特定组件后的结果，从而高效验证故障假设。
- 研究发现，智能体在复杂任务中的失败往往源于多个组件的级联错误，而非单一节点的失误，这突显了全局追踪的必要性。
- AgentRx 引入了一种细粒度的轨迹分析机制，能够区分“执行错误”（操作失败）与“决策错误”（判断失误），提供更精准的归因分析。
- 该框架显著降低了调试成本，相比传统的试错法或人工检查，能更快速地收敛至根本原因，提升了智能体的迭代优化效率。
- 通过对失败模式的系统性分类，该研究为构建更具鲁棒性和自愈能力的 AI 智能体架构提供了理论依据与实践指导。

## 常见问题


### 1: AgentRx 是什么，它主要解决什么问题？

1: AgentRx 是什么，它主要解决什么问题？

**A**: AgentRx 是一个旨在诊断 AI Agent（人工智能代理）失败原因的框架或工具。根据其标题 "Diagnosing AI Agent Failures from Execution Trajectories"（从执行轨迹中诊断 AI Agent 的失败），它主要解决的是当自主智能体在执行复杂任务失败时，人类难以理解具体失败原因的问题。

传统的 AI Agent 通常是一个“黑盒”，我们只能看到输入和最终的结果（成功或失败）。AgentRx 通过分析 Agent 的**执行轨迹**——即 Agent 在完成任务过程中采取的一系列行动、观察到的中间状态以及产生的思维链——来定位和解释导致失败的具体环节。这有助于开发者和研究人员调试 Agent，提高其可靠性和性能。

---



### 2: 什么是“执行轨迹”，为什么它对诊断 Agent 失败很重要？

2: 什么是“执行轨迹”，为什么它对诊断 Agent 失败很重要？

**A**: **执行轨迹**是指 AI Agent 在执行任务过程中按时间顺序记录的完整历史记录。这通常包括：
1.  **行动**：Agent 调用了哪些工具（例如搜索引擎、代码解释器、API）。
2.  **观察**：工具返回的结果或环境反馈。
3.  **思考**：Agent 在采取行动前的内部推理过程（如 Chain of Thought）。
4.  **环境状态**：执行过程中的上下文变化。

它对诊断至关重要，因为 Agent 的失败往往不是由于最终一步的错误，而是源于中间某一步的逻辑偏差、工具误用或对环境的错误理解。通过分析轨迹，我们可以像调试程序一样，回溯到失败发生的具体节点，而不是仅仅通过猜测来修复模型。

---



### 3: AgentRx 与传统的 LLM 调试或评估方法有什么区别？

3: AgentRx 与传统的 LLM 调试或评估方法有什么区别？

**A**: 传统的评估方法通常侧重于**端到端的指标**，例如最终答案的准确率、通过率或 BLEU/ROUGE 分数。这些方法虽然能告诉开发者 Agent “失败了”，但无法解释“为什么失败”。

AgentRx 的区别在于其**归因能力**：
*   **粒度更细**：它不把任务看作一个整体，而是将其分解为子任务或具体的执行步骤。
*   **因果关系**：它试图建立早期步骤的错误与最终失败之间的因果联系，而不是仅仅进行相关性分析。
*   **针对性修复**：传统方法可能暗示需要微调整个模型，而 AgentRx 可能指出只是某个特定的工具调用逻辑有缺陷，从而允许进行更精确的工程修复或提示词优化。

---



### 4: AgentRx 是如何具体实现故障诊断的？（技术原理）

4: AgentRx 是如何具体实现故障诊断的？（技术原理）

**A**: 虽然具体实现细节取决于论文的算法设计，但基于此类诊断系统的通用原理，AgentRx 通常采用以下技术手段：
1.  **轨迹解析**：将 Agent 的执行日志结构化，提取出动作、观察和推理三元组。
2.  **反事实推理**：系统可能会模拟“如果在某一步采取了不同的行动，结果是否会不同”，以判断该步骤是否是导致失败的关键点。
3.  **模式匹配与分类**：利用预定义的失败模式（如“幻觉循环”、“工具参数错误”、“忽略约束”）或训练分类器来识别轨迹中的异常片段。
4.  **因果图构建**：构建任务执行的依赖图，分析信息流在哪个环节中断或失真。

---



### 5: 使用 AgentRx 诊断 AI Agent 失败对实际应用有什么价值？

5: 使用 AgentRx 诊断 AI Agent 失败对实际应用有什么价值？

**A**: 在实际应用中，Agent 的可靠性是落地的最大障碍之一。AgentRx 的价值体现在：
1.  **加速开发迭代**：开发者可以快速定位是提示词写得不好、工具 API 文档不清楚，还是模型推理能力不足，从而大幅缩短调试周期。
2.  **构建更安全的系统**：在金融、医疗或自动驾驶等高风险领域，仅仅知道 Agent 失败是不够的，必须知道失败是否由不可接受的风险（如数据泄露或错误的逻辑跳跃）引起。
3.  **自动化纠错**：诊断结果可以反馈给 Agent，使其具备自我反思和自我修正的能力，形成“执行-诊断-改进”的闭环。

### 6: AgentRx 能诊断所有类型的 AI Agent 吗？

6: AgentRx 能诊断所有类型的 AI Agent 吗？

**A**: 理论上，AgentRx 适用于任何**生成可读执行轨迹**的 AI Agent。这包括基于大语言模型（LLM）的 ReAct（推理+行动）Agent、规划 Agent、多模态 Agent 等。

然而，其诊断效果取决于 Agent 的**透明度**。如果一个 Agent 的内部状态是完全隐藏的，或者其决策过程完全是端到端的神经网络黑盒而不输出中间步骤，AgentRx 将难以获取足够的信息进行诊断。因此，它最适合那些设计为“思维链”或“过程透明”的 Agent 架构。

7: 该研究提到的“Execution Trajectories”数据通常从哪里获取？
