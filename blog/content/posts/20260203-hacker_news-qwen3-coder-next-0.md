import os

def batch_rename_files(directory, prefix):
    """
    批量重命名指定目录下的文件
    :param directory: 目标目录路径
    :param prefix: 新文件名前缀
    """
    for count, filename in enumerate(os.listdir(directory)):
        # 跳过目录，只处理文件
        if not os.path.isfile(os.path.join(directory, filename)):
            continue
            
        # 获取文件扩展名
        ext = os.path.splitext(filename)[1]
        # 构造新文件名
        new_name = f"{prefix}_{count+1}{ext}"
        # 重命名操作
        os.rename(
            os.path.join(directory, filename),
            os.path.join(directory, new_name)
        )
        print(f"已重命名: {filename} -> {new_name}")

# 使用示例

import requests
from time import sleep

def fetch_with_retry(url, max_retries=3, timeout=5):
    """
    带重试机制的HTTP请求函数
    :param url: 请求URL
    :param max_retries: 最大重试次数
    :param timeout: 超时时间(秒)
    :return: 响应内容或None
    """
    for attempt in range(max_retries):
        try:
            response = requests.get(url, timeout=timeout)
            response.raise_for_status()  # 检查HTTP错误
            return response.json()
        except (requests.RequestException, ValueError) as e:
            print(f"第{attempt+1}次尝试失败: {str(e)}")
            if attempt < max_retries - 1:
                sleep(2 ** attempt)  # 指数退避
    return None

# 使用示例

def process_large_file(file_path, chunk_size=1024):
    """
    分块处理大文件避免内存溢出
    :param file_path: 文件路径
    :param chunk_size: 每次读取的块大小(字节)
    """
    word_count = 0
    
    with open(file_path, 'r', encoding='utf-8') as f:
        while True:
            # 每次只读取指定大小的块
            chunk = f.read(chunk_size)
            if not chunk:
                break
                
            # 处理逻辑示例：统计单词数
            words = chunk.split()
            word_count += len(words)
            
    return word_count

# 使用示例

## 最佳实践指南

### 实践 1：利用长上下文能力进行全项目分析

**说明**: Qwen3-Coder-Next 模型通常支持较长的上下文窗口。最佳实践是充分利用这一特性，将整个代码库或相关模块的文件一次性输入模型，而非仅粘贴单个文件。这能让模型理解模块间的依赖关系、全局变量定义以及跨文件的调用链，从而生成更连贯、符合整体架构的代码。

**实施步骤**:
1. 收集相关代码文件，构建一个包含项目结构和关键代码的上下文包。
2. 在提示词中明确提供文件目录结构，以便模型理解文件间的层级关系。
3. 按照依赖顺序（如基础定义 -> 工具类 -> 业务逻辑）排列输入的代码片段。

**注意事项**: 虽然长上下文能力强，但应去除无关的注释和冗余的日志输出，以减少噪声干扰，确保模型聚焦于核心逻辑。

---

### 实践 2：结构化提示词工程

**说明**: 采用结构化的提示词格式能显著提升模型输出的准确性和可用性。对于代码生成任务，应明确指定角色、任务、输入数据、约束条件和期望的输出格式。

**实施步骤**:
1. 定义角色：例如“你是一位拥有10年经验的Python后端工程师”。
2. 明确任务：清晰描述需要实现的功能或需要修复的Bug。
3. 设定约束：指定代码风格（如PEP 8）、不允许使用的库、性能要求或安全规范。
4. 要求输出：明确要求模型只返回代码，或者包含单元测试和解释文档。

**注意事项**: 避免模糊的指令，例如“优化这段代码”，而应具体为“降低这段代码的时间复杂度并提升内存使用效率”。

---

### 实践 3：交互式调试与迭代优化

**说明**: 不要期望一次性生成完美的代码。将 Qwen3-Coder-Next 视为结对编程伙伴，当生成的代码报错或不符合预期时，将具体的错误信息和堆栈跟踪反馈给模型进行修正。

**实施步骤**:
1. 运行模型生成的代码，捕获错误信息。
2. 将错误信息、复现步骤以及相关代码片段重新输入给模型。
3. 要求模型分析错误原因并提供修正后的版本。
4. 对于逻辑错误，要求模型添加详细的注释或断言来验证逻辑。

**注意事项**: 在反馈错误时，尽量提供完整的上下文，因为模型无法“看到”你的屏幕，只能依赖你提供的文本信息。

---

### 实践 4：强制生成测试用例与文档

**说明**: 代码质量不仅在于功能实现，还在于可维护性和稳定性。强制要求模型在生成功能代码的同时生成对应的单元测试（如使用 pytest 或 JUnit）和API文档。

**实施步骤**:
1. 在提示词中添加要求：“请为上述代码编写完整的单元测试，覆盖边界条件和异常情况”。
2. 要求模型遵循测试驱动开发（TDD）的原则，先列测试用例，再写实现。
3. 要求生成 Docstring 或符合 OpenAPI 标准的接口文档。

**注意事项**: 模型生成的测试用例可能需要人工审核，确保其断言逻辑是有效的，避免形式主义的测试代码。

---

### 实践 5：跨语言代码翻译与重构

**说明**: 利用模型强大的代码理解能力进行语言迁移或遗留系统重构。当需要将代码从一种语言（如 Java）转换为另一种语言（如 Python 或 Go）时，要求模型保留原有的业务逻辑，同时利用目标语言的特性进行优化。

**实施步骤**:
1. 提供源语言代码，并明确说明目标语言版本。
2. 指示模型：“请将此代码转换为 idiomatic（地道的）Python 代码，利用其列表推导式等特性”。
3. 要求模型对比新旧实现，列出重构后的改进点（如可读性提升、性能变化）。

**注意事项**: 跨语言转换时需特别注意标准库的差异和并发模型的区别（如线程与协程），人工审查转换后的并发逻辑至关重要。

---

### 实践 6：安全性审查与漏洞检测

**说明**: 在代码生成后，利用模型进行静态安全分析。要求模型扮演安全专家的角色，审查代码中是否存在 SQL 注入、XSS、硬编码密钥或未处理的敏感数据泄露风险。

**实施步骤**:
1. 将生成的代码或现有代码库输入模型。
2. 提示词：“请审查以下代码的安全漏洞，重点关注注入攻击和权限控制”。
3. 要求模型不仅指出问题，还要提供修复后的安全代码示例。

**注意事项**: 模型的安全知识基于训练数据，可能无法识别最新的 0-day 漏洞或特定业务逻辑中的权限漏洞，因此不能完全替代专业的安全审计工具。
