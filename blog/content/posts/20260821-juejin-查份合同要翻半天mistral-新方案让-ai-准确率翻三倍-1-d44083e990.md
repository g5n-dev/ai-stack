## 核心结论

传统单次检索 RAG 在复杂文档场景下准确率仅为 26.7%，Mistral 发布的 Agentic Search 方案将这一数字提升至 86%，提升幅度接近 60 个百分点。该方案的核心转变在于将检索目标从“找文档”调整为“找答案”，通过多步循环验证替代一次性检索，以构建完整证据链。这一范式转变在 FinanceBench 基准测试中得到验证，该测试包含 368 份 SEC 文件、约 53,900 页内容及 150 个需要多跳推理的复杂问题。

## 能力机制

Agentic Search 构建了一个由五个工具组成的多步检索循环：`search` 在向量索引中执行语义检索并返回候选片段；`open` 打开完整文档以获取全局上下文；`navigate` 支持在文档内部跳转，例如从目录进入具体章节；`read` 提取指定页码或段落的内容；`grep` 执行关键词匹配用于定位特定条款或数据。

这五个工具并非串行执行，而是由模型在每次推理时自主决定调用顺序和次数。模型在每一步都会评估当前信息是否足以回答问题，若信息不足则继续调用工具。完整导航循环相比仅搜索循环，Token 用量最多可降低约三分之一，原因在于多步验证使模型能够精确定位所需信息，减少了读取无关片段的开销。

## 快速开始

Mistral 官方在公告中建议根据文档规模和查询复杂度选择检索策略：当文档库规模在 1000 份以下且问题以事实查询为主时，优先使用 File Search；当文档规模超过 1000 份或问题涉及多跳推理时，再考虑 Agentic Search。Search Toolkit 提供了分层检索能力，可在 Studio 或 Vercel 等平台中配置不同的检索策略，根据场景动态切换。该工具集的环境变量配置涉及模型选择、检索深度阈值等参数，具体名称需参考官方文档。

## 适用边界

Agentic Search 的适用场景集中在文档结构复杂、关键信息分散且需要交叉验证的领域，包括监管申报文件、合同条款提取以及扫描版 PDF 处理。这类场景的共同特征是准确率优先级高于响应速度。对于追求秒级反馈的应用场景，例如客服问答或即时搜索，该方案的平均延迟 71 秒、p90 延迟 154 秒难以接受。

从成本维度考量，虽然完整循环的 Token 用量相比仅搜索循环可节省约 24% 至 34%，但绝对值仍远高于单次检索。延迟的增加意味着单位时间内查询吞吐量下降，成本结构从按 Token 计费转向按时间计费。实际部署中，建议通过复杂度分类器将问题路由至不同管道：简单问题走 Naive RAG，中等复杂度走 File Search，复杂多跳问题才启用 Agentic Search。

## 核验清单

在评估是否引入 Agentic Search 时，应逐项确认以下条件：业务场景是否涉及 SEC 文件、合同或扫描件等复杂文档；答案错误是否会产生重大影响；用户或业务流程是否能够接受数分钟的等待时间。如果这三个条件均满足，则 Agentic Search 能够填补现有检索方案在复杂文档理解上的空白；若延迟不可接受或问题以简单事实查询为主，则 Naive RAG 或 File Search 是更务实的选择。

试点阶段应建立人工复核机制，记录错误类型以优化检索策略。生产部署时应设计降级策略，当循环次数超过阈值时自动切换至单次检索并标注置信度。该方案的价值在于让 AI 从被动接收检索结果转向主动规划检索路径，其代价是响应时间增加，适用于将准确率视为硬约束、合规审查错误成本极高的场景。
