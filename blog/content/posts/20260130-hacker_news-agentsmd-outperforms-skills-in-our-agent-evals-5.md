## 评论

### 深度评价：AGENTS.md outperforms skills in our agent evals

**文章中心观点**
在构建基于 LLM 的 Agent 时，使用结构化的 `AGENTS.md`（即定义代理的目标、背景、约束和可用工具的系统提示词）比传统的“Skills”（将功能硬编码为特定函数或子流程）在任务执行的通用性和成功率上表现更好。

**支撑理由与边界分析**

1.  **上下文理解与意图对齐（事实陈述 / 作者观点）**
    *   **理由**：`AGENTS.md` 方法本质上是利用 LLM 的推理能力进行“即时规划”。通过在系统提示层提供完整的上下文和目标，模型能够自主决定何时调用工具以及如何组合工具，而不是被迫执行预定义的僵化逻辑。作者指出，这种方法减少了因 Skill 接口定义不清导致的错误调用。
    *   **边界条件（反例）**：对于确定性要求极高、且步骤固定的任务（如“调用 A 接口获取数据，原样传入 B 接口”），硬编码的 Skills 或 Workflow 在稳定性和延迟上远优于依赖 LLM 生成调用代码的 Agent。

2.  **泛化能力与维护成本（你的推断 / 作者观点）**
    *   **理由**：传统的 Skills 开发模式类似于传统的 API 开发，需要为每个特定功能编写描述、参数校验和错误处理。`AGENTS.md` 将复杂性转移到了 Prompt 层，使得 Agent 能够处理 Skills 定义范围之外的边缘情况。作者认为这降低了维护大量特定代码的负担。
    *   **边界条件（反例）**：当工具链非常庞大且复杂时（例如拥有数百个 API 的企业级 ERP 系统），单纯依赖 `AGENTS.md` 会导致上下文窗口溢出或模型注意力分散，此时经过检索增强的 Skills 定义（RAG for Functions）可能更有效。

3.  **调试的可观测性与透明度（事实陈述）**
    *   **理由**：文章暗示 `AGENTS.md` 使得 Agent 的思维链更加透明。因为代理是基于“目标”行动的，开发者可以通过阅读系统提示词来理解代理的行为逻辑，而在复杂的 Skills 编排中，控制流往往隐藏在代码逻辑深处。
    *   **边界条件（反例）**：如果 `AGENTS.md` 编写不当（例如包含模糊的指令），LLM 可能会产生幻觉或执行不可预测的操作，这种“软逻辑”错误比代码报错更难调试和复现。

**多维评价**

1.  **内容深度：**
    文章触及了 Agent 设计的核心矛盾：**代码逻辑 vs. 模型推理**。作者通过实验数据支持了“重 Prompt、轻代码”的路线。论证较为严谨，指出了 Skills 模式在处理非预期输入时的脆弱性。然而，文章未详细披露测试集的具体构成（如任务的复杂度分布、使用的模型版本），这使得结论的普适性需要打一个折扣。

2.  **实用价值：**
    对于初创团队或快速原型开发阶段，这一观点具有极高的指导意义。它建议开发者不要急于编写大量 Python 包装器，而是先优化系统提示词和上下文供给。这能显著缩短开发迭代周期。

3.  **创新性：**
    虽然类似观点在 LangChain、AutoGPT 等社区早有讨论，但该文章明确提出了 `AGENTS.md` 这一具体文件格式作为优于 Skills 的工程实践，具有一定的范式总结意义。它挑战了当前流行的“一切皆工具”的 Agent 框架设计思路。

4.  **可读性：**
    表达清晰，技术术语使用准确。文章结构紧凑，直接对比了两种方法的优劣，易于工程师理解。

5.  **行业影响：**
    这篇文章可能会推动 Agent 开发框架的演进。未来的框架可能会更倾向于支持“基于文件的配置”来驱动 Agent 行为，或者增强 Prompt 管理功能，而不是仅仅聚焦于工具调用的标准化。

6.  **争议点：**
    *   **Token 成本与延迟**：`AGENTS.md` 模式通常需要更长的 Prompt，这会导致每次推理的 Token 成本和延迟显著高于直接调用函数的 Skills 模式。文章对此似乎提及较少。
    *   **模型依赖性**：这种模式极度依赖模型本身的指令遵循和规划能力。如果使用的是较小的开源模型（如 Llama-3-8B），`AGENTS.md` 的效果可能远不如结构化的 Skills。

**实际应用建议**

1.  **混合架构策略**：不要完全废弃 Skills。建议采用“路由层”策略：对于高频、低歧义的任务（如数据查询）保留 Skills 接口；对于复杂、多变的任务使用 `AGENTS.md` 驱动的 Planner。
2.  **Prompt 工程化**：将 `AGENTS.md` 视为核心代码库，进行版本控制和 A/B 测试。明确写入“五步法”思维链或 ReAct 模式提示，以弥补模型规划能力的不足。
3.  **工具描述优化**：即使在 `AGENTS.md` 模式下，工具的描述也至关重要。确保工具描述不仅仅是参数列表，还应包含“何时使用此工具”的语义信息。

**可验证的检查方式**

1.  **边缘案例测试**：
    *   *指标*：故意给 Agent 输入一个需要组合 3 个以上工具才能解决的复杂问题，或者输入一个不在任何 Tool 描述中的干扰信息。
    *   *观察*：`AGENTS.md` 模式是否能通过拒绝回答

def dynamic_agent_tool():
    """
    模拟AGENTS.md描述的动态工具选择机制
    解决问题：根据用户输入自动选择最合适的工具（比固定技能更灵活）
    """
    class Agent:
        def __init__(self):
            # 定义可用工具（模拟AGENTS.md中的工具描述）
            self.tools = {
                "search": {"desc": "搜索实时信息", "params": ["query"]},
                "calculate": {"desc": "执行数学计算", "params": ["expression"]},
                "translate": {"desc": "多语言翻译", "params": ["text", "target_lang"]}
            }
        
        def route_request(self, user_input):
            # 简单的关键词匹配路由（实际AGENTS.md会使用更复杂的决策逻辑）

                return self.tools["search"]

def context_aware_response():

    解决问题：根据对话历史做出更智能的响应

## 最佳实践指南

### 实践 1：优先采用 AGENTS.md 配置范式

**说明**: 根据评估结果，使用 AGENTS.md 文件定义 Agent 的行为比传统的硬编码“技能”表现更优。AGENTS.md 允许大语言模型（LLM）在运行时动态理解和生成执行逻辑，而技能通常依赖于预定义的代码结构。通过自然语言描述 Agent 的角色、目标和约束，可以更灵活地处理复杂任务。

**实施步骤**:
1. 创建一个标准的 AGENTS.md 文件，置于项目根目录或配置文件夹中。
2. 在文件头部清晰定义 Agent 的角色设定和主要目标。
3. 使用自然语言详细描述 Agent 应如何响应不同类型的用户请求。

**注意事项**: 确保文件格式清晰，避免过于复杂的嵌套结构，以便 LLM 能够准确解析。

---

### 实践 2：构建结构化的上下文描述

**说明**: AGENTS.md 的核心优势在于上下文的质量。评估显示，结构化且信息丰富的上下文能显著提升 Agent 的推理能力。不仅仅是列出指令，还需要包含背景知识、业务规则和期望的输出格式。

**实施步骤**:
1. 在 AGENTS.md 中划分明确的章节，如“角色”、“能力”、“约束”和“工作流”。
2. 提供具体的示例来说明预期的行为，即“少样本提示”。
3. 明确列出 Agent 不应该做什么（负面约束）。

**注意事项**: 保持上下文的连贯性，避免指令之间的逻辑冲突。

---

### 实践 3：实施动态工具调用策略

**说明**: 相比于将工具绑定在特定的硬编码技能中，AGENTS.md 允许 Agent 根据当前情境动态选择工具。这种灵活性使得 Agent 能够处理技能设计者未曾预见的场景组合。

**实施步骤**:
1. 在 AGENTS.md 中维护一个可用工具列表及其描述。
2. 指导 Agent 在执行任务前评估需要哪些工具，而非盲目调用。
3. 允许 Agent 在工具调用失败或结果不理想时进行自我修正和重试。

**注意事项**: 工具描述必须极其准确，否则 Agent 可能会产生幻觉或误用工具。

---

### 实践 4：建立迭代式的提示词优化流程

**说明**: 既然 AGENTS.md 本质上是一种高级提示词工程，就需要建立一套持续的优化机制。通过评估结果反馈，不断调整 AGENTS.md 中的措辞和结构，可以持续提升 Agent 性能。

**实施步骤**:
1. 建立 Agent 评估基准，记录 AGENTS.md 在特定任务上的表现。
2. 当 Agent 表现不佳时，定位 AGENTS.md 中导致歧义或错误指令的具体段落。
3. 修改描述并重新测试，对比修改前后的评估分数。

**注意事项**: 每次只修改一个变量，以便准确判断改动对性能的影响。

---

### 实践 5：强化错误处理与边界条件管理

**说明**: 传统的技能模式通常在代码层面处理异常，而 AGENTS.md 模式需要通过自然语言来指导 Agent 如何应对边界情况和错误。明确的错误处理指令是防止 Agent 陷入死循环或产生幻觉的关键。

**实施步骤**:
1. 在 AGENTS.md 中增加“故障排除”或“异常处理”章节。
2. 定义当 Agent 无法获取足够信息时的标准询问话术。
3. 设定超时或最大迭代次数的限制规则。

**注意事项**: 定期审查 Agent 的日志，找出未被覆盖的边界条件并补充到文档中。

---

### 实践 6：分离领域知识与推理逻辑

**说明**: 最佳的 AGENTS.md 实践是将静态的领域知识（如产品信息、API 文档摘要）与动态的推理逻辑（如思考链、决策步骤）分离开来。这有助于减少上下文窗口的占用，并提高 LLM 的注意力效率。

**实施步骤**:
1. 将不常变动的知识库剥离到单独的文档或向量数据库中，通过引用方式接入。
2. 在 AGENTS.md 中专注于定义“如何思考”和“如何检索知识”。
3. 使用清晰的标记或语法来区分知识引用和执行指令。

**注意事项**: 确保引用机制与 Agent 的检索增强生成（RAG）系统无缝集成。
