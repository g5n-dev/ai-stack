KCP is a fast and reliable ARQ (Automatic Repeat reQuest) protocol that trades 10-20% additional bandwidth for 30-40% lower average latency and 3x lower maximum latency compared to TCP. It is designed for real-time applications where responsiveness is more critical than bandwidth efficiency.

This page introduces KCP’s purpose, design philosophy, and key characteristics. For detailed protocol mechanisms, see Protocol Fundamentals. For specific features, see Key Features. For API documentation, see API Reference.

Sources: README.md1-23 README.en.md1-21

What is KCP?

KCP is implemented as a pure algorithm with no system calls or dependencies. The entire protocol consists of two source files—ikcp.h1-388 and ikcp.c1-1115—totaling approximately 3,000 lines of code. This minimal footprint makes it trivial to integrate into existing protocol stacks.

Pure Algorithm Design

Title: KCP’s Transport-Agnostic Architecture

KCP does not perform I/O operations. The user must:

  1. Provide an output callback function to send packets (set in ikcpcb->output)
  2. Call ikcp_input() when packets arrive from the network
  3. Call ikcp_update() periodically with the current time in milliseconds
  4. Implement the underlying transport layer (typically UDP)

This design allows KCP to run on any platform and integrate with any event loop or networking framework.

Design Philosophy

KCP is optimized for flow velocity (latency) rather than flow volume (throughput). The design philosophy prioritizes minimizing the time for individual packets to travel from sender to receiver, accepting higher bandwidth usage as a trade-off.

KCP achieves lower latency through:

  • Smaller RTO multiplier: 1.5x instead of 2x (ikcp.c699-711)
  • Selective retransmission instead of full retransmission
  • Fast retransmit after 2 ACK skips (configurable)
  • Optional immediate ACK without delay
  • Hybrid UNA+ACK acknowledgment system
  • Optional non-yielding flow control

When to Use KCP

Ideal Use Cases

KCP is designed for real-time applications where low latency is critical:

  • Online gaming : Player actions and game state synchronization
  • Voice/Video calls : Real-time audio and video streaming (VoIP)
  • Remote desktop : Low-latency remote control systems
  • Network tunneling : VPN and proxy services (e.g., kcptun, v2ray)
  • Live streaming : Interactive broadcast with minimal delay
  • Financial trading : Time-sensitive data transmission

When NOT to Use KCP

KCP may not be appropriate for:

  • Bulk file transfers : TCP’s higher bandwidth efficiency is preferable
  • Background syncing : Latency is not critical
  • Shared networks with strict fairness requirements : KCP’s aggressive retransmission can use more bandwidth
  • Battery-constrained devices : More frequent retransmissions increase power usage

Network Conditions

KCP excels in challenging network conditions:

  • High packet loss (3G/4G/WiFi networks with 5-15% loss)
  • Variable latency (jitter)
  • Network congestion

In ideal network conditions (0% loss, stable latency), KCP and TCP perform similarly. The benefits become apparent under realistic Internet conditions.

Core Architecture

Title: KCP Core Data Structures and Queue System

Key Structures

ikcpcb (ikcp.h272-340): The control block managing a single KCP connection. Contains:

  • conv: Conversation ID to match with remote peer
  • mtu/mss: Maximum transmission unit and segment size
  • Four queues: snd_queue, snd_buf, rcv_queue, rcv_buf
  • Sequence numbers: snd_una, snd_nxt, rcv_nxt
  • Window control: snd_wnd, rcv_wnd, cwnd, ssthresh
  • Timing: rx_srtt, rx_rttval, rx_rto, rx_minrto
  • output: Callback function pointer for sending packets

IKCPSEG (ikcp.h239-255): Represents a protocol segment. Contains:

  • Header: conv, cmd, frg, wnd, ts, sn, una, len
  • Retransmission state: resendts, rto, fastack, xmit
  • Payload: data array

Queue System : Four intrusive linked lists (IQUEUEHEAD) manage packet flow:

  1. snd_queue : Application data waiting to enter the send window
  2. snd_buf : Sent segments awaiting acknowledgment (retransmission buffer)
  3. rcv_buf : Received out-of-order segments awaiting reordering
  4. rcv_queue : In-order segments ready for the application to read

1. 技术架构深度剖析 🏗️

核心架构模式

KCP 的架构设计遵循 “算法库” 模式，而非传统的 “网络协议栈” 模式。

  • 技术栈：纯 C (C99)。无系统调用，无外部依赖。
  • 架构模式：用户态协议栈。它完全运行在应用层，将 TCP 的拥塞控制和流量控制逻辑重写并优化。
  • 设计哲学：可插拔与无状态。KCP 将网络 I/O 与逻辑处理分离。用户必须自己负责数据的收发，KCP 只负责处理这份数据。这种设计使得它可以运行在 UDP、WebSocket 甚至自定义的帧传输协议之上。

核心模块设计

KCP 的内部实现虽然简洁，但精密模仿并改进了 TCP 的核心机制：

  1. 发送/接收缓冲区：管理待发送和已接收的数据段。
  2. RTO 计算器：动态计算超时重传时间。
  3. ACK 列表：处理选择性重传（SACK）和快速重传。
  4. 拥塞窗口：控制发送速率，但比 TCP 更激进。

技术亮点与创新点

  • RTO 退避算法优化：TCP 的超时重传退避通常是 2 秒起步，这会瞬间卡死游戏。KCP 的 RTO 下限设为 30ms，并以此进行非线性的动态调整，保证了在丢包时的快速反应。
  • 前向纠错（FEC）支持：虽然核心 KCP 不包含 FEC，但其架构设计允许在数据包中混入冗余包，这是 TCP 难以做到的。

2. 核心功能详细解读 🛠️

主要功能与场景

  • 核心功能：在不可靠的 UDP 连接上提供类似 TCP 的可靠、有序交付，但延迟显著低于 TCP。
  • 适用场景：
    • MOBA/FPS 游戏战斗数据：对毫秒级延迟极其敏感。
    • 实时互动直播：主播与观众的低延迟互动。
    • 远程控制/云桌面：鼠标移动的即时反馈感。
    • 物联网控制：弱网环境下的指令下发。

解决的关键问题

TCP 的天然缺陷：TCP 协议栈位于操作系统内核中，其设计初衷是公平性和吞吐量，而非低延迟。一旦发生丢包，TCP 的拥塞控制算法会导致窗口骤减，且 RTO 最小值通常为 200ms（Linux 默认），这在实时应用中是不可接受的。KCP 解决了"丢包时恢复速度慢"和"延迟累积"的问题。

3. 技术实现细节 ⚙️

关键算法方案

KCP 之所以比 TCP 快，是因为它打破了 TCP 的几条"铁律"，并在以下四个方面进行了重写：

  1. RTO 不翻倍：

    • TCP：超时重传时间 RTO 翻倍，导致长尾延迟。
    • KCP：超时重传 RTO 不翻倍，调整为 1.5 倍或固定步进，保证恢复速度。

  2. 选择性重传 (SACK)：

    • TCP：累积确认，丢包时可能重传已接收数据。
    • KCP：使用 sn (序列号) 和 una (未确认序号) 机制，配合 ACK 列表，告诉发送方哪个包丢了，只重传丢失的包。

  3. 非延迟ACK：

    • TCP：通常捎带 ACK 或延迟 40ms 发送 ACK，以减少包量。
    • KCP：收到数据立即发送 ACK。这虽然增加了 20% 的带宽，但显著降低了延迟。

  4. UNCORK (取消 Nagle 算法)：

    • TCP：Nagle 算法会缓冲小数据包。
    • KCP：完全取消 Nagle 算法，数据写入即刻发送。

代码结构与设计模式

  • 面向对象 (C风格)：ikcp.h 中定义了结构体 IKCPCB (KCP Control Block)，这是一个句柄。所有操作函数如 ikcp_update, ikcp_send, ikcp_input 都接受该句柄作为参数。
  • 接口隔离：
    • ikcp_output：回调函数，由用户定义，用于将打包好的 KCP 数据包发送出去。
    • ikcp_input：用户收到网络数据后，喂给 KCP。
    • ikcp_update：时钟驱动，用户需在主循环中定期调用以触发超时和窗口更新。

性能优化难点

KCP 的最大难点在于 时钟管理。由于它是用户态协议，它依赖应用层传入当前时间戳（current_ms）。如果应用层调用 ikcp_update 的频率过低，会导致协议响应迟钝；频率过高，则消耗 CPU。通常建议配合定时器每 10ms~20ms 调用一次 update。

✅ 最适合的场景

  • 局域网对战匹配系统：虽然延迟本身低，但需要防止偶发的丢包导致卡顿。
  • 跨洋/弱网环境下的关键指令传输：例如远程手术指令、工业控制，此时带宽不是问题，延迟才是大敌。
  • 手机游戏对战：3G/4G 网络抖动大，TCP 往往会死锁，KCP 能维持流畅。

❌ 不适合的场景

  • 大文件下载：KCP 牺牲带宽换取延迟。在下载 1GB 文件时，那额外的 20% 带宽浪费是非常昂贵的，且此时延迟并不重要。请使用 TCP 或 HTTP。
  • 极度受限的单片机环境：虽然代码量小，但 KCP 需要一定的 RAM 来维护发送/接收窗口，且对 CPU 定时器有要求。

集成方式与注意事项

  1. MTU 问题：KCP 默认 MTU 为 1400（避免 IP 分片）。如果在应用层再封装一层协议（如加密），务必减小 KCP 的 mtu 设置，否则底层 UDP 会进行分片，导致丢包率指数级上升。
  2. 防拷贝优化：ikcp_send 会拷贝数据。对于高频数据（如每秒 60 次的坐标），建议使用 Zero Copy 技术或直接发送指针，减少内存复制开销。

5. 发展趋势展望 🔮

  • QUIC 的挤压：随着 HTTP/3 (QUIC) 的普及，Google 的 QUIC 协议不仅解决了 TCP 的队头阻塞，还集成了 TLS 1.3。在通用 Web 领域，KCP 将逐渐被 QUIC 取代。
  • 游戏行业的标准：尽管 QUIC 很强，但 KCP 更轻量、更可控。游戏引擎（如 Unreal, Unity）通常集成 KCP 或其变种（如 ENet 的某些设计思路）作为内部 RPC 通道。
  • WebRTC 数据通道：WebRTC 也采用了类似 KCP 的理念（基于 SRTP 的可靠传输），KCP 的思想正在融入现代 Web 标准。
  • FEC 融合：未来的 KCP 变种可能会更深度地结合前向纠错码，在弱网下通过数学计算恢复数据，而不是请求重传，进一步降低延迟。

⚙️ 参数调优三板斧

KCP 的强大在于其可配置性。根据场景调整以下三个参数是使用的关键：

  1. nodelay (无延迟模式)：

    • 设置：ikcp_nodelay(kcp, 1, 20, 2, 1)
    • 含义：不延迟发送 ACK；interval 更新间隔设为 20ms；fastresend 为 2（触发两次 ACK 就重传）。
    • 适用：FPS 游戏，极速响应。

  2. wnd_size (窗口大小)：

    • 默认是 32。如果是宽带环境，建议调大到 128 或 256，以填满带宽时延积（BDP）管道。
    • 适用：需要高速
