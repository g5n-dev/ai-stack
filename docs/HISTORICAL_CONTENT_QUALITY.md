# 历史文章质量修复报告

本报告记录 2026-07-15 对 AI Stack 历史文章库执行的确定性质量治理。目标不是把所有页面“写长”，而是把可核验正文、重复路由、不可恢复生成稿和短来源卡片分开处理，避免用看似完整的文本掩盖来源缺失。

## 修复前盘点

| 指标 | 数量 | 含义 |
| --- | ---: | --- |
| Markdown 文件 | 6,700 | 修复前物理文章文件 |
| 高置信异常文件 | 2,481 | 命中提示词/思维泄漏、正文缺失、结构损坏或仅标题推演 |
| 唯一来源身份 | 2,366 | 按共享 canonical URL 规则归并 |
| 重复来源组 | 1,150 | 同一来源存在多个本地副本 |
| 冗余文件 | 4,334 | 可由稳定路由与 aliases 替代的重复文件 |
| 最终可恢复身份 | 1,987 | 至少有一个未命中完整质量门的副本 |
| 无可信副本身份 | 379 | 不能在不编造内容的前提下恢复 |

异常原因允许重叠。最终计划识别到 `prompt_context_leak` 2,053 个、`missing_source_content` 308 个、未闭合代码围栏 222 个、Unicode `�` 编码损坏 182 个、`title_only_generation` 95 个，以及半句终止、翻译助手元话术、来源缺失后推演、索要原文和 `</think>` / `Understand the User's Request` 模型思维泄漏。检测器不把篇幅短、观点不同或中文分词少直接判为异常。

同时确认了一个更重要的事实：历史 Post 没有保存来源快照和抓取完整性字段，正文很长也不能证明拿到过原文全文。因此修复后把“Post 结构完整”和“来源全文可证明”分开标记，禁止把前者包装成后者。

## 确定性处理规则

1. 以规范化外链作为文章身份，保留最早发布日期对应的稳定站内路由。
2. 同一身份存在可信副本时，只从可信候选中选择正文；按结构完整度排序，路径作为最终稳定排序键。
3. 被删除的重复路由写入 canonical 页 `aliases`，并同步改写站内 `relref`。
4. 所有候选都异常时，保留透明归档页和原始来源入口，删除不可核验正文，不生成替代事实。
5. 透明归档页清空 tags、categories、scenarios，并从文章列表、Pagefind 和知识图谱排除。
6. 所有 active 文章统一使用共享 URL 身份规则和版本化标签别名，标签稳定去重且最多 8 个。
7. 只有满足固定来源、有效外链、标准结构、无 fatal reason 的 6 个短 Hacker News 卡片标记为 `legacy_source_brief` / Tier C；它们与具有现代来源快照契约的 `source_brief` 严格区分。
8. 其余通过结构门的历史正文标记为 `legacy_analysis` / LEGACY：可以阅读和检索，但页面明确提示“来源快照缺失，不等同于原文全文”。
9. 新生成链先写不可变来源契约；metadata、摘要或 RSS 节选只能生成确定性 Tier C 来源卡，不再调用模型扩写长文。

## 执行与回滚

迁移使用 `reviewed_git_repository` 安全配置，并绑定执行时精确 Git HEAD、确定性计划 SHA-256、显式变更上限与唯一备份 ID。最终计划覆盖全部 2,366 个 canonical 身份：1,046 个同源合并、941 个元数据/来源状态规范化、379 个透明归档；共 6,700 个文件操作（原子写入 2,366、删除冗余副本 4,334）。

首轮迁移后又对结构 warning 做固定点清理：789 篇文章共删除 1,881 个没有正文的空壳标题；正常的“父标题 → 子章节”容器保持不变。该步骤只删除无内容标题，不生成、补写或改写任何事实。

执行前要求 clean `codex/` 分支、精确 HEAD、精确计划摘要、显式变更上限和独立备份 ID。所有受影响文件在写入前完整备份；每个写入和删除都校验修复前 SHA-256，并在异常时回滚。

执行前还必须校验备份目录不存在，执行后校验 `before/` 中的文件数与受影响路径数一致，且 `plan.json` 与 `receipt.json` 绑定同一个计划摘要。如果进程在自动回滚边界之外被终止，立即停止后续构建，按计划绑定的 Git HEAD 恢复 `blog/content/posts` ，再对备份中每个文件重算 SHA-256。备份目录不完整、没有 receipt 或摘要不一致时，不得复用同一 backup ID；必须恢复 clean HEAD、重新生成计划并使用新 ID。

幂等验收不依赖 receipt 的“已执行”标记，而是在修复后重新 dry-run：`planned_changes` 必须为 0、`issues` 必须为空。
