# 历史文章质量治理与来源证据恢复

本文记录 AI Stack 在 2026-07-15 至 2026-07-18 完成的两阶段历史数据治理。目标不是把页面机械地“写长”，而是区分可核验来源证据、证据支持转写、重复路由和证据不足记录，避免把模型补写或旧长文误称为来源全文。

## 阶段一：确定性去重与异常正文隔离

第一阶段按规范化外链归并同源记录，保留稳定站内路由，并隔离提示词泄漏、模型思维过程、正文缺失、结构损坏和仅标题推演等高置信异常。处理规则如下：

1. 同一来源存在多个本地副本时，从通过结构门的候选中确定性选择规范记录。
2. 被删除的重复路由写入规范页 `aliases`，同步修复站内引用。
3. 所有候选都缺少可信证据时，保留透明归档页与原始来源入口，删除不可核验正文。
4. 透明归档页从文章列表、Pagefind、趋势与知识图谱排除，但原站内路由仍可直达。
5. 标签使用共享别名规则稳定去重；篇幅短、观点不同或中文分词少本身不构成异常。

第一阶段结束时，历史正文仍有大量 `legacy_analysis`。这个状态只说明旧正文通过结构检查，不证明曾完整抓取原文，因此不能作为最终来源质量结论。

## 阶段二：来源证据恢复

第二阶段对 2,365 条待恢复记录逐条调用来源专属适配器，并把抓取、发布和安全校验分离。输入清单包含 2,422 条记录，其中 2,365 条需要来源恢复、56 条已有来源快报、1 条已有证据支持转写。

抓取成功不等于允许发布。8 条已抓取记录未通过发布前敏感内容或结构校验，因此本轮实际写入 2,089 条新来源快报，并将 268 条抓取失败和 8 条校验失败记录转为透明归档。

### 公开内容边界

- ArXiv 发布官方摘要；GitHub Trending 与 Hacker News 发布可核验元数据。
- 博客与掘金只发布最多 800 个 Unicode 字符的有界节选，并明确展示截断提示与原始来源入口。
- 最终 2,138 条来源快报由 571 条摘要、799 条元数据和 768 条节选组成。
- `source_support: 1.0` 只表示公开展示字段被记录的证据覆盖，不代表已获得或发布原文全文。
- 旧的不可核验长文不会因为篇幅更长而优先于来源证据，也不会被模型补写成“完整文章”。

### 证据与安全边界

每条公开快报保存来源身份、抓取模式、展示载荷摘要与来源快照摘要。博客和掘金还记录原始抓取字符数、原始抓取 SHA-256 与公开节选字符数，并将这些字段纳入来源契约校验。

SHA-256 在这里只用于内容摘要、一致性校验和哈希绑定；它不是数字签名，不提供来源身份认证、不可抵赖性或可信时间证明。

发布前会扫描标题、链接、公开节选和来源专属元数据中的高置信凭据形态、邮箱、本机路径与私有网络地址。命中时 fail closed，只记录稳定原因码，不记录命中值。动态内容继续经过 Markdown 与渲染结果安全验证。

原始抓取审计、事务计划、receipt 与写前备份保存在仓库外的权限受限文件中。Git 仓库只提交有界公开内容与脱敏汇总，不提交原始载荷、绝对本地路径或备份正文。

## 可复核性与发布门禁

来源恢复事务绑定输入清单摘要、预期 Git HEAD、确定性计划摘要、显式变更上限和唯一备份 ID。写入前备份每个目标并校验旧文件 SHA-256，异常时回滚。随后执行独立的重复记录合并事务。

仓库提交的脱敏审计汇总位于 `config/historical-rehydration-audit-v1.json`；原始抓取与逐条 receipt 不进入 Git。最终清单摘要为：

```text
sha256:0ce519df14d344050a8dcd71d1e964e3dc121a9dd7178e43bc75b33fb2b3477a
```

验收不依赖 receipt 中的“已执行”状态，而是在变更后重新运行固定点检查：`planned_changes` 必须为 0、`issues` 必须为空。CI 还要求：

- 质量清单重建后零差异，待恢复、quarantine 和结构 warning 均为 0；
- 来源契约、历史抓取、发布边界、XSS 与敏感内容回归测试通过；
- 图谱和趋势资产从 2,140 条 active Post 确定性重建并通过哈希校验；
- Hugo、Pagefind 与公开渲染验证通过，透明归档可直达但不进入列表、搜索、趋势和图谱。
