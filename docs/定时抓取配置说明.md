# 定时抓取与数据刷新

AI Stack 的生产刷新由 [`.github/workflows/deploy.yml`](../.github/workflows/deploy.yml) 执行，工作流名称为 **Build and Deploy**。

## 调度

```yaml
on:
  schedule:
    - cron: "17 * * * *"
  workflow_dispatch:
    inputs:
      refresh_data:
        type: boolean
        default: true
  push:
    branches:
      - main
```

- cron 使用 UTC，但 `17 * * * *` 表示每个小时的第 17 分钟，与时区无关。
- 选择第 17 分钟是为了避开整点拥堵，不能保证秒级准时。
- GitHub 可能延迟计划任务；新鲜度监控以数据生成时间判断，不依赖预期启动时刻。

## push 与 schedule 的差异

| 触发 | `AI_STACK_REFRESH_DATA` | 行为 |
| --- | --- | --- |
| Push 到 `main` | false | 验证并发布已经提交的静态快照 |
| schedule | true | 采集、生成、重建派生资产并发布 |
| workflow_dispatch + `refresh_data=true` | true | 手动完整刷新 |
| workflow_dispatch + `refresh_data=false` | false | 手动快速发布 |

生产生成机器人提交带有 `[skip ci]`，且 push job 排除 `github-actions[bot]`，避免生成提交再次递归运行部署。

## 权限隔离的完整刷新

所有触发都经过同一生产 DAG：

```text
refresh → validate → persist → build → deploy → production-verify → notify
```

1. `refresh` 在精确 `main` base SHA 上采集/整理；完整刷新时可读取模型密钥，但仓库权限只有 read。
2. `validate` 复验 handoff，在无模型密钥和无写权环境中按 `lineage → content quality → trends → graph` 重建并校验派生数据。
3. `persist` 不持有模型密钥，只能以 exact-base CAS 写入文章和数据白名单；冲突即失败。
4. `build` 检出 persisted SHA，重建固定点、CSS、Hugo、Pagefind 和结果 catalog，并创建受公开树门禁保护的 release marker。
5. `deploy` 是唯一拥有 Pages 写权的 job。
6. `production-verify` 核对线上精确 SHA、release ID 和关键资源；成功后保留 90 天生产验证回执。
7. `notify` 只在生产验证后通知搜索索引。

## 来源预算与去重

来源开关、超时和单轮预算位于 [`config/sources.yaml`](../config/sources.yaml)，CI 档位位于 [`runtime_profile.py`](../runtime_profile.py)。

X/Twitter 的 `accounts` 是本地完整订阅列表；生产 CI 只抓 `priority_accounts`。人物级 `account_profiles` 可开启回复页并绑定确定性的信号监控，当前 `thsottiaux` 用于区分 Codex/ChatGPT Work 的 hard reset、banked reset、临时额度提升、策略变化与弱前兆。X 匿名页不可见时使用 `fallback_feed_url`；该入口必须通过 HTTPS、主机/路径白名单、响应大小、账号一致性、时间新鲜度和字段形状校验，记录仍以原始 X 帖为外链并把镜像地址写入来源谱系。仅来自独立镜像的重置信号统一标记为“待核验”，不得触发“已重置”通知；页面同时展示镜像入口和外部核验状态。

流水线先用规范化外链对整个历史归档去重，再用有界的原始来源证据建立跨 URL 事件谱系：

- 已归档 URL 不会再次消耗模型预算。
- 同一轮多来源重复项会合并。
- 本站最早观测、疑似源头、转载、衍生和同事件观察保留各自来源；不把生成正文当作原创性证据，也不声称绝对原创。
- 趋势按稳定 `event_id` 的 `unique_events` 计数，只合并 allowlist 认可的 `same_event`，并把重复来源记录为 `redundant_observations`。
- “本轮没有新增文章”不等于失败，可能只是全部候选已存在。

判断异常时同时查看候选数、去重数、抓取错误、质量拒绝和最终新增数。

## 手动运行

GitHub 页面：

1. 打开 Actions。
2. 选择 **Build and Deploy**。
3. 点击 **Run workflow**。
4. 选择是否刷新数据。

GitHub CLI：

```bash
gh workflow run deploy.yml \
  --repo g5n-dev/ai-stack \
  -f refresh_data=true
```

模型密钥只配置在 GitHub Actions Secrets，不通过命令行参数传递。

## 本地模拟

```bash
git clone https://github.com/g5n-dev/ai-stack.git
cd ai-stack
bash scripts/setup.sh
nano .env
bash scripts/run_local.sh --serve
```

只检查前置条件：

```bash
python3 scripts/preflight.py --require-hugo
```

## 并发与写入安全

部署工作流使用：

```yaml
concurrency:
  group: build-and-deploy-main
  cancel-in-progress: false
```

含义：

- 不取消正在写入数据或部署的生产任务。
- 后续运行排队，避免两个生成器同时修改 `main`。
- 推送前如果远端已经变化，任务失败关闭，而不是 force push 覆盖人工改动。

## 新鲜度监控

[`monitoring.yml`](../.github/workflows/monitoring.yml) 在每小时第 41 分钟运行：

```yaml
on:
  schedule:
    - cron: "41 * * * *"
```

它使用只读权限检查：

- `main` 的精确 SHA、提交时间与线上 `ai_stack_release_v1.json`。
- SHA 分歧是否超过 3 小时，生产 release 是否超过 12 小时未更新。
- marker schema、release ID 和时间字段是否有效；长期状态直接查看 Actions 历史和 Summary。

监控使用只读 Actions 权限，不打印 `GITHUB_TOKEN`。

## 故障分类

| 阶段 | 常见信号 | 处理 |
| --- | --- | --- |
| 采集 | crawler 步骤失败、来源超时 | 检查单个来源和超时预算，不先放宽质量闸门 |
| 内容质量 | manifest、历史固定点失败 | 查看具体文章原因，修生成器或透明归档 |
| 派生数据 | 图谱/趋势构建或哈希失败 | 确认 schema、分片和确定性输出 |
| 搜索/构建 | Hugo、Pagefind 失败 | 检查模板、站内引用和 catalog 契约 |
| 写入冲突 | Commit generated data 失败 | 同步最新 `main` 后重新运行，不 force push |
| Pages | artifact/upload/deploy 失败 | 核对 Pages 设置、权限和 artifact |
| 新鲜度 | live graph/trends 超过 12 小时 | 追溯最近完整刷新与部署，不掩盖陈旧数据 |

## 安全要求

- 不在日志中输出认证值、cookie、完整请求头或私有 endpoint。
- 示例只用 `replace_with_your_token` 等明显占位符。
- 工作流权限保持最小化；模型阶段只读、CAS writer 无模型密钥、监控只读、Pages 权限只进入 deploy。
- 手动删除文章先 dry run，再重建质量、图谱、趋势和搜索资产。
